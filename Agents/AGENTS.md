# Great Voyage — Codex 작업 지침

> 적용 범위: 새 Unity 프로젝트 저장소 전체. 이 파일은 새 작업에 진입하는 모든 Codex 에이전트의 공통 규칙이다.
> 프로젝트 목적: 2D 함선 운영·무역·선내 생활 게임을 **최종 구조 위에서, 실제 게임에 사용할 수 있는 작은 완성 단위**로 누적 개발한다. 기능 수는 제한하되 설계·동작·물리·사용감·시각·성능·안정성을 축소하지 않는다.

## 1. 시작할 때 반드시 할 일

1. 현재 사용자 요청의 목표·범위·허용 행위를 확인한다. 추정으로 범위를 확대하지 않는다.
2. 읽기 전용으로 Git 브랜치·HEAD·작업 트리·스테이징·최근 변경 사항을 확인한다. 사용자 변경을 덮어쓰지 않는다.
3. `CurrentState.md`에서 실제 진행 단계, 현재 승인·미해결 항목 및 검증 상태를 확인한다.
4. 작업에 필요한 문서를 읽는다. 작업 범위가 복수 도메인에 걸리면 `Architecture.md`의 의존성·소유권부터 검토한다.
5. 실제 Unity Scene·Prefab·코드·패키지·메타데이터를 확인한다. 문서의 계획 또는 과거 성공을 현행 구현의 증거로 사용하지 않는다.
6. **코드 작성 전에** 아래 작업 계약을 사용자에게 간결하게 제시한다. 이미 승인된 계약 범위라면 불필요하게 재승인받지 않고 진행한다.

### 작업 계약 (요청 단위로 대화에 제시; 별도 로그 파일 생성 금지)

- 기획 근거: `GameDesign.md`의 해당 절과 인수 기준 A번호, 관련 D/E/G 참고 이미지.
- 목표: 이번 작업에서 플레이어가 실제로 확인할 **한 가지 대표 동작**과 화면·공간의 결과.
- 범위: 구현할 동작 / 화면에 남겨 둘 무반응 Frame / 이번에 건드리지 않을 영역.
- 설계: 변경되는 도메인 객체·소유권·의존 방향·상태 전이·생명주기·저장 영향.
- 자산: 만들거나 변경할 Scene·Prefab·Sprite·UI·스크립트 및 예상 경로.
- 품질 속성: 이번 변경이 건드리는 **조작 반응·이동 연속성·충돌 역할·애니메이션/피드백·프레임 비용·안정성**과 실제 플레이에서 기대되는 관찰 결과. 영향 없는 항목은 사유를 적어 제외한다.
- 설계 선택: 채택할 방법, 고려한 대안, 필요한 복잡도와 품질·성능상의 근거. 지시의 문자만 충족하는 최저 비용 구현을 자동 선택하지 않는다.
- 검증: 구조 / 시각·동작 / 실제 조작·기능 / 저장 / 성능 가운데 해당 항목의 방법과 합격 조건.
- 위험: 미정 기획, 외부 에셋 부재, 구조 변경, 기존 데이터 영향 및 필요한 사용자 결정.

## 2. 문서 위치와 권위

관리 문서 원본은 저장소의 Agents/에, 참고 자료는 Agents/References/에 둔다. 저장소 루트 AGENTS.md는 진입 안내만 담당한다. 이 문서의 상대 경로는 Agents/ 기준이다. Unity 임포트 대상인 Assets/와 분리하며, Git으로 함께 공유한다.

| 문서 | 유일한 책임 |
|---|---|
| `GameDesign.md` | 게임의 확정 규칙·기획·공간/화면 요구·A01~A28 인수 기준 |
| `VisualStandards.md` | 기획 이미지의 적용 우선순위, 실게임 시각 품질, 비활성 Frame·시각 게이트 |
| `Architecture.md` | 도메인 객체·상태 소유권·의존성·상호작용·생명주기·저장 경계 |
| `ProjectStructure.md` | Unity 기술 환경·경로·에셋·Scene/Prefab/패키지 관리 |
| `DevelopmentRules.md` | 코드 작성·변경 권한·Git·검증 절차·완료 판정 |
| `RoadMap.md` | 현재 프로젝트에 사용할 단계·선행조건·완료 기준 |
| `CurrentState.md` | **현재 상태만** 기록하는 에이전트 인수인계 원본 |

**우선순위**: 최신 사용자 명시 지시 → `GameDesign.md`의 확정 게임 규칙/시각 자료 역할 → 승인된 `Architecture.md` 설계 계약 → `VisualStandards.md`·`DevelopmentRules.md`·`ProjectStructure.md` → `RoadMap.md` → `CurrentState.md`의 현황. 충돌은 임의로 합성하지 말고 정확한 충돌 항목을 보고한다. Git/실제 파일은 구현된 사실의 근거지만 게임 요구를 변경하는 권한은 없다.

`GameDesign.md`는 두 기획 문서를 통합·정리한 **신규 프로젝트용 게임 명세**다. 15절은 기획 범위 분류이며 개발 단계·작업 허가가 아니다. 새 실행 단계는 `RoadMap.md`만 사용한다. 과거 개발 기록·코드·저장소 문서를 새 기준으로 자동 계승하지 않는다.

## 3. 절대 지켜야 할 구현 원칙

1. **게임 전체의 객체 모델·책임·수명과 경계를 먼저 설계한 후 그 안에 최소 기능을 구현한다.** 기능별 독립 구현을 마지막에 임의 연결하는 작업을 금지한다.
2. 실제 게임 Scene을 목표로 만든다. 도형·텍스트·디버그 창으로 구성한 임시 데모를 제품 기능 완료로 선언하지 않는다.
3. **최소 기능 ≠ 최소한의 구현 ≠ 낮은 품질**. 이번 범위에서 활성화한 동작은 실제 UI·캐릭터·월드 표현, 입력, 상태 전이, 오류·복원과 함께 그 동작에 필요한 연속성·피드백·성능 특성을 갖춰야 한다.
4. 미래 기능은 필요한 화면·상호작용 위치·계층만 Frame으로 준비하고 **명시적으로 비활성**으로 둔다. 클릭해도 성공한 척하지 않고, 가짜 데이터나 우회 기능을 만들지 않는다. 비활성 Frame은 미구현으로 기록한다.
5. 도메인 상태의 원본은 하나다. MonoBehaviour, 화면, 애니메이션, Prefab은 게임 규칙과 저장 상태를 소유하지 않는다.
6. 한 시스템이 다른 시스템의 내부 상태나 UI Controller에 직접 접근해 규칙을 완성하지 않는다. 허용 의존성은 `Architecture.md`에 따른다.
7. 전체 기능을 미리 구현하거나 미래 기능의 범용 프레임워크를 추측해 만들지 않는다. **현재 필요한 객체 경계는 최종 모델과 일치**, 미래 알고리즘은 미구현으로 남긴다.
8. **물리·이동·표현은 엔티티의 역할에 따라 설계한다.** 모든 오브젝트에 Collider/Rigidbody를 일괄 추가하거나, 이동을 좌표 점프·프레임 종속 갱신으로 대체하지 않는다. 예외는 게임 규칙 또는 명시된 전환 연출에 근거한다.
9. 구현 방법은 담당 에이전트가 전문적으로 선택한다. 기술을 과하게 복잡하게 만들 필요는 없지만, 최소 요구만 흉내 내는 구현은 거절하고 **대안 검토→합리적 구현→실제 플레이 평가→개선**을 끝까지 수행한다.
10. 품질은 마지막 단계의 미술·최적화 과제가 아니다. 매 Slice에서 게임플레이·시각/동작·안정성·성능을 영향 범위에 따라 확인하고 기준 미달이면 같은 Slice를 개선한다.
11. 실제 플레이·도안 확인·구조 검증 없이 '완료'라고 쓰지 않는다. 컴파일 성공, 테스트 건수, 정적 검사 통과만으로 게임 품질을 대리 판정하지 않는다.
12. 현재 요청과 무관한 코드·자산·패키지·설계 변경 및 자체 기획 추가를 금지한다.

### 품질 판정 권한

에이전트는 코드 구조와 측정 결과를 검토할 수 있지만 화면의 완성도와 조작감이 사용자 기대에 맞는지는 사용자 수용 없이는 확정하지 않는다. Unity 실행·녹화·Profiler가 불가능하면 해당 항목은 `미확인`이며, 추정으로 통과 처리하지 않는다. `DevelopmentRules.md`의 횡단 품질 계약을 모든 활성 기능에 적용한다.

## 4. 작업 정지 조건

다음 중 하나면 억지 구현을 계속하지 말고 차이·영향·추천 선택지를 보고한다.

- `GameDesign.md` 확정 규칙이나 D/G 시각 기준과 충돌하는 구현만 가능한 경우.
- 설계된 상태 원본·객체 책임·의존성 계약을 깨야만 기능이 연결되는 경우.
- 필수 실제 게임용 아트가 없어서 도형 기반 화면으로만 만들 수 있는 경우. 제품 작업을 '완료' 처리하지 않는다.
- 사용자 승인 없는 파괴적 Git 작업, 저장 데이터 초기화, 대규모 아키텍처 교체가 필요한 경우.
- 필요한 Scene/Prefab 참조 또는 테스트 실행 결과를 확인할 수 없는 경우. 해당 품질 주장을 `미확인`으로 남기며 검증 없이 다음 단계 완료로 승격하지 않는다.
- 대표 동작이 끊기거나 입력이 불안정하거나 필수 충돌 정책이 틀린데도 기능 조건만 충족했다는 이유로 계속 확장해야 하는 경우. 결함을 먼저 해결한다.

## 5. 제출 형식

매 작업 종료 시 다음만 보고한다: **변경한 실파일 / 실제 게임에서 관찰된 동작·조작감 / 선택한 구현 방식의 근거 / 구조·시각·동작·물리·기능·저장·성능의 통과·미통과·미확인 및 증거 / 미구현 Frame / 남은 위험**. `CurrentState.md`를 현재 상태로 갱신하고, 대화 원문이나 에이전트의 과정 로그는 별도 MD에 남기지 않는다. 사용자가 승인하지 않은 Git 커밋·푸시·브랜치 병합은 수행하지 않는다.
