# Great Voyage — P5 Water 구현·승인 로드맵 (최종 합의 기준)

- 문서 유형: **단계별 작업 계약 및 승인 게이트**
- 상태: **단계 순서·분리 원칙 승인** / 각 단계 구현, 시각 수용, 기술 선택은 아직 승인 전
- 상위 범위: 전체 게임 `Agents/RoadMap.md`의 P5 중 **해수 시각 시스템 하위 로드맵**. 출항·방향타·항해·입항의 제품 기능 요구를 대체하지 않음.
- 연관 문서: `P5_OceanSystem_Design.md`, `P5_Water_VisualDesign.md`, `P5_Water_References.md`
- 작성 의도: AI 에이전트가 결과 중심으로 임의 단축하거나 선행 승인 없이 후속 효과를 섞어 제작하는 것을 방지한다.

## 공통 계약

1. **승인 한 단계씩**: 이번에 명시적으로 승인된 단계만 구현한다. 다음 단계 진입 전에 실제 Game View/동작 증거와 사용자 수용을 요청한다.
2. **기존 기능 보존**: 현재 Git/Unity P5를 먼저 검사하고, 이미 작동하는 항해 규칙·저장·입출항·Scene 구성에 영향을 주는 변경을 열거한다. 기존 타일 회전 구현은 목표 설계에 맞지 않지만 이를 제거하는 시점과 관련 영향은 사용자 승인 범위 내에서 결정한다.
3. **최종 시스템과 독립 Slice**: 후속 단계에서 공유할 데이터/책임 경계는 첫 단계에 설계하지만, 아직 활성화하지 않은 물보라·조명·경제/항해 기능을 데모 완성용으로 가짜 구현하지 않는다.
4. **사용자 승인 근거 분리**: 정적 시각, 연속 애니메이션, 실제 조작/항해, 물리 반응, 성능/저장 결과는 서로 다른 증거다. 자동 테스트가 사용자 시각 승인을 대체하지 않는다.
5. **동일 스타일·동일 좌표계**: 선박 화면상 고정, 공통 해수 좌표계, 타일 Transform 비회전·비이동, 상대 흐름의 공유, 선체 형태 기준은 전 단계 강제다.
6. **시각 후속 확장**: 조명은 별도 Stage 5. Stage 2에서 조명·광학 반사를 미리 구현하지 않는다. Stage 2 파도 형상 데이터와 색상 경계는 후속 확장을 고려해 분리한다.
7. **문서상 미정 처리**: 수치·팔레트·선박 자체 회전 연출·SDF 텍스처 규격 등 미확정 조건을 에이전트가 영구 정책으로 확정하지 않는다. 해당 조건이 현재 단계 구현에 필수일 때 결정안을 보고한다.

## Stage 1 — 해수 시스템 기반 구조 확정

**목표**: 현행 P5와 목표 구조의 차이를 파악하고 데이터 원본·수명·좌표계·Scene/Prefab 소유권·후속 Lighting 확장 지점을 확정한다.

**필수 산출**:
- 기존 P5 Navigation State, 해수 타일 회전 경로, World/Prefab, Material/Shader/Particle의 실제 관계 조사.
- 현재→목표 구조의 책임/참조/의존 방향 비교. Navigation State는 항해 상태의 단일 원본.
- Relative Flow, Ambient Motion, Ocean Shader, Hull WaterlineShape/SDF, 2D Collision, Particle 2종, 후속 Lighting의 계약 정의.
- 선체 `Hull/Interior` Hierarchy 분리와, Layer는 실제 필요한 충돌/렌더 필터링 용도라는 구분 명시.
- 물리적 이동이 아닌 **선박의 화면상 위치 고정**과 논리적 항해 진행의 관계 명시.
- 후속 법선/기울기 생성 가능한 형상 정보 경계 설계(실제 조명 구현은 하지 않음).
- 변경 예상 Scene/Prefab/Art/Script, 기존 데이터 영향, 구조 검증 및 위험 보고.

**제외**: 실제 Water Shader·포말·파티클·조명 구현, 항해/입항 규칙 임의 변경.

**통과 게이트 G1**: 사용자 설계안 승인. 설계 문장만으로 실제 기능이 구현되었다고 표시하지 않는다.

## Stage 2 — Stylized Toon Water 기본 표현

**목표**: 선박·항해 상태·선체 충돌·조명에 의존하지 않는 **바다 그 자체의 아트 스타일**을 완성한다.

**필수 표현**:
- 청색·청록색의 여러 단계 색면, 넓고 굴곡진 파도 띠, 약한 잔물결, 파도 마루를 따라 끊겨 나타나는 자연 포말.
- Noise는 곡선·경계를 변형하는 보조. 무작위 Noise 스크롤만으로 스타일 완료 금지.
- 공통 셰이더·공통 시간·공통 좌표계로 서로 다른 타일 경계가 자연스럽게 연속.
- 자연 Ambient Animation은 항해 속도 0에서도 동작.
- 색면·파도 형상·애니메이션을 논리적으로 분리. 후속 Normal/Lighting 파생이 가능한 데이터 경계 마련.

**승인 게이트 G2-A — 정적 표현**: 선박·HUD·입자·조명 없는 동일 시점 Game View로 색상·파도 윤곽·포말을 사용자 수용. 이때 다음 소단계를 자동 진행하지 않는다.

**승인 게이트 G2-B — 자연 애니메이션**: 실제 움직임 자료에서 패턴 형태 보존, 속도, 반복성, 타일 경계 및 시각 연속성을 사용자 수용.

**제외**: 상대 항해 흐름, 선체 반응, 파티클 충돌/항적, 현실적 조명·Specular·반사.

## Stage 3 — 항해 상태 연동과 상대 해수 흐름

**목표**: 화면상 고정된 선박을 기준으로 항해 방향·속도·가속/감속·회전 상태가 해수 표현에 반영되도록 한다.

**필수 표현**:
- 항해 상태에서 동일한 상대 유속 기준을 계산. 선박 전진 시 바다의 항해 유래 흐름은 반대 방향.
- 타일/배경 Transform 회전·이동 대신 셰이더 샘플링 좌표나 동등한 내부 흐름 제어.
- 자연 파도 자체의 움직임과 항해 기인 흐름을 별도로 계산·합성.
- 정지에서는 항해 흐름이 0으로 가고 자연 파도는 유지; 가감속·방향 변경에서 시각적 점프 방지.
- Stage 2의 승인된 물결 형태·색면·자연 애니메이션을 유지.

**제외**: Hull SDF 국소 분기/선미 후류, 충돌 파티클, 조명.

**통과 게이트 G3**: 동일 시점의 정지·전진·가속·감속·방향 변화 비교 및 실제 조작 자료를 사용자 수용. 좌표계 변환·타일 Transform 불변 검증.

## Stage 4 — 선체 형상 기반 해수·입자 상호작용

**목표**: 선체의 수면선 형상에 따라 물살이 갈라지고, 흐르며, 충돌하고, 후류를 만든다.

**필수 구성**:
- `Hull/Interior` Hierarchy 책임 구분. `WaterlineShape`는 Bake의 명시적 원본, 내부 Floors/Walls/Facilities는 제외.
- 선박별 WaterlineShape에서 **Editor Bake**로 Hull SDF/Mask 산출. 선체 경계 거리와 방향은 셰이더 유동 계산에 공급. SDF 자체를 물리 유체 계산기로 간주하지 않음.
- 충돌형 입자용 PolygonCollider2D 등 선체 충돌 데이터는 SDF와 역할 분리; Rigidbody2D는 필수 아님.
- 선수 좌우 분기, 선측 접선 흐름, 선미 후류/포말의 범위·감쇠를 반영. 먼 바다는 본래 흐름 유지.
- **A 비충돌 미세 입자**는 선체 통과 허용. **B 충돌 반응 입자**는 반사·감속·소멸·작은 입자로 분열/확산. 선수/선측 물보라와 선미 항적을 구분.
- 모든 효과는 Stage 3의 항해 상태와 상대 흐름 기준을 공유하되, 서로 다른 반응 모델을 가진다.
- 서로 다른 선체의 SDF 데이터 교체로 공통 셰이더·파티클 시스템을 재사용할 수 있는지 검증.

**검증 순서(동일 Stage 4 내)**: 선체 형상/Bake 증거 → 국소 물결·포말 분기 → A/B 입자 및 충돌/분열 → 선미 항적 → 두 선체 형태 비교. 엔진 Collider만 넣으면 물결 분기가 자동 생성되는 것으로 간주하지 않는다.

**제외**: 실제 유체역학 CFD, 런타임 재Bake가 필요한 선체 형태변형, 조명.

**통과 게이트 G4**: 선수/선측/선미 연속 시각 검증 + 두 입자 계열 구분 + 다른 선체 2종 이상 + 충돌/성능 측정 및 사용자 수용.

## Stage 5 — 수면 조명 및 반사(독립 단계)

**목표**: Stage 2~4에서 승인된 수면에 **가상 법선/기울기 기반의 현실적 원리를 활용한 Toon 조명**을 더한다.

**필수 표현**:
- 수면 형상과 표면 색상 계산은 보존하고 조명 계산만 별도 계층으로 추가.
- 광원 방향·색상·강도에 대응하는 법선 기반 명암과 선택적인 반짝임/Specular.
- 실제 3D 파도 메시/PBR 물리 수면/화면 전체 반사·굴절 등은 자동 요구가 아님.
- 동일한 장면에서 조명 **Off/On**을 비교할 수 있고 Off일 때 이전 승인 Water를 재현할 수 있어야 함.
- 실제 2D Renderer에서 2D Light와 커스텀 조명 계산의 역할/호환성/성능을 확인한 후 채택.

**통과 게이트 G5**: 조명 Off/On의 동일 장면 비교, 광원 방향 변화, Toon 화풍·파도 형태/움직임 보존, 사용자 조명 시각 승인. 조명 승인과 기본 Water 승인 기록은 분리.

## Stage 6 — 전체 통합·안정성 검증

**목표**: P5 항해 시스템과 Water의 모든 구성 간 상태·품질·성능·저장/복원 일관성을 검증한다.

**필수 검증**:
- 선체 크기/형상이 다른 최소 두 종류, 정지/전진/가감속/방향전환, 입출항 화면 전환/복귀.
- 타일 경계·장시간 UV 정밀도·파티클 누적/소멸·원점/좌표계·입자 충돌 성능.
- 구조·Editor/PlayMode·실제 Game View·연속 동작·Windows Player를 가능한 범위에서 구분 검증.
- 게임 시간, 논리적 위치, 항해 결과·저장/복원 및 이전 P4 기능 회귀.
- 단일 인물 또는 Editor 기준선만으로 다수 입자·실제 Player 성능을 보증하지 않음.
- 화면의 화풍/동작/조명과 전체 기능의 **사용자 최종 수용**을 분리해 기록.

**통과 게이트 G6**: 검증 결과와 미확인을 명시한 뒤 사용자 최종 통합 승인. Stage 1~5 사용자 승인 근거를 보존한다.

## 착수 지시 시 에이전트 제출 계약

매 단계마다 구현 **전**: 현재 상태·기존 구현과 차이·범위·비범위·책임/데이터 흐름·수정 대상 파일/자산·복원/회귀 위험·검증 계획·사용자 판단 필요한 미정사항을 보고한다.

매 단계마다 구현 **후**: 실제 변경 파일·Game View 정지/연속 자료·테스트 결과·미구현/미확인 항목·선행 단계 회귀 결과·다음 단계로 진행 가능한 조건을 보고한다. **사용자 승인 전 다음 단계 착수 금지.**

## 추후 결정해야 하는 입력(미확정 목록)

- 방향 변경 시 선박 Sprite 자체가 회전하는가, 아니면 선수의 화면 방향도 고정하고 수면 흐름만 회전하는가?
- 확정 색상 팔레트, 파도 폭·밀도·형태, 자연 움직임 속도, 포말/입자/후류의 최종 수치.
- Hull SDF 해상도·파일 포맷·Bake 방식, Collider와 물결 형상 원본의 세부 제작 방식, 비용 한계.
- 조명 물리 근사와 Toon화 단계·Specular 범위·최종 밝기/태양 방향, 실제 지원 플랫폼의 성능 목표.

미정 항목은 단계 진입 시 필요성에 따라 **결정 요청**하고, 테스트 편의상 임시값을 쓰더라도 승인된 최종값으로 문서화하지 않는다.
