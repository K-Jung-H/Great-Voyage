# Great Voyage — P5 항해·해수 상호작용 시스템 설계

- 문서 종류: **시스템 설계 방안**
- 상태: **대화에서 승인된 설계 의도 확정** / 실제 구현 방식·수치·시각 결과는 별도 승인 및 검증 대상
- 범위: P5 해상 항해의 상대 운동, 선체 형상 기반 해수 흐름, 셰이더·파티클·충돌·자산 구조
- 연관 문서: `P5_Water_VisualDesign.md`, `P5_Water_References.md`, `P5_Water_ImplementationRoadmap.md`
- 프로젝트 기준: Unity 6 / URP 2D / uGUI·Prefab·Scene 직렬화 우선 / 기존 `Agents/Architecture.md`, `Agents/DevelopmentRules.md`, `Agents/RoadMap.md` 및 실제 P5 구현과 대조 필수

## 1. 핵심 결정

**Ship-Centric Relative Ocean Flow + Hull-Aware Ocean Flow**를 채택한다.

1. 항해 중 **선박은 화면상 고정**하며, 바다와 포말·물방울이 상대적으로 움직여 항해를 표현한다. *시각적으로 고정*이라는 의미로, 게임의 논리적 위치·항해 거리·입출항 상태를 고정한다는 뜻이 아니다.
2. 항해 방향·속도는 권위 있는 **Navigation State**가 관리한다. 시각 효과는 이를 읽을 뿐 항해 규칙을 변경하지 않는다.
3. **바다 타일 Transform의 위치·회전·크기를 항해 표현에 사용하지 않는다.** 해수 타일은 고정된 배치 자산으로 두고 공통 셰이더의 UV/샘플링 좌표 또는 동등한 내부 좌표계를 움직인다.
4. 자연 물결(환경 애니메이션)과 항해에 따른 상대 유속을 **분리**한다. 정지 상태에서도 자연 물결은 유지될 수 있지만, 항해로 인한 흐름·항적은 속도 0에서 사라져야 한다.
5. 해수 셰이더와 파티클은 **동일한 항해 상태 및 상대 흐름 기준**을 사용한다. 효과별 이동·방출 규칙은 서로 달라도 된다.
6. 선수에서는 물살이 좌우로 갈라지고, 선측을 따라 흐르며, 선미에는 난류·포말 항적이 남는다. **실제 유체역학 시뮬레이션이 아니라 일관된 실시간 시각 모델**이다.
7. 선체 윤곽과 내부 시설은 **Hierarchy상의 소유권을 분리**한다. Layer는 필요한 물리 충돌·렌더링 필터링에 별도로 사용한다.
8. 해수 디자인은 `P5_Water_VisualDesign.md`의 **Unity 2D Stylized Toon Water 시각 규격**을 따르며, 기본 화풍 승인 전에 물보라를 덧씌워 기본 셰이더의 품질 부족을 가리지 않는다.
9. **수면 조명은 의도적으로 후속 독립 단계**로 미룬다. 최초 Water Shader 단계에서는 태양광·Specular·반사·현실적 Normal 조명 등을 구현하지 않는다. 파도 형상/색면과 최종 셰이딩 계산을 분리하여 나중에 조명을 추가할 수 있게 한다.
10. 기본 파도, 상대 흐름, 선체 상호작용, 조명은 **각각 별도 승인 게이트**다. 후속 효과가 선행 승인 결과를 임의로 재해석하거나 덮어쓰면 안 된다.

## 2. 책임·데이터 흐름

```text
Navigation State (방향·속도·회전 / 논리적 항해 정보)
                  │ read only
                  ▼
Relative Flow Resolver (선박 기준 상대 흐름 벡터)
                  │
        ┌─────────┴─────────┐
        ▼                   ▼
Hull Shape Source      Ocean Ambient Motion
(수면선 형상 원본)        (항해와 독립된 자연 물결)
        │
        ├── Editor Bake → Hull SDF / Mask
        └── 충돌 형상 → HullCollision
                  │
                  ▼
Hull-Aware Flow (거리·외곽 방향·선수 분기·선측 유동·선미 후류)
        ┌─────────┴──────────┐
        ▼                    ▼
Ocean Shader Driver    Ocean Particle Controller
        │                    │
모든 바다 타일 공통 표현   A 비충돌 / B 충돌 / 파편·물보라·항적
```

- **Navigation State**: 항해의 방향·속도·회전·논리적 진행을 소유하는 유일한 원본. P5 기존 모델과 대조해 중복 생성 금지.
- **Relative Flow Resolver**: 선박의 상대적인 물 흐름을 계산한다. 선박이 전진하면 표면 패턴의 주 흐름은 반대 방향이다. 회전 시 사용한 좌표계 변환을 전 파이프라인에서 통일한다.
- **Hull Shape Source**: 수면과 접촉하는 **Waterline Hull Shape**를 정의하는 단일 형상 원본. 배의 전체 Sprite 외곽이나 갑판 시설 윤곽을 그대로 사용하지 않는다.
- **Hull Mask/SDF**: 셰이더가 선체의 내부·외부와 경계까지의 거리를 파악하도록 제공한다. SDF 자체가 자연스러운 물살을 자동 계산하지는 않는다.
- **Hull-Aware Flow**: 상대 흐름을 선체의 거리·경계 법선/접선에 따라 변형한다. 선체 근처에서만 영향을 주고 먼 바다는 공통 흐름을 유지한다. 선미 후류는 별도 감쇠·난류 함수로 표현한다.
- **Ocean Shader Driver**: 공통 셰이더의 시간·색상·방향·속도·흐름 오프셋·마스크 변환 등을 제공한다. 개별 타일에서 서로 다른 시간이나 방향을 임의 생성하지 않는다.
- **Ocean Particle Controller**: 같은 상대 흐름을 기준으로 입자 이동, 충돌·반사·분열·확산·수명 및 포말 생성량을 제어한다.
- **Ocean Lighting (후속 선택적 셰이딩 계층)**: 승인된 수면 형상에서 유도할 수 있는 법선·기울기와 광원 상태를 읽어 명암/Specular/하이라이트를 계산한다. **P5 해수 개발의 5단계 전에는 구현·활성화하지 않는다.** 파도 형상을 조명 편의를 위해 재설계하지 않는다.
- **구현의 자유도**: 위 명칭은 책임을 설명하기 위한 것이며 클래스 하나씩 의무적으로 생성하라는 뜻이 아니다. 객체 분할·파일명은 실제 Architecture와 함께 검토한다.

## 3. Scene / Prefab / 물리 형상 구조

권장 구조(개념 예시, 클래스·실제 파일명 확정 아님):

```text
Ship
├─ Hull
│  ├─ Visual                # 선박 외형 표현
│  ├─ WaterlineShape        # SDF Bake를 위한 수면선 윤곽
│  └─ HullCollision         # 입자와 선체의 2D 충돌 형상
├─ Interior
│  ├─ Floors
│  ├─ Walls
│  └─ Facilities
└─ OceanEffects
   ├─ HullFlowBinding
   ├─ SurfaceEffects
   └─ FoamParticles
```

- `Hull`은 외형/수면선/충돌 책임을 맡고, `Interior`는 선내 바닥·벽·시설만 맡는다. 선내 시설 변경이 해수 SDF 재생성으로 이어지지 않아야 한다.
- `WaterlineShape`와 `HullCollision`은 다를 수 있다. **물과 접촉하는 형상**, **입자가 맞는 형상**, **캐릭터가 막히는 형상**을 무분별하게 동일 Collider로 결합하지 않는다.
- **PolygonCollider2D**는 정교한 선체 외곽 및 입자 충돌에 적합한 기본 후보이다. **Rigidbody2D는 SDF 데이터 전달에 필요하지 않다.** 현재 화면상 고정 선체는 정적 Collider 구성이 가능하다. Rigidbody2D가 필요한지는 실제 충돌 방식·성능 테스트를 보고 결정한다.
- Layer는 입자-선체 충돌 필터링 등 필요할 때 사용한다. Bake 포함 대상은 기본적으로 **명시적 WaterlineShape 참조**로 선택하고, Layer 전체를 무조건 Bake하는 방식은 금지한다.
- 실제 생성·연결은 Unity Editor에서 편집 가능한 Scene/Prefab과 직렬화 참조를 사용한다. 해상 화면 전체를 실행 중 임시 객체 계층으로 생성하지 않는다.

## 4. Waterline Mask / SDF Bake

### 4.1 데이터 의미

- **일반 마스크**: 선체 내부/외부를 구분한다.
- **SDF(Signed Distance Field)**: 선체 경계를 기준으로 내부 음수, 경계 0, 외부 양수인 **부호 있는 거리**를 가진다.
- 셰이더는 SDF에서 거리를 샘플링하고, 필요하면 거리의 공간 기울기(gradient)로 외곽 방향을 근사할 수 있다. SDF만으로 물의 유동 경로가 자동 생성되는 것은 아니다.

### 4.2 Bake 시점과 런타임

1. Editor에서 각 **선박 모델의 WaterlineShape**를 읽는다.
2. 형상 내부·외부·경계 거리를 계산해 **선체 로컬 좌표 기반 SDF Texture 또는 동등한 데이터**로 Bake한다.
3. 생성 자산을 선박 Prefab의 해당 형상 버전과 연결한다.
4. 실행 중 **현재 선박에 해당하는 SDF**와 로컬↔월드(또는 선박 기준) 좌표 변환을 셰이더에 공급한다.
5. 선박 위치/회전 변화에 대해 텍스처를 재생성하지 않고 좌표 변환으로 처리한다. 크기 변경에는 거리 단위 보정이 필요하다.
6. **선체 윤곽이 실제로 변경되었을 때**에만 Bake를 다시 수행한다. 동적 구조변형이 나중에 도입되면 별도의 갱신 정책을 설계한다.

### 4.3 선박별 확장

- 길고 뾰족한 선체, 넓고 둥근 선체 등은 **선박별 SDF/형상 데이터 교체**로 동일한 공통 해수 시스템을 사용할 수 있어야 한다.
- 비균일 Scale에서는 거리·법선 해석 오류가 날 수 있으므로 비균일 변형 보정 또는 해당 형상 재Bake 정책을 선택해 테스트한다.
- 극단적으로 복잡한 형상은 SDF만으로 자연스러운 후류를 보장할 수 없다. 필요할 때 선박별 최소 보조 파라미터(선수·선미 기준점, 흐름 영향 반경, 후류 폭 등)를 허용하되 **보편적인 화면 결과를 위해 임의로 선체 형태를 왜곡하지 않는다.**

## 5. 물결 셰이더 연결

- 해수 타일 모두 동일한 **셰이더 구조와 공통 흐름 기준**을 적용한다. 필요한 Material 파라미터 차이는 승인된 환경 차이(연안/외해 등)에 한정한다.
- UV 흐름/곡선 변형과 실제 타일 Transform을 구분한다. **타일 회전·타일 이동으로 항해를 표현하지 않는다.**
- 타일별 시간·위상/무작위 시드의 불일치로 이음매가 생기지 않도록 월드/공통 해수 좌표와 공유 흐름 오프셋을 사용한다.
- *자연 물결*과 *항해 상대 흐름*을 분리하여 정지·전진·감속·회전 조건을 각각 검증한다.
- **선체 부근**에서는 Hull-Aware Flow가 물결 샘플링 좌표/포말을 수정하며, **선체 바깥**에서는 본래의 큰 파도와 잔물결 형태가 유지된다.

## 6. 파티클 계열과 충돌 표현

| 종류 | 의미 | 선체 충돌 | 효과 |
|---|---|---|---|
| **A. 비충돌 입자** | 작은 물방울·표면의 미세 표현 | 끔 | 공통 상대 유동으로 이동, 필요 시 선박 아래 렌더링되어 시각적으로 관통 가능 |
| **B. 충돌 입자** | 선체와 상호작용하는 포말·물방울 | 켬 | 충돌 위치/법선/상대 속도에 따라 반사·감속·소멸·분열·확산 |
| **선수/선측 물보라** | 선체 접촉의 국소 반응 | 발생 지점 기반 | 접촉 위치와 상대 유속에 따른 방출량·방향 |
| **선미 항적** | 지나간 해수의 후류 | 지속 시간 기반 | 뒤쪽에 형성, 거리/시간에 따라 확장·감쇠 |

- B 입자의 분열은 **원래 입자를 소멸/축소시키고 작은 후속 입자를 다수 방출하는 시각 효과**다. 실제 유체 방울 분할 해석을 요구하지 않는다.
- Unity Particle System의 **Collision (2D)** 및 **Sub Emitters**를 우선 검토한다. 단, 원하는 흐름장 추종·선체 접선 반응에 기본 모듈만으로 한계가 있으면 제한된 사용자 정의 입자 제어를 검토하고 CPU 비용을 측정한다.
- 모든 입자에 무조건 Collider를 적용하지 않는다. 수명·동시 입자 수·Sub Emitters 생성량을 제어한다.
- 움직임 기준은 공통이지만 자연 파도·포말·충돌 물보라가 **동일 속도·방향으로 기계적으로 이동하는 것은 금지**한다.

## 7. 수면 조명 확장 계약 (후속 단계 전용)

- **확정**: 기본 파도 형태·움직임·색면이 사용자 승인된 이후에만 조명 개발을 시작한다. 조명을 파도 시각적 합격의 필수 선행조건으로 만들지 않는다.
- **선행 구조 요건**: 기본 물결의 공간·시간·형상 정보를 색상 결과와 구분하고, 필요 시 높이/기울기/법선을 파생시킬 수 있는 설계 여지를 확보한다. **이것이 초기 단계에서 높이 텍스처나 Normal Map을 의무적으로 생성한다는 뜻은 아니다.**
- **조명 단계 기능**: 수면 법선 기반 명암, 광원 방향·색상·세기, 선택적 Specular/반짝임을 추가하되 Toon 스타일과 기존 파도 형태·움직임을 보존한다. 실제 반사/투과 또는 3D 물리 수면은 자동 범위에 포함되지 않는다.
- **격리**: 조명을 끈 상태에서 앞 단계와 동일한 파도 결과를 재현할 수 있어야 한다. Lighting On/Off 비교를 수용 증거로 제출한다.
- **기술 선택 미확정**: URP 2D Light2D/2D Lit Shader Graph만으로 목표 표현이 가능한지, 별도 커스텀 광원 계산이 필요한지는 5단계에서 현재 Unity 버전과 Renderer 설정을 확인한 후 결정한다.

## 8. 검증 시나리오와 단계 게이트

1. **기본 화풍 우선**: 선박을 제거한 독립 해수 화면에서 Water 디자인의 정적 구조 확인 → 사용자 승인 → 자연 파도 움직임 확인 → 승인. 상대 운동·입자·선체 효과·조명을 미리 중첩해 보여주지 않는다.
2. **선박 정지**: 자연 물결만 지속하며 항해에 의한 상대 흐름, 접촉 물보라, 항적은 정지/감쇠한다.
3. **일정 전진**: 타일 Transform 불변, 상대 해수 흐름 반대 방향, 선수 분기·선측 유동·선미 후류가 일관된다.
4. **가속/감속**: 물결/포말/충돌 효과의 관련 변화가 자연스럽다. 값과 곡선은 실제 시각 검토 후 확정한다.
5. **방향 전환**: 선체/해수의 좌표계가 일치하며, 타일 회전으로 대신하지 않는다.
6. **형상 변경**: 좁은/넓은 선체에 다른 WaterlineShape와 SDF를 사용해 같은 코드로 결과 검증.
7. **입자 비교**: A는 비충돌, B는 반사·분열/확산. 선체 관통은 A에만 의도적으로 허용.
8. **연결성/장시간**: 타일 이음매, UV 정밀도, 파티클 누적, 속도 변화 시 튐을 확인.
9. **조명 단계**: 승인된 파도를 유지하면서 조명 On/Off, 빛 방향·세기 변화, 파도 형태와 색면 보존을 확인. 파도 승인과 조명 승인은 별도 기록.
10. **회귀/실행**: 기존 P5 입출항·게임 상태·저장 복원에 영향이 없는지 확인. EditMode/PlayMode/실제 Game View/Windows Player 테스트 근거를 분리해 기록.
11. **성능**: Editor 수치만으로 Player 성능을 주장하지 않는다. 대표 입자 밀도에서 GPU 셰이더·CPU 충돌·GC/Frame Time을 측정한다.

## 9. 아직 확정되지 않은 사항 (임의 결정 금지)

- 선박의 **방향 전환 시 선박 Sprite도 회전하는지**, 아니면 화면상 선수 방향까지 고정한 채 상대 해수 흐름 방향을 회전시키는지.
- 수면 색상 단계·정확한 색상 값, 파도 크기·밀도·속도, 포말 양·항적 길이, 입자 충돌/분열 확률의 최종 수치.
- SDF 해상도·포맷·Bake 툴 형태 및 기본 Particle 모듈과 커스텀 계산의 정확한 분담.
- 물결·포말이 실제 게임에서 보여야 할 최종 시각 품질: 정지 이미지와 연속 동작의 **사용자 수용이 필요**하다.
- 조명 구체 모델·빛 방향·명암 강도·반사/Specular 수준, 2D Light와 커스텀 조명의 기술적 분담.
- 실시간 SDF 생성은 **현재 기본 요구가 아니다**. 형상 편집 뒤 Editor 재Bake를 우선하고, 런타임 변형은 별도 승인한다.
- 타일이 반드시 Unity Tilemap 컴포넌트라는 뜻이 아니다. 현재 실제 수면 렌더 방식과 연결하되, Transform 비회전·비이동 및 타일 간 연속성은 강제한다.

## 10. Codex 수행 계약

1. **현 P5 구현 코드를 읽고** 타일 회전의 책임/의존을 확인한다. 이전 P4/P5 동작·저장 규칙을 임의로 바꾸지 않는다.
2. 구조 비교안(현재→목표), 수정 대상 Scene·Prefab·Material·Shader·Script, 보존할 동작과 테스트 계획을 **수정 전** 보고한다.
3. 사용자 승인 없이는 아키텍처 교체나 기존 제품 Scene/Prefab을 수정하지 않는다.
4. 실제 구현은 `P5_Water_ImplementationRoadmap.md`의 **6단계**와 승인 게이트를 따른다. Stage 2 내부에서도 정적 스타일 승인과 자연 애니메이션 승인을 구분한다. Hull 상호작용은 SDF/흐름장과 파티클을 포함하여 Stage 4에서 단계적으로 검증하며, 조명은 Stage 5에서만 구현한다.
5. 명세 문구만 충족하는 임시 효과나 별개 생성물을 최종 구현으로 선언하지 않는다. 모든 시각 완료는 실제 Game View 및 사용자 수용으로 판정한다.


## 11. 구현 계약을 오해하지 않기 위한 명시적 판정

| 요구 | 올바른 해석 | 금지되는 대체 |
|---|---|---|
| 선박 화면 고정 | 시각 좌표에서 선체 기준 위치 유지, 논리적 항해는 지속 | 실제 항해 거리/입출항 상태까지 고정 |
| 타일 유지 | 배치 Transform을 항해 표현을 위해 회전·이동하지 않음 | Transform 회전, 타일 전체 이동 |
| 공통 셰이더 | 전체 수면이 공통 시간·좌표·상태를 사용하여 연결됨 | 타일별 독립 시드/흐름·이음매 |
| 선체 형상 기준 | 수면선 윤곽 원본 → SDF와 별도 충돌 형상 | 전체 Sprite/선내 시설을 마스크에 포함 |
| SDF 역할 | 선체 표면까지 거리·경계 방향의 입력 | SDF가 자체적으로 유체 흐름을 시뮬레이션한다고 가정 |
| 입자 두 계열 | A는 비충돌, B는 선체 충돌·반사·분열·확산 | 동일한 모든 입자에 충돌 부여 |
| 조명 분리 | Stage 5에서 별도 추가 및 사용자 승인 | Stage 2의 화풍을 조명 효과로 대체 |

**진행 권한:** 이 문서는 기술 방향의 의사결정과 문서화 승인이다. 코드·Scene·Prefab·기존 P5 결과물의 변경 승인으로 자동 확장되지 않는다. 사용자 지시와 현재 저장소의 적용 규칙을 따른다.
