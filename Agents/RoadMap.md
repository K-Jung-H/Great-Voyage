# RoadMap — 설계 우선·실게임 품질의 단계별 구축

> 이 문서는 **새 프로젝트용 실행 순서**다. `GameDesign.md` 15절은 기획상 **기능 범위의 분류**다. 실제 실행 순서·단계 번호·게이트는 이 문서를 따른다. 기획의 확정 규칙과 A01~A28 수용 결과는 재해석하지 않는다.

## 1. 전체 진행 원칙

**모바일 범위 정정(2026-11-02):** 현재는 PC/모바일 공통 행동 인터페이스와 입력 충돌 방지 경계만 설계한다. 모바일 상세 동작/UX·실제 입력은 기본 프레임워크 완성 및 테스트 통과 후 별도 설계·구현한다. P12는 그 후속 검증 범위이며 구체 착수 순서는 사용자 요청으로 정한다.

**최신 범위 결정(2026-11-01):** 항구 거래·고용·정비 → 출항 → 선내 생활·업무·항해 → 입항·계약 정산의 기본 프레임워크를 완성하고 관련 테스트·실플레이·저장 복원 검증을 통과한 뒤 항해 중 사건·불침번·전투·미니게임을 구체 설계·구현한다. P1은 Event 진입/복귀 연결 경계만 다룬다. 아래 P8의 불침번·사건 연계, P9의 사건/전투 및 관련 후속 항목은 이 선행조건 이후 범위다. 게임 기획의 해당 요구는 삭제하지 않는다.

- 처음에 전체 게임의 **도메인 객체·상태·책임·의존/수명·저장 아키텍처**를 설계한다. 단일 기능을 만든 뒤 서로 억지 연결하는 구조는 허용하지 않는다.
- 구현은 `한 구역/화면에서 실제로 플레이 가능한 완성 단위`를 늘리는 방식으로 한다. **제품 품질을 후반으로 미루지 않는다. 기능의 개수만 작게 만들고 해당 기능의 움직임·물리·조작감·안정성·성능 수준은 낮추지 않는다.**
- 새 기능이 등장하면 해당 공간과 UI의 목표 스타일·실제 자산을 같은 단계에서 준비한다. 기본 도형을 배치한 임시 화면은 중간 기술 확인일 뿐 단계 완료가 아니다.
- 아직 실행하지 않는 조작·화면 요소는 게임 위치와 구조를 유지한 `FrameDisabled`로 구현한다. 임의 성공 메시지·임시 경제/항해 규칙·가짜 데이터는 넣지 않는다.
- 게임 기획의 확정 수치·예외를 유지한다. 후속 기능의 **구조적 연결점**은 먼저 둘 수 있지만 아직 필요하지 않은 게임플레이 알고리즘은 구현하지 않는다.
- 각 단계는 `DevelopmentRules.md`의 **해당하는** 품질 속성·게이트를 통과해야 완료된다. P0 환경 구축과 P1 설계처럼 아직 실제 플레이 기능이 없는 단계에는 G3~G5의 실행 항목을 적용하지 않고 `해당 없음(사유)`으로 기록한다. **P3부터 활성 기능을 완료하려면 G0~G5 전부와 해당 품질 검증을 통과**해야 한다. 다음 단계로의 진행은 선행 의존 범위에 대해 `완료` 또는 사용자 명시적 단계 조정 승인이 필요하다.
- 이 문서에 기록된 계획은 구현/테스트/커밋/푸시의 자동 허가가 아니다. 시작 범위는 현재 사용자 요청으로 정한다.

### 전 단계 공통 품질 원칙

- 매 Slice 시작 시 게임 내 **실제 사용자 경험**을 먼저 기술한다(무엇이 보이고, 어떻게 움직이고, 무엇이 반응하는가). 이어서 책임 모델·물리/공간 정책·표현·성능 비용을 검토한다.
- Codex의 기술 선택은 허용하지만, 구현이 요구 문장만 형식적으로 만족하면 `부분 구현`이다. 실제 Game Play로 평가하고 보완한 뒤 통과한다.
- 이동이 있는 단계에는 일반 이동의 연속성·경로·접촉·프레임 변화·카메라/애니메이션 검증을 포함한다. 물리 객체가 새로 등장하면 **Collider를 왜 쓰는지 또는 왜 필요 없는지**를 분류한다.
- 정상/대표 부하에서 프레임 시간·CPU/물리·GC 비용을 적절하게 확인한다. 초기 단계부터 회귀를 추적하고, P11은 이미 확보한 기반 위에서 **전체 게임 성능·밸런스**를 마무리한다.
- 사용자에게 실제 화면·동작 증거를 제시한다. 정적 검사만 통과한 상태에서 체감 품질을 `완료` 처리하지 않는다.

## 2. 최초 개발의 출발 범위

첫 번째 실제 플레이 목표는 **선장실의 작은 완성 장면**이다. 게임 전체 기능을 만들기 전에 한 장면에서 다음을 실제 게임 수준으로 검증한다.

- 가로형 함선의 선장실을 G02 탑뷰·D02 공간 맥락과 양립하는 완성도 있는 Sprite로 배치한다.
- G03 방향과 맞는 플레이어 캐릭터를 실제 자산/구성으로 배치하고 이동·벽 충돌을 구현한다.
- 책상이라는 월드 상호작용 객체에서 일지 화면으로 진입한다.
- 일지는 D03의 좌측 기록·중앙 지도·우측 설명/이미지·닫기 구조를 Editor Prefab으로 제작한다.
- 현재 필요한 **열기/닫기/중첩 정지·포커스**만 활성화하고, 기록·계획·경로 기능은 명시된 위치에 `FrameDisabled`로 둔다.
- 플레이어 위치·게임 시간 등 이번에 존재하는 상태의 저장·복원 기반을 정식 게임 실행 흐름에서 확인한다.

**위 장면이 시각·구조·실제 조작·복원 기준을 통과하지 못하면**, 단순히 화면이 뜨거나 객체가 움직였다는 이유로 함선·항해·경제 기능으로 넘어가지 않는다.

## 3. 단계별 범위와 승인 게이트

### P0. 새 저장소·기획 원본·실행 환경

**목표:** 깨끗한 새 Git/Unity 프로젝트와 정확한 기획 원본.

- 새 저장소·Unity 프로젝트 생성, 정확한 Unity/패키지/렌더러/입력 버전 기록.
- `GameDesign.md` 통합 게임 명세의 규칙·확정 보완·A01~A28을 대조하고 신규 저장소에 배치. D01~D12 / E01~E11 / G01~G03의 **26개 원본 이미지**를 `References/`에 복사하고 파일을 실제로 열어 링크 검증.
- 7개 신규 관리 MD와 `GameDesign.md`의 문서 역할을 확인. `.meta`, ProjectSettings, Packages, `.gitignore` 검증.
- **제외:** 오래된 소스/Scene/Prefab/상태·저장 데이터·과거 운영 MD·대화 로그 이식.
- **통과:** 빈 새 게임 프로젝트가 열리고 실행/컴파일 가능, 입력/2D 렌더·UI 환경 사용 가능, 참고 이미지 경로가 실제로 유효, 새 저장소가 원본을 추적. Git commit/push는 사용자 승인 후.

### P1. 게임 도메인/객체/생명주기 설계 승인

**목표:** 전체 게임의 구조 계약을 코드보다 먼저 검증.

- `GameDesign.md`의 게임 흐름·기능·A01~A28을 **도메인 소유자/상태/명령/결과**에 연결.
- `Architecture.md`의 세계·함선·선원·업무·항해·일지·경제·계약·사건/전투·저장·UI 경계 확정.
- 핵심 시나리오 검토: 일지 열기/정지; 선원 업무/시설; 독립 입항/계약 및 확정 SaveEvent; 수면 고속 연산/기상 저장. Event는 전략 교체·공통 생명주기·범위별 복원 경계만 검토하며 사건 체크포인트/전투/미니게임 상세는 기본 프레임워크 검증 후로 연기한다.
- 각 객체의 생성/화면 전환/저장 복원/종료 수명, 정의 ID/인스턴스 ID, 비표시 층 상태, 안정적 저장의 소유권 결정.
- 이동/공간 질의·역할별 물리·레이어 충돌·렌더/물리 동기화·표현/카메라의 책임을 모델에 포함하고, 유닛 수 증가 등 주요 비용 확장축을 명시한다.
- 폴더·Scene 수명·테스트 구조가 객체 모델과 일치하는지 확정. 공통 흐름을 GameObject/화면에 강제로 연결하는 방식 금지.
- **통과:** 소유권 없는 가변 상태·역방향 UI 의존·도메인 사이의 순환 참조·다중 결과 적용 루트가 남지 않으며 사용자가 설계 방향을 수용. **이전 단계에서 게임 코드 없이도 확인 가능**.

### P2. 실게임 표현 규격과 첫 화면 아트 수용

**목표:** 도형 프로토타입을 제품 화면으로 받아들이는 실수를 원천 차단.

현재 상태: **P2 Complete.** 사용자 합격 소품 B안·Human 9파트·독립 Repeat 바닥을 실제 Game Scene의 Prefab에 적용하고 기존 일지 UI와 함께 3종 해상도에서 확인했다. 사용자가 최종 Scene의 모습을 수용했다. PPU/피벗/정렬/Canvas/파티션·파츠 참조와 정적 구조 검증은 ProjectStructure 2.3절 및 ApprovedArtValidation/SceneApplication 근거를 따른다. 방향별 파츠와 눈 감기 표시가 준비되어 있으며 실제 행동·입력·충돌·애니메이션 재생·저장·성능 수용은 P3다. 단계 완료는 Git 공유나 P3 자동 착수 허가가 아니다.

- 최신 사용자 합격 B안 고정 명세와 원본 샘플 전용 참조(`VisualStandards.md` 1.3절·`ArtFactory/StyleB.locked.prompt.txt`), G02/G03의 공간·유닛 구성 및 D02/D03를 기준으로 선장실 바닥·벽·책상·플레이어·일지 UI Frame의 **실제 사용 가능한 자산**을 준비한다. 사용자가 최종 채택한 현재 생성 방식과 스타일 문구를 유지하고 별도 스킬·모델·후처리를 임의로 추가하지 않는다. 스타일/생성 방식 수용과 실제 개별 자산/게임 화면 수용을 구분한다. Human은 별도로 수용된 HumanParts.locked.prompt.txt·HumanStyle.json의 9파트 계약을 따르고 소품 화풍을 전파하지 않는다. 수용된 일지 UI는 유지한다.
- PPU/셀·충돌/피벗/정렬/카메라/텍스트/Canvas 규격을 실제 자산으로 검증하고 `ProjectStructure.md`에 기록한다.
- 정식 `Game.unity`와 편집 가능한 월드·캐릭터·UI Prefab을 구성한다. 테스트용 도형 실험은 별도 Fixture로 격리한다.
- Game View를 목표 해상도 3종에서 캡처하고 D/G 참조와 비교하여 사용자 시각 승인. 움직임·입력 피드백에 필요한 애니메이션 상태/표현 규격도 확보한다(실제 행동 수용은 P3).
- **통과:** Scene을 열면 실제 제품 방향의 선장실·플레이어·일지 Frame이 보이고 배치·계층·가독성이 만족스러움. 이 단계는 기능 완료를 주장하지 않는다.

### P3. 첫 Production-Ready Slice — 이동·책상·일지·정지·기본 복원

**대표 활성 동작:** 선장실 이동 → 책상 상호작용 → 일지 열기·닫기 → 세계 입력/시간 복귀.

- `GameSession`, 시간·중첩 정지, Action 입력, Interaction, World/Character View, Journal Screen의 최소 실행 경로를 구현한다.
- 플레이어의 **연속적인 이동·방향 변화·정지/재개·벽/가구와의 실제 접촉**, 카메라 추적·캐릭터 표시·입력 피드백을 함께 완성한다. 움직임을 좌표 점프로 대체하거나 모든 Sprite에 일괄 Collider를 부여하지 않는다.
- 정상/변동 프레임과 충돌 반복 조건을 관찰하고, 첫 대표 장면의 물리 비용·프레임 시간·GC 기준선을 남긴다.
- `GameDesign.md`의 하루 600초, 한 번에 한 층 표시 구조·UI 정지 정책을 위반하지 않는다.
- D03 일지 UI의 기록·지도 조작·메모 관련 미래 기능은 실제 위치의 `FrameDisabled`로 둔다.
- 이번 도메인 상태에 대해서만 버전형 기본 SaveSnapshot·종료/재진입을 구현한다. 아직 없는 사건·계약 저장을 미리 가짜 데이터로 생성하지 않는다.
- **통과:** A02 관련 실제 중첩 정지, A03의 현재 층 표시 전제, A27의 정상 종료/이어하기 관련 **현재 구현 부분**을 정식 Game Play로 검증. 플레이어 조작/이동/벽 충돌/카메라/상호작용의 실조작 영상·사용자 수용을 포함한다. Game View 시각 수용, 아트 적용·구조 검사·사용자 조작·저장 재진입 통과. 아직 없는 A항목 전체를 통과라고 쓰지 않는다.

### P4. 함선 층·항구 구역과 동일 세계 상태

**대표 활성 동작:** 선내의 실제 층 이동, 항구/선착장 간 정해진 공간 전환.

- D02, D08~D12 공간 연결의 **목표 구조**를 보존한다. 시각 제작은 이번에 실제 방문하는 구역만 완성하되 등장하는 화면은 G02와 동일한 게임 품질.
- 함선 모델별 층·시설/타일/통행 데이터, 플레이어/선원의 공간 ID, 월드 뷰 전환·표시 밖 상태를 연동.
- 실제 구현하지 않는 상점·게시판·주점/조선소 서비스 위치는 Frame으로 배치하고 호출 시 무반응.
- **통과:** 층 왕복·항구 이동에서 도메인 상태 유지, **지역별 역할 기반 충돌·연속 이동과 필요한 명시적 전환 효과**/접근점/카메라·저장 복원 검증, A03 관련 항목 통과. 표시와 게임 상태의 생명주기가 분리됨.

### P5. 수동 항해·입출항과 첫 플레이 흐름

**대표 활성 동작:** 혼자 출항 → 방향타로 이동 → 항구 입항.

- 해상/선내 위치·항해 고유 ID/출입항 흐름, D01의 기본 HUD(실제 정보), 항해/입항 표시와 실제 해상 표현.
- 미구현 자동 조타·일지 계획은 Frame에 남긴다. 항해 계획선만으로 배가 이동하지 않는다.
- **통과:** A01의 현재 시작 조건, A04의 같은 항구 복귀 항해 1회, A05 관련 무반응 조건, 입항 ID 중복 방지·저장 복원·화면 전환, 시각 검증.

### P6. 선원·시설·업무의 동일 상태 모델

**대표 활성 동작:** 한 명의 선원이 자격에 맞는 한 시설 업무를 맡아 수행·중단·복귀.

- 선원/시설 정의와 인스턴스 ID, 예약·업무/생활·이동 표현, 다른 층의 지속 시뮬레이션, 식량·시설 내구도와 수리 경계.
- 지금 실제로 출현하는 캐릭터/시설은 완성된 표현과 필요한 상태 피드백을 갖춘다. 선원 간 근접·장애물 회피·경로 수정·작업점 도착의 **동작 연속성**과 유닛 증가에 따른 물리·AI 비용을 검증한다. 나머지 선원 유형/시설은 구조 연결점·비활성 Frame만.
- **통과:** A07·A08·A15~A17의 **구현된 대표 조건**에 대한 실제 업무/출항 검사, 중복 선점/타층 진행/저장 중복·회귀; 전체 시설 콘텐츠 완료와 구분.

### P7. 무역·고용·계약 첫 통합 순환

**대표 활성 동작:** 상품 1종의 정상 구매·판매 + 선원 1명의 N회 계약→항해→만료/정산.

- D04/D05 및 거래 대행인·주점/게시판 구조를 실제 품질의 UI/월드로 제작. 다른 상품·후보/서비스는 필요 위치 Frame으로 둔다.
- 재고·골드·인물·계약·항해 ID는 각각의 소유 도메인에서 관리하고 거래/계약은 애플리케이션 트랜잭션으로 연결.
- **통과:** A09/A10/A13 및 관련 정산/재계약·보존/정지·반복 입항 저장 경계, 실제 클릭·월드 접근·UI 스크롤/해상도·시각 검증. 미구현 강제 매각 전체 규칙은 완료라고 표시하지 않는다.

### P8. 항해 일지·자동 조타·취침 첫 통합 순환

**대표 활성 동작:** 경로 기록/계획·자격 선원 조타·침대 취침을 일관된 시간/저장에 연결.

- D03의 이번 활성 기능을 실제 화면/지도 그래픽(G01)으로 구현하고 기존 Frame에서 기능을 활성화한다.
- 일지 기록·미기록 경로·이월·취침/불침번·항해사의 조타 명령과 저장 상태를 연결. 미정 이벤트 종류는 실제 구현 전까지 비활성.
- **통과:** A05/A06/A21~A24의 해당 조건, 무자격 자동 조타 거부·사건/입항 시각 경계(해당 구현 단계별 부분 판정)·저장/복원 및 시각 검증.

### P9. 사건·관전 전투·포로/결과의 안전한 확대

**대표 활성 동작:** 사건 1종의 발생→선택→결과 및 해당 시작 체크포인트 저장; 이후 대표 관전 전투/포로 흐름.

- `GameDesign.md`의 이벤트 시작 체크포인트·난수·종료 결과 적용 1회 규칙을 실제 복원으로 검증한다.
- D06 관전 전투 UI, 해당 캐릭터/무장·시각 피드백, 관련 전투/포로·계약 결과를 같은 상태 원본으로 연결한다.
- **통과:** A14/A18~A20/A26에서 실제 도입한 규칙의 플레이·저장/중복 적용/게임 오버 검증. 새 사건·전투 유형 추가 전에 대표 경로 통과.

### P10. 전체 확정 콘텐츠·서비스 확장

- `GameDesign.md` 5~12절의 남은 확정 규칙·시설·선원 유형·거래·명성/평판·퀘스트·미니게임을 **사용자가 승인한 우선순위**로 확장.
- 낚시·보드게임·치료 등 구현 중 구체화가 필요한 사항은 미정 기능으로 보존한다. 임의로 세부 규칙을 확정하지 않는다.
- 게시판·무기고·조선소·시청·포로 인계 등은 해당 활성화 단계에서 실제 화면·규칙·저장 수용을 수행한다.
- **통과:** 기능별 검증 완료와 별개로 A01~A28 전 항목의 미구현/부분/완료·검증 매핑이 추적 가능하고, 완성 항목은 실제 품질 기준을 통과.

### P11. PC 통합 수용·성능·밸런스

- 게임 전체 실제 조작·사운드·UI 접근·다중 해상도·장기 항해·실저장 복원·오류 복구를 검증한다.
- 초기 Slice부터 축적한 측정치와 실제 PC Player 빌드의 CPU/GC/메모리/로딩/Frame Time을 비교하고 통합 병목을 수정한다. 성능 목표·테스트 기기·복합 시나리오는 해당 단계에 사용자와 명시한다.
- 남은 미술/콘텐츠가 있다면 이 단계에서 '처음 제작'으로 미루지 않고 각 기능 개발 단계의 미통과 상태를 해결한다.
- **통과:** PC 전체 게임의 시각·기능·안정성/성능을 실제 근거로 수용. 컴파일 성공만으로 통과 금지.

### P12. 모바일 입력/기기 검증

- 기존에 Frame으로 보존해 둔 가상 조이스틱·상호작용 입력 및 지도/UI 터치 조작을 동일 게임 행동 계약에 연결한다.
- 모바일 해상도·입력/포커스·메모리·성능·저장/복원을 실제 대상 기기에서 검증한다.
- **통과:** PC와 같은 도메인 규칙·저장 결과를 유지하는 모바일 전체 플레이 경로.

## 4. 단계 카드 작성 방식

개별 구현 요청을 시작할 때 별도 일회성 MD를 추가하지 말고 대화의 **작업 계약**으로 다음 내용을 제시한다. 완료/미완료 결과는 `CurrentState.md`에 반영한다.

```text
단계 / 대표 기능:
GameDesign 근거(절, A번호) / 이미지(D,E,G):
이번에 실제로 활성화할 동작:
보여 주되 비활성으로 둘 Frame:
도메인 상태 소유자·명령/결과·생명주기:
변경할 Scene/Prefab/코드/실제 자산:
시각·움직임·조작감 수용 및 실제 Game Play 시나리오:
객체 역할별 충돌/공간 질의 정책(불필요한 물리 제외):
구현 대안·선택 근거(관련 영향이 큰 경우):
저장·복원/회귀/성능 영향과 측정 조건:
승인·미정·차단 항목:
G0~G5 결과: 아직 실행 전에는 모두 미확인
```

## 5. 범위 조정

단계는 의존성에 따라 더 작은 Slice로 쪼갤 수 있지만 **게임 규칙과 필수 UI/공간 구조를 삭제하거나 시각 완성을 뒤로 미루는 용도**로 사용하지 않는다. 사용자 지시로 순서를 조정하더라도 상태 원본/설계 정합성을 먼저 검증한다. 구현 범위를 좁히는 것은 기능 개수를 줄이는 것이지, 해당 기능의 품질·완료 조건을 낮추는 것이 아니다.
