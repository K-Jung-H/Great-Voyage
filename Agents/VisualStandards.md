# Visual Standards — 화면·움직임·피드백까지 실게임 수준

상태: **새 프로젝트의 필수 시각·동작 표현 수용 계약**. 유일한 기획 원본은 `GameDesign.md`이고, 기존 이미지 원본은 `References/D01~D12.png`, `E01~E11.png`, `G01~G03.png`다. 2026-11-02 사용자가 지정한 샘플·제작 시트·프롬프트 원본은 `References/ArtStyle_2026-11-02/`에 보존한다. 이 문서는 사용자 결정의 적용 기준을 기록하며 자체적으로 새 콘텐츠를 확정하지 않는다.

## 1. 시각 자료 우선순위

1. **게임 규칙과 필수 정보**: `GameDesign.md`의 확정 본문·후속 보완·A01~A28.
2. **화면/공간의 구획과 연결**: D01~D12. 상대 배치, 공간 진입, 정보 위치, 상호작용 지점을 보존한다.
3. **실제 게임의 화풍·시점**: 월드 Sprite 렌더링은 2026-11-03 지정 PainterlyHarborStyle·PainterlyMaritimeStyle을 우선한다(1.3절). 과거 샘플 및 G02/G03의 공간 가독성·유닛 구성·지정 시점은 유지하며 새 스타일 참조의 오브젝트·배치·시점을 복제하지 않는다. G01은 지도 표현 기준이다.
4. **분위기와 화면 조합 참고**: E01~E11. 도안과 확정 규칙을 바꾸는 지시가 아니다.

- G02: 위에서 내려다보는 2D 공간. 방·바닥·벽·문·통로·사물 외곽 및 통행 의미를 한눈에 식별할 수 있어야 한다.
- G03: Head / Body / Hand가 구분되는 단순한 SD 유닛. 예시의 다리 달린 RPG 캐릭터나 사선 투시를 그대로 적용하지 않는다.
- G01: 종이 질감과 절제된 해안선·육지·수면 색으로 가상 지도를 구성한다. 실제 도시·대륙을 게임 콘텐츠로 채택하지 않는다.
- 인물 초상: `GameDesign.md` 3.2절의 방향을 따른다. 월드 SD 유닛과 대화/고용 일러스트는 **서로 다른 자산 계층**이며 동일 인물의 특징은 대응시킨다.
- E에만 존재하는 추가 기능·숫자·도시·버튼·스킬·마법·장식 상호작용은 구현 요구가 아니다.

- 핵심 시각 언어: 단순하고 읽기 쉬운 기능적 실루엣과 **재질별 표면 디테일·회화적 음영·미세한 색 변화**를 함께 유지한다. 소품·환경은 얇고 일정한 단일 윤곽선을 사용하고 재질 내부의 회화적 변화는 유지한다. Human 관련 파츠는 이번 화풍 동기화의 논의·변경 대상이 아니다. 캐릭터는 Head / Body / Hand 구성과 다리 없는 기존 방향을 유지한다. 픽셀 격자나 픽셀 아트 제작 방식을 새로 강제하지 않는다.
- 제작 시트의 목재·석재·천·식생·해양 색감과 재질 표현도 사용자 수용 범위다. 프롬프트의 질감·그라데이션 금지를 절대 규칙으로 승격하여 사용자가 만족한 시트를 배제하지 않는다. 기준이 충돌할 때 실제 사용자 지정 이미지와 최신 지시를 우선하고 같은 장면의 선 굵기·시점·밀도는 통일한다.
- 샘플의 현대 차량·교도소 장비나 시트의 무기·실제 국기는 신규 콘텐츠 요구가 아니다. 지중해 건축도 전체 세계를 그리스풍으로 고정하는 결정이 아니다. 초상·지도·UI는 각자의 기존 기준을 유지한다.
- 첨부 문서의 2048×2048, 200% 확대, 정사각 시트는 제작 참고 목표다. 전 자산의 필수 크기·월드 타일 규격·PPU·필터 설정으로 확정하지 않는다. 출력 가능한 해상도와 개별 자산의 실제 화면 크기·선명도를 함께 검증한다.

### 1.2 원본의 기술 확인과 제품 사용 조건

- 원본 14개(이미지 11개, MD 3개)를 그대로 복사하고 SHA-256 일치를 확인했다. `Assets/` 밖의 참고 자료이며 Unity에 임포트된 제품 자산이 아니다.
- 파일 검사: 샘플1은 860×899, 샘플2는 860×1105이며 두 파일은 모든 픽셀이 불투명하다. 보이는 체크무늬는 실제 투명 영역이 아니므로 샘플 자체를 잘라 제품 Sprite로 사용하는 근거가 되지 않는다.
- 항구 시트 -2/-3/-4는 1536×1024, 항구 시트 -1과 기본 결과물1~5는 1254×1254다. 이 9장에는 완전 투명 픽셀과 넓은 반투명 영역이 실제로 존재한다. 알파 채널 존재만으로 배경 제거·외곽선 품질 합격을 선언하지 않는다. 밝은/어두운 바탕 합성에서 잔여 배경색·테두리·불필요한 반투명을 확인해야 한다.
- 시트 내 사물 크기·시점과 사물 사이 간격이 일정한 격자라는 보장이 없다. 일괄 Grid Slice를 적용하지 않고 채택 대상별 경계·실제 크기·시각 기준점·점유 영역·접근점을 정의한다. 선체·시설·밧줄·화물의 배치/분리 관계도 실제 사용 목적에 맞게 확인한다.
- 바닥은 3×3 반복, 벽·부두·해안은 모서리·분기·인접 조합을 확인해야 한다. 시트에 타일 모양이 있다는 이유로 Seamless/Autotile 합격으로 처리하지 않는다. 현재 연결성·애니메이션 적합성·Unity 합성은 미확인이다.
- 첫 P2 제작 범위는 D02/D03의 선장실 바닥·벽·문·책상과 필요한 가구, 플레이어 구성 파츠, 일지/가죽 Day 텍스트 탭 Frame이다. 우선 소수 자산으로 크기·선 굵기·시점·합성 기준을 검증하고 같은 기준으로 확장한다. 대량 시트 전체 제작이나 사건·전투 아트 구현을 선행하지 않는다.
- P2는 내장 imagegen으로 필요한 아트를 제작하고 Unity에 별도로 임포트했다. 추가 스킬 설치·엔진/패키지 교체는 없다. 실제 제작 규격·경로는 ProjectStructure 2.3절, 제작 프롬프트는 `References/P2/ArtSources.json`, 실제 Game 카메라 검토본은 `References/P2/`에 있다. 해당 검토본의 사용자 시각 수용은 아직 미확인이다.

### 1.3 활성 Factory 아트스타일 계약 (2026-11-03)

- **B안 스타일 사용자 수용·고정**: 원본 샘플1·샘플2로만 생성한 StyleB_OriginalSamplesOnly_01.png가 합격 판정을 받았다. 추가 사물의 일관성은 개별 검토한다. 후속 사용자 수용으로 B안/Human/Repeat 바닥을 조립한 첫 Scene은 P2 Complete이며, 게임 전체 미래 자산에 대한 포괄 수용으로 확대하지 않는다.
- 형태·비율·시점·윤곽선·색상 체계·명암 구조·디테일 밀도 전체를 원본 샘플에 맞춘다. 직선/단순 곡선, 얇고 일정한 단일 짙은 회색/검은 선, 외곽/내부 구조선의 유사한 두께, 화면 축 정렬, 최소 측면 두께를 유지한다. 저해상도 2D 래스터·약한 안티앨리어싱을 따르며 강한 계단식 픽셀 표현과 날카로운 벡터 표현은 피한다.
- 안정된 기본 색면·절제된 채도와 대비·무방향 확산광을 사용한다. 접합부/단차 외의 깊은 그림자를 억제한다. 내부 표면의 부드러운 나뭇결·미세 색차, 절제된 금속 반사, 천 섬유/주름만 보강하며 형태·선 두께·입체감을 증가시키지 않는다. 회화적 붓질·사실적 질감·장식 구조가 화풍을 지배하지 않게 한다.
- **필수 참조 규정**: 모든 과거 생성 결과물을 생성 입력·EDIT_TARGET·긍정/부정 참조로 금지한다. 사용자 제공 원본 레퍼런스·샘플만 허용한다. 합격 결과는 평가 대조용이며 생성 입력이 아니다. 이번 고정 레시피는 원본 샘플1·샘플2 두 장만 전달한다.
- 고정 원문은 ArtFactory/StyleB.locked.prompt.txt, 설정은 FactoryStyle.json·PromptTemplates.json, 조립 템플릿은 IMAGE_PROMPT.template.txt다. 승인된 생성의 스타일 문구를 그대로 보존하고 이번 배치는 사물 목록만 변경한다. 별도 Factory 실행 엔진은 없다. 과거 생성 프롬프트는 생성 당시 기록으로 보존하며 활성 규칙으로 사용하지 않는다.
- 투명 배경·여백·분리·이름/ID·시점 정렬·접합·단위 배율 파티션 규칙은 보존한다. 검토 셀 크기를 월드 크기로 확정하지 않는다. 알파·Sprite 경계·반복/모듈 접합·실제 Unity 표시 검증은 제품 적용 시 별도 수행한다. Human 파츠와 수용된 UI는 제외한다.

### 1.4 Human 파츠 스타일·생성 프롬프트 확정 (2026-11-03)

- 사용자가 Captain_Parts_FinalCandidate01.png의 결과물을 합격으로 판정했다. HumanParts.locked.prompt.txt에 실제 사용한 프롬프트를 원문 그대로 고정하며 HumanStyle.json에서 규격·수용 범위·한계를 관리한다. 소품 B안과 독립된 미니멀 Pawn 화풍: 원형 머리·돔 몸통·매끈한 짙은 윤곽선·불투명 단색 채움·점 눈·안티앨리어싱을 유지한다.
- 3×3 파츠 순서: 정면/후면/약한 사선 머리, 정면/후면/약한 사선 몸통, 눈 감은 정면 머리/왼손/오른손. 손은 독립된 단순한 손바닥 파츠이며 팔·다리·발은 생성하지 않는다. 원래 외부 참고 문서의 손 금지는 사용자 후속 지시로 이 범위에서 대체됐다.
- 머리카락·모자·복장 방향별 일관성을 유지한다. 실제 출력 1254×1254/418px 셀을 수용한 것이며 요청한 1536×1536과 혼동하지 않는다. 정확한 SVG 경로 재사용·눈 외 픽셀 불변은 검증되지 않았다. 생성 결과에 대한 평가는 이 한계와 구분한다.
- 손 크기는 현재 결과 그대로 유지한다. 프롬프트 수치 의도보다 크게 출력됐지만 사용자가 허용했으므로 자동 축소하지 않는다. 실제 게임 테스트 결과를 본 뒤 사용자가 최종 크기를 판단한다. Unity 적용·조립/피벗·실제 조작 수용은 아직 미완료다.
- 참조 입력은 원본 사용자 샘플1만 사용한 현행 방식이다. 수용된 결과 포함 모든 생성물의 재참조 금지를 유지한다. 추가 스킬·모델·후처리를 임의로 도입하지 않는다.

## 2. 핵심 정의: 완성된 작은 단위

**실게임 품질의 작은 단위(Production-Ready Slice)**는 화면 하나 또는 연결된 작은 공간에서 다음을 동시에 만족하는 결과물이다.

- 최종 목표 화풍과 같은 방향의 **실제 사용 가능한 Sprite/UI 자산**을 배치한다. 도형 원시 프리미티브만으로 제품 화면을 대체하지 않는다.
- 도안의 화면/공간 구도와 실제 상호작용 위치가 올바르다.
- 플레이어가 조작할 이번 대표 기능은 실제 입력→도메인 상태 변경→**연속적인 움직임·애니메이션/카메라·명확한 피드백**→저장/복원을 통과한다.
- 추가 기능은 예정된 위치에 Frame을 두되 명시적으로 비활성화한다. 활성 버튼에 가짜 성공을 연결하지 않는다.
- 제품 Scene/Prefab의 구조를 에디터에서 편집하고 자산을 대체할 수 있다. 전체 화면을 런타임 임시 객체로 구성하지 않는다.

**임시 도형은** 별도 실험/테스트 Fixture에서 짧게 사용할 수 있으나 제품 Scene의 '완료된 기능'을 대신할 수 없다. 최종 자산이 아직 없으면 그 기능의 시각 게이트는 `미통과` 또는 `미확인`이다. '나중에 교체할 예정'은 합격 사유가 아니다.

| 시설 | 외형·점유·접근 위치가 일치하고 기능/내구도 상태 표현 가능 | Collider/시각 면적을 서로 혼동하지 않음 |
| 항구 | D08~D12의 통로·포털·가게/서비스 위치를 유지 | 예시 E의 추가 길을 새 이동 규칙으로 추가하지 않음 |
| 지도 | 가상 항구·경로·현재 위치·이벤트 기록의 읽기 쉬운 레이어 | 실제 지구 지도나 임의 자동 항해 버튼 도입 금지 |

- 렌더링하지 않는 층의 상태는 보존한다. 표현이 비활성인 것과 시뮬레이션이 멈추는 것은 별개다.
- 타일 크기·PPU·정렬 레이어·피벗·앵커·애니메이션 프레임은 최초 자산 묶음 전에 정하고 `ProjectStructure.md`에 실제 값으로 기록한다. 미정값을 임의로 확정된 게임 규칙으로 승격하지 않는다.
- Sprite의 시각 중심과 Collider/접근점은 각 객체의 역할에 맞게 분리하며, 변형 크기/앵커가 다른 해상도에서 왜곡되지 않도록 검수한다.

## 4. UI 계약

- 필수 화면 구획은 `GameDesign.md` 4절 및 D01/D03~D07에 대응한다: HUD, 일지, 거래, 대행인, 고용, 조선소, 전투. 게시판·무기고는 기획 본문에 따라 같은 시각 체계를 적용한다.
- UI의 Canvas/패널/버튼/스크롤/입력/텍스트/비활성 Frame은 Scene/Prefab 자산으로 관리한다. 반복 행만 미리 만든 Item Prefab에서 생성한다.
- 화면 Controller는 게임 규칙을 복제하지 않고 화면에 필요한 상태·명령을 매핑한다.
- 화면의 시각 언어는 패널·테두리·배경/텍스트 대비·선택·초점·비활성 상태·마우스 피드백을 통일한다. 의미 없는 장식 때문에 정보와 조작성이 손상되면 실패다.
- 기본 화면은 가로형. **최초 수용 해상도 세트**는 개발 편의를 위한 제안으로 1280×720 / 1600×900 / 1920×1080을 사용한다. 최종 지원 해상도를 확정했다는 의미는 아니다. 실제 카메라/Canvas에서 각 화면의 클리핑·겹침·스크롤·앵커를 확인한다.
- 한국어 문자열과 폰트는 실제 TextMeshPro 화면에서 글리프 누락·줄바꿈·말줄임·동적 목록 너비를 검증한다.

## 5. Frame 정책 — '보이지만 아직 동작하지 않음'

Frame은 **장래 기능의 실제 위치와 크기를 보존하는 제품 구성 요소**다. '기능을 흉내 내는 프로토타입'이 아니다.

| 상태 | 화면에서 보이는 것 | 입력 | 완료 판정 |
|---|---|---|---|
| `Active` | 목표 스타일의 실제 UI/월드 표현 | 정식 도메인 명령 실행 | 해당 기능 검증 대상 |
| `FrameDisabled` | 실사용 위치의 화면 요소·상호작용 지점 | 클릭/키 입력 시 **행동·데이터 변화 없음**, 가짜 전환 없음 | Frame 배치만 수용. 기능 미구현 |
| `HiddenUntilStage` | 해당 단계에서 아직 등장하지 않는 화면 | 진입 경로 없음 | 제품 기능으로 계산 금지 |
| `DebugOnly` | 테스트 환경에서만 보이는 진단 | 제품 빌드 비포함 | 제품 화면 검증 대상 아님 |

- 비활성 Frame의 표시 방식은 기능별 도안에 맞춘다. 사용자 요청대로 입력 시 무반응을 기본으로 하며, 임의의 '준비 중' 대화창·가짜 데이터는 만들지 않는다.
- 보이는 영역이라도 아직 기능이 없다면 디버그 값이나 임의 숫자로 채워 완성도를 가장하지 않는다. 값 표시는 정의된 중립/비어 있음 상태를 따른다.
- Frame의 책임·소유화면·활성화 조건·필요한 미래 계약만 문서화하고, 지금 필요 없는 도메인 로직이나 저장 필드를 미리 생성하지 않는다.

## 6. 정지 이미지에 없는 품질 — 움직임·상호작용·게임 감각

샘플 이미지의 배치만 모방하거나 움직이는 도형을 놓는 것으로는 제품 품질에 도달하지 않는다. **실제 플레이 화면에서 시간에 따른 표현**을 평가한다. 물리적 책임은 `Architecture.md` 9절, 실행 검증은 `DevelopmentRules.md`를 따른다.

| 평가 대상 | 실제 게임에서 요구하는 모습 | 실패 사례 |
|---|---|---|
| 플레이어/선원 이동 | 입력 또는 AI 목표에 맞춰 시각적으로 연속 이동하고 방향·속도 변화가 납득 가능 | 프레임별 좌표 점프, 불필요한 덜컥임·떨림·발 묶임 |
| 접촉·회피 | 벽·시설·다른 유닛과의 접촉 반응이 게임 세계의 역할·통행 규칙과 일치 | 모든 Sprite에 물리 반응 추가, 장식에 막힘, 유닛끼리 과도하게 밀림 |
| 애니메이션 | 이동/정지/상호작용/업무가 알아볼 수 있는 상태로 연결 | 좌표만 변하고 캐릭터가 부자연스럽게 정지·전환 |
| 카메라·화면 전환 | 대상 추적·시야·화면 변화가 동작 인지를 방해하지 않음 | 화면 떨림, 급격한 불필요한 점프, 포커스/모달 전환 오류 |
| 조작 피드백 | 유효 입력·선택·불가능 조건·행동 중단을 모호하지 않게 전달 | 아무 표시 없이 결과가 늦게 바뀜, 가짜 성공, 반응과 실제 상태 불일치 |
| 프레임 안정성 | 움직임·UI 변화·동적 객체 수가 증가해도 대표 장면의 체감 끊김이 없는지 확인 | 기본 장면만 부드럽고 선원/표시가 늘면 눈에 띄게 끊김 |

- 실제로 규칙에 존재하는 포털·층 이동 등 **명시적 순간 전환**은 불연속 이동의 예외가 될 수 있다. 이를 일반 이동의 단순화 근거로 쓰지 않는다.
- 한 번의 정지 스크린샷은 화풍·배치만 증명한다. 이동·충돌·카메라·조작 피드백은 **연속 실행 영상 또는 실제 게임 조작 관찰**로 별도 확인한다.
- 회전, 이동 가속, 보간, 카메라 감쇠, 애니메이션 프레임 등 정확한 방법과 값은 아트/입력/게임 성격에 맞춰 선정한다. 모든 캐릭터에 동일한 물리 파라미터를 기계적으로 적용하지 않는다.
- 사용자의 체감 판단이 필요한 항목은 에이전트의 코드 검토로 합격 처리하지 않는다. 수용 이전은 `미확인`으로 명시한다.

## 7. 시각·동작 승인 순서

1. **원본 매핑**: 이번 Slice와 관련된 D/E/G 파일을 실제로 열고 맞는 항목을 적는다. 파일이 없거나 열리지 않으면 미확인 상태로 멈춘다.
2. **실제 에셋 준비**: 배경/캐릭터/대상 시설/UI의 적용 가능한 자산과 제작 규격을 마련한다. 수급·제작 경로는 사용자 승인 범위 안에서 결정한다.
3. **Unity Editor 배치**: 게임 화면에서 Sprite 정렬, 카메라, UI 계층, 입력 영역을 배치한다.
4. **Game View·연속 동작 확인**: 목표 해상도별 스크린샷과 실제 입력/AI 동작을 보여 주는 연속 영상 또는 동등한 실조작 기록을 제공한다. 편집기 Hierarchy 캡처만으로 대체할 수 없다.
5. **대조표 검사**: 도안 배치 / G 화풍·시점 / 정보 가독성 / Frame 비활성 / 해상도 변화 / 움직임·접촉/애니메이션·카메라/조작 피드백을 각 `통과·미통과·미확인`으로 표시한다.
6. **사용자 수용**: 외형적 판단이 필요한 항목은 사용자에게 실제 화면을 보여 주고 승인 여부를 확인한다. 이미지 생성물이나 코드 리뷰만으로 승인이라고 기록하지 않는다.

### 시각 게이트 통과 조건

- **필수**: 대상 D의 공간 연결·상대 구도 일치, 대상 G와 양립하는 실제 게임용 표현, 주 기능의 **연속성·자연스러운 반응·피드백**, 비활성 Frame의 무반응 확인, 검사 해상도에서 정보/조작 영역 정상.
- **미통과 예**: 도형으로 대략 비슷하게 배치, 미승인 예시 기능 추가, 클릭 시 빈 화면만 열림, 끊기는 일반 이동, 역할에 맞지 않는 물리 접촉, 실제 화면/연속 동작 증거 부재, 필요 Sprite 없음.
- 작업 보고에는 사용한 이미지 ID, Unity 자산 경로, Game View 캡처·동작 확인 자료의 위치, 통과/미확인 근거를 반드시 남긴다.
