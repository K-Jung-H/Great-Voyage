# Development Rules — 설계·제작·검증·Git 운용

> 목적: 코딩 가이드가 아니라 **제품 수준의 작은 기능만 프로젝트에 누적하도록 강제하는 작업 계약**이다. 기능 개수와 콘텐츠 범위는 최소화할 수 있지만, 활성 기능의 설계·움직임·상호작용·피드백·안정성·성능은 생략할 수 없다.

## 1. 기본 진행 절차

모든 구현 요청은 아래 게이트를 순서대로 지난다. 아직 없는 문서·아트·실행 환경을 '존재함'으로 가정하지 않는다.

| 게이트 | 수행 사항 | 합격의 최소 근거 |
|---|---|---|
| G0 요구/범위 | 기획 절·A번호·D/E/G 자료·대표 기능·비활성 Frame 목록·체감 품질 목표 확인 | 기획/구현/제외 범위와 요구되는 사용자 경험을 연결하는 작업 계약 |
| G1 설계 | 객체·소유 상태·의존 방향·수명·저장, 이동/충돌/표현 정책, 구현 대안과 품질 비용 검토 | `Architecture.md`와 모순 없는 호출/상태 흐름·선택 근거 |
| G2 자산/화면 | 실제 게임용 자산과 Editor Scene/Prefab/UI Frame 및 동작 표현 기준 준비 | 이미지 대비 Game View와 필요한 애니메이션/조작 피드백 계획 |
| G3 구현 | 승인된 객체 경계에서 대표 기능과 역할에 맞는 물리·이동·피드백 구현 | 명령→도메인 결과→연속 동작/표현·실패 처리, 기능 시늉으로 대체하지 않음 |
| G4 통합/검증 | 정적 구조·컴파일·자동 테스트·실제 플레이(입력/이동/접촉/피드백)·저장/복원·규모별 성능 확인 | 실행 환경/영상·캡처/측정치와 미확인 구분. 단순 컴파일로 완료 금지 |
| G5 수용/인계 | 게임의 품질·조작감·시각 결과 사용자 수용 및 상태 기록 | `CurrentState.md`에 검증 증거·판정·남은 결함 명시 |

- 사용자 승인이 필요한 변경이라면 G1/G2에서 사용자에게 판단 자료를 제시한다. 이미 승인한 범위 안의 통상적인 소스 수정마다 같은 승인을 반복 요구하지 않는다.
- 승인된 테스트 범위의 **격리된 테스트 슬롯**에서 컴파일, EditMode/PlayMode, 화면 캡처를 수행할 수 있다. 사용자 실제 저장·외부 서비스·파일 초기화에 영향이 있으면 별도 승인받는다.
- Unity를 실행할 수 없는 환경이면 정적 결과만 기록하고 G4/G5 통과를 선언하지 않는다. 사용자가 직접 실행한 검증은 실행 방법과 결과를 받아 별도 표시한다.
- 한 게이트가 미통과면 범위 확대를 중지한다. 보고 및 수정은 가능하지만 다음 시스템의 '완성'으로 대체하지 않는다.

## 2. 프로젝트 횡단 품질 계약 — 모든 활성 기능에 적용

**구현 범위의 축소와 구현 수준의 축소를 혼동하지 않는다.** '선원이 움직인다', '책상을 클릭할 수 있다', 'UI가 열린다' 같은 동작의 존재만으로 상용 게임을 목표로 한 Slice가 완성되지 않는다. 구현자는 동작을 실제 게임에 사용할 수 있는 수준으로 설계·제작·평가해야 하며, 요구사항에 구체적인 알고리즘이 없다는 이유로 가장 단순한 시늉을 채택해서는 안 된다.

| 품질 속성 | 모든 Slice에서 검토할 질문 | 통과 근거의 예 |
|---|---|---|
| 구조 일관성 | 게임 세계의 상태 원본·객체 책임·상호작용·생명주기가 보존되는가? | 설계 계약, 의존성 검사, 사용 사례 테스트 |
| 플레이 감각 | 실제 입력에 반응하고 행동의 시작·진행·종료·취소가 자연스럽고 이해 가능한가? | 실조작 관찰, 동작 영상, 사용자 수용 |
| 이동 연속성 | 프레임 변화·목표 변경·충돌·정지·재개에서 불연속 점프와 떨림이 없는가? | 실제 플레이 이동 시퀀스, 반복 조건 비교 |
| 물리·공간 의미 | 각 엔티티에 정말 필요한 접촉·차단·감지·회피만 존재하는가? | 역할별 충돌 표, 레이어/질의 설정, 실제 접촉 테스트 |
| 시각·청각 피드백 | 월드·캐릭터·UI 상태가 플레이어에게 일관되고 읽기 쉽게 전달되는가? | 목표 레퍼런스 대조, 애니메이션/카메라/사운드/UX 검토 |
| 효율·확장 규모 | 정상/혼잡 상황에서 불필요한 연산·할당·물리 비용이 누적되지 않는가? | Profiler와 프레임 시간·CPU·GC·메모리 기록 |
| 안정성·회귀 | 중첩/중단/재진입/저장·복원 후에도 동일한 규칙과 품질이 유지되는가? | 자동 테스트+정식 Game Play 반복 검증 |

- **방법 선택은 에이전트 책임**이다. 업무에 적합한 작은 설계를 택하되 최소 코드량이나 작업 종료 속도를 목표로 삼지 않는다. 큰 영향이 있는 선택은 적어도 채택안/대안/장단점을 보고한다.
- 특정 기능마다 긴 금지 목록을 늘리지 않는다. 위 품질 속성을 **기능에 맞게 해석**하고, 영향을 받는 항목은 확인 방법을 명시한다. 영향이 없는 항목만 근거와 함께 `해당 없음`으로 분류한다.
- 예상 품질을 적은 다음 구현하고, **실제로 플레이해 관찰한 결과가 기대와 다르면 같은 작업에서 개선**한다. 문서상 기능 조건이나 테스트 횟수 충족만으로 마감하지 않는다.
- '상용 게임 수준'은 현재 Slice의 질적 목표이지 완성된 전체 게임·대량 콘텐츠·고가 기술 스택을 요구한다는 뜻이 아니다. 사용자의 시각·조작감 판단은 실제 화면/동작을 제시하여 수용받는다.
- 측정 장비·목표 하드웨어·수치 기준이 아직 없으면 임의의 FPS 합격 숫자를 만들어내지 않는다. 대신 측정 방법, 시험 조건, 관찰 결과, `미확인` 범위를 명확히 기록한다.

### 물리·이동·성능의 기본 판단 절차

1. 객체 유형을 **정적 장애물 / 동적 캐릭터 / 감지·상호작용 / 시각 전용** 등 실제 게임 역할로 구분한다. Collider·Rigidbody·Trigger·Physics Layer·공간 질의는 그 역할과 필요한 접촉에 근거해 선택한다. 무조건 전 엔티티에 물리 계산을 추가하지 않는다.
2. 이동은 목표·경로/조향·시간/물리 스텝·표현/애니메이션·상태 저장을 분리한다. 게임 규칙에 없는 순간 좌표 이동, 보이는 점프, 정지 직후 떨림 등은 **구현 결함**으로 취급한다. 보간·감속·회피 등의 구체 해법은 실제 게임에서 평가해 선택한다.
3. 대표 조건(정면 벽, 모서리, 좁은 통로, 근접한 선원, 목표 변경, 다른 층, 정지/복귀, 저장/로드, 변동 프레임)을 직접 재현한다. 동작이 자연스러운지 **영상/실조작**으로 검사한다.
4. Update/FixedUpdate 비용, 공간 질의 빈도, 재할당·컴포넌트 탐색·GC, 유닛 수 증가에 따른 비용을 검토한다. 필요한 경우 Profiler 측정 후 캐시·dirty 갱신·공간 분할·적정 업데이트 빈도 등 **최소 적합한 수단**을 선택한다. 사전 근거 없는 풀링/커스텀 엔진/대규모 최적화는 금지한다.
5. 기능 조건은 충족하지만 움직임·물리·피드백·성능이 불량하면 `부분 구현/품질 미통과`로 표시하고 개선을 우선한다. 사용자 미수용 또는 Unity 미실행은 `미확인`으로 표기한다.

## 3. 설계·객체지향 품질

- **책임 우선:** 타입을 늘리기 전에 실제 상태 소유자, 변경 책임, 인접 객체와의 계약을 정의한다. 기능 하나당 Manager/Interface를 자동 생성하지 않는다.
- **명령·결과 우선:** UI·입력·Unity 콜백이 게임 규칙을 직접 수정하지 않는다. 애플리케이션 사용 사례가 유효성 검사 및 도메인 결과를 수집한다.
- **의존 방향 강제:** Domain은 구체 UI, Unity Scene/MonoBehaviour, 플랫폼 IO를 참조하지 않는다. Infrastructure/Presentation에서 도메인 규칙을 복제하지 않는다.
- **단일 진실 원본:** 같은 금화·인물·선원 상태·시설 내구도·항해 횟수에 별도 원본을 만들지 않는다. View Model/캐시는 원본에서 재생성 가능해야 한다.
- **생명주기:** 씬 언로드·오브젝트 비활성·UI 닫기와 인물/계약/항해 종료를 혼동하지 않는다. 구독·정지 핸들은 자신을 만든 주체가 해제한다.
- **도메인 협력:** 다른 시스템의 내부 리스트에 접근하거나 `FindObjectOfType`으로 규칙 객체를 찾아 직접 수정해 결과를 완성하지 않는다. 장면의 런타임 검색은 좁은 표현/도구 용도로만, 매 프레임 탐색은 원칙적으로 금지한다.
- **이벤트 절제:** 복수 수신자가 동일 거래·계약·보상을 중복 확정하는 구조를 금지한다. 이벤트는 이미 완료한 결과를 알리고, 상태 변경의 권위자는 한 곳에 둔다.
- **미래 확장:** 새로운 상품/시설/선원 유형은 정의 데이터와 해당 책임의 작은 확장으로 도입할 수 있어야 한다. 전체 게임 조립자/화면 관리자를 바꾸는 것이 상시 필수라면 구조를 검토한다.

### 코드 작성 표준

- C# 명명은 `ProjectStructure.md`의 실제 채택값을 따른다. 변수·메서드 이름은 역할과 단위를 명확히 드러낸다.
- public setter로 깊은 상태를 노출하지 않는다. 도메인 규칙을 보호하는 행위 메서드와 읽기 전용 조회를 우선한다.
- 설정/밸런스와 저장 가능한 상태를 분리한다. ScriptableObject는 불변 정의 데이터 취급.
- `[SerializeField] private` 필드로 필요한 Unity 참조를 명시하고 Editor에서 설정한다. 런타임 계층 전체를 코드로 만드는 방식을 기본으로 하지 않는다.
- UI 기본 패널/레이아웃을 `new GameObject`로 생성하지 않는다. 반복되는 리스트 항목만 사전 제작한 Prefab을 생성·재사용한다.
- 테스트가 어려운 거대 클래스는 길이 숫자만으로 분리하지 말고 **업무/상태/조작 책임의 다른 변경 사유**를 기준으로 나눈다.
- 인라인 설명 주석은 지양한다. 함수 설명이 필요한 경우 `// Role: ...`, 매개변수 설명이 필요한 경우 `// Parameter: ...`만 사용한다. XML 문서·자동 생성 코드처럼 도구가 요구하는 형식은 별도 처리한다.
- null·저장 불일치·잘못된 정의 ID·중복 명령에 대해 조용히 가짜 성공을 반환하지 않는다. 실패 계약을 명시하고 복원/오류 표시를 분리한다.

## 4. 시각 품질과 Frame 개발 규칙

- **먼저 목표 화면과 제품 자산을 확정하고 기능을 연결**한다. 기본 도형만 보이는 결과물을 기능 완료로 취급하지 않는다.
- 한 Slice에서 플레이어에게 보이는 월드/캐릭터/UI는 `VisualStandards.md`를 준수한다. 임시 색상 Rect는 Editor 테스트에는 허용되지만 제품 수용 대상에서는 미통과다.
- 전체 게임의 기능을 한 번에 제작하지 않는다. 현재 등장하는 주요 화면/상호작용 위치를 실제 구조로 배치하고, 구현하지 않을 컨트롤은 `FrameDisabled`로 설정한다.
- 비활성 Frame은 입력에 반응하지 않으며 게임 상태를 변경하지 않는다. 가짜 상점·가짜 보상·진행되지 않는 가짜 장면으로 대체하지 않는다.
- 외형 변경이 포함된 기능의 완료에는 실제 Unity Game View 캡처 및 사용자 수용이 필요하다. 정적 프리팹 검수만으로 시각 완료라고 주장하지 않는다.

## 5. 테스트 전략과 완료 정의

### 검증은 반드시 구분해서 기록한다

| 유형 | 필수 확인 내용 | 금지된 과장 |
|---|---|---|
| 정적 구조 | 책임/참조/Hierarchy/도메인 상태·UI Frame·Scene 소유권 | 타입이 나뉘었다는 이유만으로 객체지향 구조 통과 |
| 컴파일/빌드 | 스크립트·패키지/에셋 임포트 오류 여부, 빌드 대상 | 컴파일 0오류를 기능 완료로 간주 |
| Domain/EditMode | 상태 전이, 조건·예외·결과 1회 적용, 안정 ID | 단독 단위 테스트 통과를 게임 통합 완료로 간주 |
| PlayMode/통합 | 정식 Game 진입, 실제 입력, 이동 연속성/충돌 역할/회피, UI 포커스, 씬/층 전환·반복 동작 | Controller 직접 호출이나 물체가 위치에 도달했다는 사실을 조작감 검증으로 표현 |
| 저장/재진입 | 정상 종료·일관된 복원, 원자 저장, 사건 체크포인트, 중복 결과 방지 | 합성 DTO 왕복을 실게임 전체 복원으로 확대 |
| 시각/UX | D/G 대조, 해상도, 실제 Sprite/UI, 이동·애니메이션·카메라/상호작용 피드백, Frame 무반응 | 정지 이미지 한 장으로 움직임·게임 감각까지 합격 선언 |
| 성능 | 초기 Slice부터 대표 부하 조건을 정하고 빌드/실행 환경별 Frame Time·CPU·GC·메모리·물리 비용 기록 | P11까지 측정을 미루거나 계측 없이 '최적화 완료' 선언 |

- 도메인 경계마다 정상/거부/중복 요청/저장 후 재실행 시나리오를 준비한다. 발견한 버그는 가능하면 재현 테스트로 고정한다.
- 제품 Scene의 대표 흐름을 끝까지 통과하지 못하면 다른 Scene에서 기능이 작동해도 통합 게이트 미통과다.
- 고정 FPS·메모리 등의 숫자는 대상 PC 성능 프로파일을 실제로 합의한 뒤 설정한다. 계측 전 근거 없는 성능 목표를 완료 기준으로 기입하지 않는다.
- 초기 Slice도 불필요한 매 프레임 전체 컴포넌트 탐색/Transform 재부모 설정/과잉 생성/할당을 피한다. 그렇다고 검증 없이 범용 풀링을 도입하지 않는다. 성능 문제가 있어도 수치가 없을 때는 관찰 사실과 추정을 구분하고 실제 병목부터 다룬다.
- **증거 표준:** 동작/조작감=실제 입력으로 실행한 짧은 연속 영상 또는 직접 관찰 기록, 시각=Game View 캡처, 구조=관련 자산/코드/의존성 확인, 성능=같은 조건의 Profiler 측정. 필요 항목을 실행하지 못했다면 `미확인`이다.

### 기능 완료(Definition of Done)

다음이 모두 `통과`여야 해당 Slice를 `완료`로 변경할 수 있다.

1. 유효한 `GameDesign.md` 규칙·도안·참조 경계와 일치한다.
2. `Architecture.md` 책임/의존/수명/단일 상태 원본을 위반하지 않는다.
3. 실제 게임 화면의 해당 범위는 시각 수용 기준을 통과하고, 동작 중 애니메이션·카메라·피드백도 자연스럽다.
4. 활성 동작은 정식 Game 진입에서 실제 조작으로 동작하며 이동 연속성·반응·역할별 충돌과 관련 규모 성능을 통과한다. 비활성 Frame은 정말 무반응이다.
5. 관련 도메인 테스트, 저장·복원, 이전 완성 기능 회귀에 필요한 검증을 통과한다.
6. 실제 실행 환경/버전/검증 증거 및 사용자 시각·조작감 수용 상태가 남고 `CurrentState.md`가 현행 상태를 반영한다.

시각·구조·기능·게임플레이 감각·물리 정책·관련 성능 중 어느 하나라도 미통과면 상태는 `부분 구현` 또는 `검증 대기`이지 완료가 아니다. 후속 작업을 허용하려면 완료되지 않은 항목과 독립적임을 명시해야 하며, 선행 기반 결함을 다른 기능으로 우회해서는 안 된다.

## 6. 사용자 승인·Git·다중 에이전트

- 사용자가 한정한 작업 범위의 통상적 파일 추가/수정·격리 테스트·검증 산출물 생성은 그 범위 안에서 수행할 수 있다. **게임 규칙 변경, 방향이 달라지는 시각/설계 결정, 핵심 구조 교체, 패키지·엔진 변경, 사용자 데이터 삭제**는 영향과 대안을 제시해 먼저 승인받는다.
- 명시 요청 없는 `git commit`, `push`, `merge`, `reset`, `rebase`, `clean`, 강제 checkout, stash/pop으로 사용자 작업 변경을 훼손하지 않는다. 읽기 전용 상태 조회는 허용한다.
- 여러 에이전트가 다른 도메인에서 작업할 때 **작업 브랜치/작업 디렉터리 및 소유 파일 범위**를 분명히 나눈다. 공통 계약·Scene·UI Root·공용 SO를 중복 수정하지 않는다. 충돌 시 먼저 설계 소유자를 결정한다.
- 작업을 서로 잇는 근거는 **현재 코드·Git Diff·승인된 Architecture·CurrentState**다. 과거 대화 문구나 '예전 에이전트가 구현했음'은 근거가 아니다.
- 별도 대화 기록·History/Queue/세션 이벤트 저장·작업별 임시 보고 MD를 자동 생성하지 않는다. 주요 변경의 추적은 Git에, 현재 수행 상태는 `CurrentState.md`에만 둔다.

## 7. 인수인계 작성 규칙

작업 완료/중단 시 `CurrentState.md`를 아래 구조로 교체·갱신한다.

- Git 기준(현재 브랜치/HEAD, 미커밋 여부), Unity 실행 가능/실제 에디터 버전.
- 승인된 작업 계약 및 이번에 실제 반영한 파일·자산.
- 대표 기능 상태(`미구현/구현 중/부분 구현/검증 대기/완료`), 비활성 Frame.
- G0~G5 항목별 `통과/미통과/미확인`, 적용한 횡단 품질 속성의 `통과/미통과/미확인/해당 없음` 및 객관적 증거 경로.
- 현재 실패·미정·재현 방법·저장 위험, 다음 한 가지 작업.

대화 전체 원문, 수행한 CLI 명령 나열, 오래된 시행착오를 누적하지 않는다. 다음 에이전트가 **현재 상태만으로 안전하게 시작**할 수 있는 정보만 보존한다.
