# Architecture — Great Voyage 단일 게임 모델 설계 계약

> 상태: **기본 프레임워크 범위 P1 설계 검토·사용자 수용 완료(2026-11-02)**. 구현·실플레이 검증 완료를 뜻하지 않는다. 기존 본문은 기본 설계안이며 자동 승인된 계약이 아니다. 아래 검토 단위별로 사용자 수용·정정을 해당 조항에 반영한다. P1 시작 승인은 개별 설계의 수용이나 구현 허가를 뜻하지 않는다. 특정 클래스명은 변경 가능하나 상태 원본·소유권·의존 방향·생명주기는 명시적으로 검토한다.
> 범위: `GameDesign.md`의 2D 함선 운영·무역·선내 생활 게임 전체를 수용하는 **구조**, 지금 구현하지 않을 기능의 **알고리즘**은 포함하지 않는다.

## 0. P1 검토 범위와 현재 제안

**최신 범위 결정(2026-11-01):** 현재 P1은 항구 거래·고용·정비 → 출항 → 선내 생활·업무·항해 → 입항·계약 정산을 반복하는 기본 프레임워크 설계다. 항해 중 사건·불침번·전투·미니게임은 기본 프레임워크 완성 및 테스트 통과 후 구체 설계·구현한다. 현재는 Event 진입·복귀와 공통 상태/입력/시간/저장 정책을 연결할 경계만 둔다. 기존 본문의 사건별 규칙은 GameDesign에 보관된 미래 요구이며 현재 설계 확정·구현 범위가 아니다. 사건 종류·발생 조건·보상·전투/미니게임 진행·체크포인트 상세를 지금 확정하지 않는다.

검토 순서는 아래와 같다. 각 단위는 기획 절·A번호, 상태 소유권, 명령/결과, 조건·예외·실패, 생명주기·저장, 품질 영향과 미결정을 함께 기록한다. 사용자 정정은 관련 표·흐름·인수 기준에 함께 반영한다. 미검토 내용을 축약 승인하거나 이름만 나열해 전체 설계 완료로 처리하지 않는다.

### P1-01 — 전체 구조와 단일 상태 원본

**근거:** GameDesign 2절의 단일 플레이 흐름, 4.2절의 비표시 층 지속, 7.5절의 인물 이동 상태, 8절의 계약, 12절의 경제, 13~14절의 일관된 저장과 ID. 2026-11-01 사용자 검토에서 시스템적 기본 방향을 수용하고 공통 자료구조 및 SaveEvent 방식을 정정했다. 수용 범위는 기본 방향과 명시된 정정이며, 후속 흐름·실패 처리까지 일괄 승인된 것은 아니다.

1. **플레이 수명:** GameSession은 새 게임/이어하기부터 종료까지 한 플레이와 도메인 루트 참조를 소유한다. 금화·계약·인물 상태의 별도 사본을 갖지 않는다. 지역 뷰 전환으로 세션을 재생성하지 않는다. GameClock이 게임 시간을, PauseReasons가 중첩 정지 토큰을 소유하며 Session의 시간 참조는 원본 복제가 아니다.
2. **세계와 함선:** WorldState는 항구·해역·지역의 정체성과 연결을, 함선 소유 목록은 함선 인스턴스와 소유·정박 관계를, 각 Ship은 해당 함선의 모델·층·타일·시설·내구도를 소유한다. 전체 보유 함선과 현재 승선 함선을 구별한다. 특정 함선이 있는 항구에서만 교체할 수 있다는 조건을 보존한다. 여러 장소에서 위치를 복제하지 않도록 실제 해상 위치·방향·속도는 해당 함선의 Navigation 상태 한 곳에 둔다. Voyage는 항해 ID·출발/도착·완료 여부를 맡고 함선 위치 사본을 소유하지 않는다. 비항해 함선의 위치는 정박 항구 관계로 표현하며 세부 전환은 P1-04/05에서 검토한다.
3. **인물과 관계:** CharacterRegistry는 인물 ID의 조회·등록을, Character는 현재 위치·생존·능력·욕구·행동에 필요한 인물 원본 상태를 소유한다. 고용·업무·전투·포로는 같은 characterId를 참조한다. Character의 행동 표시는 업무 진행도·계약 잔여 횟수의 별도 원본이 아니다. CrewWork는 업무 할당·진행·중단/복귀를, WorkReservation은 시설 작업점 선점을, CrewContract는 지급 조건·항해 잔여 횟수·채무를 각각 소유한다. Prisoners는 수감 관계·인계 처리를 소유하며 인물을 복제하지 않는다.
4. **재고와 경제:** Inventory와 Wallet이 소유자별 재고·골드 원본이다. Market은 항구별 가격·수요·상인 재고 소유자와의 연결을, Reputation은 전역 명성·현지 평판을 구분해 소유한다. 가격 화면·게시판·조선소는 해당 상태를 조회하고 명령만 전달한다. 상인 재고를 Market과 Inventory에 이중 보관하지 않는다. 상세 소유자별 재고·함선 교체 흐름은 P1-05에서 확정한다.
5. **일지·취침·사건:** Journal은 기록·미기록 경로·계획·이벤트 메모·이월 자격을, Rest는 취침/불침번 상태·중단 경계를 소유한다. 두 역할은 별개이며 기존 3절의 묶음 행이 단일 객체를 강제하지 않는다. EventProgress는 사건 ID·난수 조건·진행/결과 적용 상태를, Battle은 해당 전투 진행을 소유한다. 사건 체크포인트는 SaveCoordinator가 관리하는 저장 표현이며 별도의 두 번째 실시간 세계가 아니다. 사건 내 선택·난수·복원 상세는 P1-06에서 검토한다.
6. **협력·표현·저장:** Application의 사용 사례가 여러 소유자의 명령을 조정한다. 일지 열기·거래·입항·처분 각각에 결과 확정 경계를 두고 성공/거부/실패를 명시한다. 결과 확정과 파일 저장은 별도 경계다. SaveEvent 발생 시 저장 조정자에 요청하며 매 명령·매 프레임 저장하지 않는다. UI·Prefab·카메라는 상태를 표현하며 저장 IO를 수행하지 않는다. 저장 데이터는 SaveEvent의 일관된 상태를 기록한 결과이며 실시간 변경 주체가 아니다. 물리 위치 반영과 실패 복구 절차는 후속 단위에서 구체화한다.

**수명·저장:** 콘텐츠 종류의 definitionId와 실제 개체의 instanceId를 구별한다. 인물·시설·함선·항해·사건의 관계는 안정 ID로 연결하며 Unity InstanceID·Hierarchy 경로를 저장 정체성으로 사용하지 않는다. 뷰 파괴·UI 닫기가 인물·계약 삭제를 의미하지 않는다. 저장 복원은 기존 개체를 ID로 재연결하며 보상·항해 차감을 재실행하지 않는 계약을 후속 흐름에서 검증한다.

**선택 근거·대안:** 기능별 Manager가 상태 사본을 보관하는 방식보다, 관련 불변식을 보호하는 소유자와 명시적 협력 경계를 채택한다. Session은 수명 관리에 한정해 거대 전역 관리자가 되는 것을 방지한다. 이 논리 모델을 전부 클래스로 미리 생성하지 않으며 정의·명령·공통 계약도 실제 구현 범위에 맞춰 도입한다.

**품질·미결정:** 화면 밖 상태 보존·객체 증가 비용·연속 이동을 지킬 책임 경계는 여기서 다룬다. 경로 탐색·물리 세부 방식·갱신 빈도·정확한 성능 목표는 미확정이며 관련 단위에서 근거를 들어 결정한다. 이 제안은 화면·조작감·성능의 실행 통과를 주장하지 않는다. P1-01 수용은 후속 검토나 P1 전체 완료를 대신하지 않는다.

## 1. 설계 철학과 강제 불변식

1. 게임은 기능별 시뮬레이터들의 모음이 아니라 **하나의 세계 상태를 조작하는 일관된 모델**이다.
2. **도메인 객체**가 자신이 소유하는 상태와 불변식을 보호한다. 관련 없는 규칙을 하나의 God Manager/Service Locator가 소유하지 않는다.
3. 다른 객체의 상태를 직접 수정해 연쇄 동작을 성립시키지 않는다. 경계 간 행동은 명시적 **Command → 소유자/도메인 규칙 → Result/Event**로 진행한다.
4. Unity 오브젝트는 도메인의 권위자가 아니다. GameObject의 생성/비활성화/파괴가 선원·계약·항해의 존재/종료를 뜻하지 않는다.
5. 시뮬레이션은 화면 가시성과 독립한다. 렌더링하지 않는 층/항구의 지속 상태와 규칙은 동일하다.
6. 시스템 간 순환 의존과 UI→규칙 상태 직접 수정은 금지한다.
7. **엔티티에 물리 컴포넌트를 일괄 부여하지 않는다.** 위치·충돌·접근·감지는 서로 다른 의미다. 역할에 맞는 공간 질의와 물리 상호작용을 선택한다.
8. 움직이는 캐릭터의 위치와 보이는 이동은 게임 규칙상 이산 전환이 아닌 한 **시간에 따른 연속적인 동작**이어야 한다. 틱·물리·렌더 시점의 연결을 설계한다.
9. 설계는 기능의 유무뿐 아니라 실제 게임의 품질 속성(응답성·연속성·확장 규모·프레임 비용)을 만족해야 한다.
10. 정의 데이터와 실행 상태를 구별한다. ScriptableObject는 **정의/설정**이지 플레이어의 현재 저장 상태가 아니다.
11. 미래 기능의 이름·연결점은 준비할 수 있지만, 사용하지 않는 추상 클래스·종합 인터페이스·범용 이벤트 버스·저장 필드를 일괄 만들지 않는다.

## 2. 계층과 의존 방향

```text
Unity Entry/Bootstrap (Composition Root)
   ├─ Presentation: World / Character / UI / Camera / Audio
   ├─ Input Adapters: PC → Game Action
   ├─ Infrastructure: asset loading / serializer / file IO / Unity physics adapter
   └─ Application: GameSession / GameFlow / Command Handlers / Simulation Scheduler
             ↓               ↓
        Domain Model   ←  Domain Policies
             ↑
      Definitions / Runtime State
```

- 의존 방향: `Presentation/Input/Infrastructure → Application 계약 → Domain`. Domain은 Unity UI·GameObject·파일·타 시스템의 구체 MonoBehaviour를 몰라야 한다. 표현 코드가 도메인을 조회할 수는 있지만 변경은 명령으로만 한다.
- `Bootstrap`은 참조 연결·초기화 순서를 소유한다. **게임 규칙을 직접 수행하지 않으며**, 매 프레임 전체 UI를 억지로 갱신하는 중앙 관리자도 아니다.
- `GameSession`은 현재 플레이의 생명주기와 루트 상태를 소유한다. 모든 도메인의 임의 public setter를 노출하는 전역 상태 접근창으로 사용하지 않는다.
- `GameFlow`는 게임 모드/공간 전환·명령 라우팅/원자적 다중 도메인 흐름만 담당한다. 구체 UI Controller를 이름으로 직접 호출하지 않는다. 게임 상태 변화 통지→Presentation 반영 형태를 사용한다.
- `SimulationScheduler`는 시간 예산·정해진 규칙 실행 순서·정지 상태를 관리한다. 도메인 규칙 자체를 구현하지 않는다.
- `Infrastructure`는 DTO 직렬화·파일 교체·리소스 로딩·물리 통합을 담당한다. 게임 기획 규칙을 포함하지 않는다.

### 경계 통과 규칙

| 요청의 방향 | 허용되는 예 | 금지되는 예 |
|---|---|---|
| UI → 게임 | `BuyItems` 명령 전달, 결과를 화면에 표시 | 버튼이 금화·재고를 직접 차감 |
| 캐릭터 뷰 → 게임 | 물리 위치/상호작용 입력을 명령 또는 캡처 경계에 전달 | `OnDestroy`에서 선원·계약 삭제 |
| 경제 → 계약 | 오케스트레이터가 거래 결과를 반영하고 계약 소유자가 상태 변경 | 경제 코드가 계약의 내부 리스트/저장 파일 직접 수정 |
| 항해 → 계약 | `VoyageCompleted(voyageId)`를 게임 흐름이 배포 | 항해·UI·고용 화면이 각각 계약 횟수 감소 |
| 이벤트 → 저장 | 시작 체크포인트/종료 결과 저장을 명령/트랜잭션 경계에 요청 | 사건 객체가 별도 저장 서비스를 만들어 즉시 파일 기록 |

## 3. 도메인 객체와 데이터 원본

다음은 **논리 모델**이다. 곧바로 클래스 1개씩 만들라는 뜻이 아니다. 응집도·실제 기능을 기준으로 타입을 구성한다. 식별자와 항목은 게임 기획의 확정 요구를 반영하며, 미구현 시스템은 데이터 없이 계약만 남길 수 있다.

| 도메인 소유자/객체 | 자신이 소유하는 상태 | 본래의 책임 | 타 객체 접근 계약 |
|---|---|---|---|
| `GameSession` | 플레이 ID, 종료/게임 오버, 현재 GameMode, 시간·루트 참조 | 시작/정지·종료·진입·일관성 경계 | 하위 도메인에 명령, 결과 관찰 |
| `GameClock` + `PauseReasons` | 게임 경과 시간, 정지 사유별 토큰 | 1일=600초, 시간 흐름/중첩 정지 | 시간 읽기·정지 토큰 취득/해제 |
| `WorldState` | 항구·해역/지역 IDs, 각 지역의 지속 상태 | 위치·구역 전환 일관성 | `TravelToArea`/`AreaChanged` |
| `Ship` + `ShipLayout` | 함선 인스턴스 ID, 모델 참조, 해금 타일·현재 시설 인스턴스 목록·점유 상태 | 모델별 수용 제약·시설 추가/제거/배치·통행/출항 조건 | 시설 명령·시설 상태 조회 |
| `Voyage`/`Navigation` | 항해 ID, 목적/위치/방향/속도, 출항/입항 상태 | 출항·조타·경로·입항 판정·항해 1회 완료 | `Depart`/`Steer`/`ArrivalResolved` |
| `CharacterRegistry` + `Character` | 인물의 안정 ID, 생존/지역/스탯·활성 상태 | 인물 동일성, 행위 주체 상태 | 인물 ID 기반 조회/변경 |
| `CrewWork` + `WorkReservation` | 업무 할당·목표·선점·중단·복귀 상태 | 자격/우선순위/업무 수행, 중복 선점 방지 | 업무 요청/완료·예약 해제 |
| `Inventory` + `Wallet` | 소유자별 상품 수량·재화 | 거래 가능한 원본 재고, 이전과 소비 불변식 | `Transfer`/`Consume` 트랜잭션 |
| `ContractRegistry` + `CrewContract` | 인물 ID별 계약·선불/후불·횟수·채무/만료 | 고용·항해 차감·만료·정산·재계약 | `Hire`/`ApplyVoyage`/`Settle` |
| `Journal` + `Rest` | 과거/미기록/계획 경로·이벤트·메모, 취침/불침번 | 기록 누적·이월·소실 조건·취침 시간 경계 | `Record`/`Sleep`/`Wake` |
| `EventProgress` + `Battle` + `Prisoners` | 사건 ID/난수·선택·체크포인트·전투/포로 결과 | 개별 사건 처리, 관전 전투, 단일 결과 확정 | `BeginEvent`/`ResolveEvent` |
| `Economy`/`Market`/`Reputation` | 상인·항구의 거래 조건, 명성/평판 | 가격·구매·판매·강제 매각·명성 규칙 | 게임 흐름의 거래/정산 작업 |
| `QuestRegistry` | 의뢰 ID·진행·기한·결과 | 수주·납품·조건 판정 | `Accept`/`Complete` |

- 위 명칭은 역할 설명용이며 런타임에 모든 `Registry`를 한 번에 생성하라는 뜻이 아니다.
- 각 객체마다 **정의 ID**(동일 종류를 식별)와 **인스턴스 ID**(실제 개체)를 구별한다. `characterId`, `shipInstanceId`, `facilityInstanceId`, `voyageId`, `eventId`, `portId` 등은 저장·이력·관계에서 안정적으로 참조한다.
- 계약은 동일 인물을 ID로 참조한다. 화면 목록이나 Prefab을 인물 원본으로 사용하지 않는다.
- 항구와 선내는 현재 표시 지역과 별개로 지속 상태를 갖는다. 출항/입항/층 이동은 상태를 **전환**하지 복제하지 않는다.
- 보유금·재고·명성의 일관성은 여러 규칙에서 동시에 값을 쓰지 않도록 단일 변경 주체와 트랜잭션 단위로 보장한다.

### 3.1 공통 자료구조·컴포지션 계약 — 사용자 확정 방향

- **예시 구조 사용자 수용:** CrewData에 관련 스탯·현재 상태를 묶고, ItemDefinition에 공통 품목 정보와 선택적 기능 스탯을 연결하며 ItemStack으로 소유자별 수량을 관리하는 방향이 사용자 의도에 적합함을 확인했다. 예시의 필드 목록·타입명·public/internal 접근자·구체 소비/전투 산식까지 최종 구현으로 승인된 것은 아니다.
- 적용 대상은 인물에 한정하지 않는다. 화물 품목·함선·시설·무기·자원 등 게임에서 데이터로 다루는 개념 전반에 같은 원칙을 적용한다. 같은 개념은 시스템이 달라도 공통 모델·자료구조·ID·단위·열거형을 사용한다.
- 목적은 동일 정보를 시스템마다 다른 구조체로 재정의·변환하거나 구조체를 과도하게 세분화하는 것을 막는 것이다. 고용/업무/전투별 인물 원본, 구매/화물/약탈별 품목 원본을 따로 만들지 않는다.
- 공통 모델은 식별·정의와 실제 필요한 기능의 스탯·상태를 조합한다. 필요한 기능이 있으면 관련 데이터를 컴포넌트처럼 연결한다. 모든 객체에 모든 기능·스탯·저장 동작을 넣는 Master 구조를 만들지 않는다.
- 예: 동일 품목 정의를 거래·적재·소비·장비 기능이 함께 참조한다. 소비 기능이 필요하면 해당 소비 스탯을, 무기 기능이 필요하면 해당 무기 스탯을 연결한다. 일반 화물에 무기 데이터를 일괄 부여하거나 시스템별로 같은 가격·수량·정의를 복제하지 않는다. 이는 연결 방식의 예시이며 품목의 실제 소비·장비·약탈 자격은 GameDesign의 규칙을 따른다.
- 정의 데이터는 종류의 공통 정보이며, 보유 수량·내구도 같은 현재 상태와 구분한다. 같은 품목이라도 소유자별 수량은 다른 사실이다. 그런 실제 차이와 시스템별 원본 복제를 혼동하지 않는다. 인물별 계약·업무 진행·수감 관계도 같은 인물 ID에 연결한다.
- 데이터 컴포지션은 Unity ECS/DOTS나 모든 스탯을 MonoBehaviour로 구현한다는 결정이 아니다. C# class/struct·연결 방식은 책임·수명·실제 사용에 맞춰 선택한다. 같은 원본에 대한 변경 권한은 담당 소유자에게 한정하고 struct 복사로 오래된 상태가 남는 문제를 피한다.
- 기능 수행과 파일 저장은 공통 데이터 구조체의 책임으로 몰지 않는다. 담당 시스템/객체가 공통 데이터를 사용해 규칙을 수행하고 저장 조정자가 SaveEvent를 처리한다. 화면에는 선택·스크롤·표시 문자열 같은 표현 상태만 추가한다.
- 저장 컨테이너의 버전·ID 연결·고정 시드/파생 키 식별 정보·처리 완료 표식은 허용하되 이를 시스템별 중복 게임 모델을 만드는 근거로 삼지 않는다. 공통 데이터 직렬화를 우선 검토하고 별도 데이터 타입이 꼭 필요하면 차이·이유·필드 대응을 설명한다. 과도한 컴포넌트 분할·인터페이스·변환 계층을 선행 생성하지 않는다.

### 3.2 품목의 Unity 시각 자산 연결 — 구현 제안

- 실제 품목은 Editor에서 해당 품목 ID에 Sprite를 연결할 수 있어야 한다. 공통 품목 정의의 게임 규칙 데이터와 Unity 표현 자산을 같은 품목 ID로 대응시킨다. Domain의 공통 데이터에 UnityEngine.Sprite 의존성을 넣지 않는다.
- Content/Definitions의 품목 정의 자산에서 공통 품목 데이터와 Sprite 참조를 연결하는 방식을 기본 제안으로 삼는다. 자산 래퍼는 별도의 거래용/화물용 품목 모델이 아니며, 같은 규칙·스탯을 복제하지 않는다.
- UI 아이콘과 월드 표시가 같은 그림이면 재사용하고, 다른 그림이 필요하면 해당 표현 참조를 추가한다. 개별 ItemStack에 Sprite를 중복 보관하지 않는다. 저장에는 품목 ID와 소유/수량 등 진행 상태를 기록하고 Sprite 자체는 저장하지 않는다.
- 데이터 구조 방향은 사용자 수용 상태이나 이 절의 구체 Unity 자산 연결 방식은 기술 제안이다. 실제 제작 단계에서 사용 범위에 맞춰 확정한다.

## 4. 객체 생명주기·Unity 연결

| 대상 | 생성/복원 | 전환 중 유지 | 종료/해제 |
|---|---|---|---|
| `GameSession` 및 루트 상태 | 새 게임 또는 저장 복원에서 한 번 | 씬·층·UI 전환 전체 | 게임 종료/새 플레이 교체 시 해제 |
| 정의/카탈로그 | 프로젝트 자산 로드·검증 | 같은 플레이 동안 읽기 전용 | 세션 정리 시 참조만 해제 |
| 항구·함선·선원 **도메인** | 안정 ID별 생성/복원 | 화면 비활성·포털 이동에도 유지 | 명시된 게임 규칙으로만 상태 종료 |
| `WorldView`/`CharacterView` | 현재 지역/층 상태를 읽고 바인딩 | **뷰만** 활성/비활성·재활용 | 지역 전환/게임 종료 시 참조 해제 |
| UI 화면/모달 | Editor 제작 Prefab에 바인딩 | 화면 열기·닫기는 게임 상태를 임의 폐기하지 않음 | 이벤트 구독·정지 토큰 정확히 해제 |
| 자동 업무·항해·시간 | `SimulationScheduler`에 의해 처리 | 비표시 지역/층에서도 규칙에 따라 지속 | 전투/사건/정지 사유에 따라 명시적으로 중단 |

- Unity Scene 형식(단일 기반 + Prefab 콘텐츠, Additive 등)은 공간 수명·편집 규모·저장 정책에 의해 결정한다. **초기 기본안**은 단일 `Game` 실행 Scene, 하나의 Composition Root, 지역/함선/화면 별 Editor-authored Prefab이다. Scene 복제나 도구 편의성을 위해 여러 독립 게임 세션을 만들지 않는다.
- `GameObject.SetActive(false)`는 표시/충돌/입력의 제어다. 시간이나 AI를 유지해야 하는 도메인을 비활성 오브젝트의 `Update()`에 종속시키지 않는다.
- 프레임마다 월드 객체·UI를 새로 생성하지 않는다. 동일 ID의 View를 재사용하고 변경 사항만 반영한다. 동일한 의미의 값이 바뀌지 않았다면 구조 탐색·Transform 재설정·UI 텍스트 재할당을 반복하지 않는다.
- 시작 시 의존성 생성 순서: 정의 검증 → 저장 DTO 로드/검증 → 도메인 상태 구성·ID 연결 → 서비스/명령 경계 연결 → 월드·뷰 생성/바인딩 → UI 표시 → 입력/시뮬레이션 활성화. 로드 중 자원 소비·이벤트 판정·보상 적용을 발생시키지 않는다.
- 종료 순서: 신규 입력 차단 → 시뮬레이션 경계 확정 → 상태 캡처 → 저장 성공 확인 → 화면/구독/세션 해제 → 종료. 저장 실패를 '정상 저장됨'으로 처리하지 않는다.

## 5. 도메인 협력 시나리오 (사실상 아키텍처 테스트)

### 5.1 플레이어의 선장실 책상 → 일지

```text
PC Input → InteractAction → Interaction Resolver(targetId, distance, obstruction)
→ Application: OpenJournal → Screen Navigation + Pause Token
→ Journal UI View Model ← Journal State (읽기 전용)
→ Close/Back → Screen Close + 정확한 Pause Token 해제 → World Input 복귀
```

- 책상/접근점은 `WorldContent`의 편집 가능한 객체다. 단순 UI 버튼이 선장실 상호작용을 대신하지 않는다.
- 아직 작성/지도 기능을 구현하지 않았다면 일지의 해당 컨트롤은 `FrameDisabled`로 남는다.

### 5.2 선원 수리 업무

```text
GameClock → Scheduler → CrewWork(자격·욕구·업무 후보)
→ WorkReservation(시설 ID 선점) → Path/Movement
→ 시설 작업 위치 도착 → ShipFacility.Repair(재료·내구도 계약)
→ Result → Crew state/Inventory state 반영 → View 변경 통지
```

- 자격·선점·수리·이동/물리·표현은 서로의 책임을 대신하지 않는다.
- 밀린 선원은 작업 위치 밖에서 진행하지 않고 복귀 규칙에 따른다. 다른 층이 보이지 않아도 일과가 유지돼야 한다(`GameDesign.md` 선원 이동 보완).

### 5.3 항해 완료 → 계약 횟수·일지·저장

```text
Navigation.ResolveArrival(voyageId)
→ Application: VoyageCompletion Transaction
   → Voyage marks completed exactly once
   → ContractRegistry.ApplyVoyage(voyageId) exactly once
   → Journal.Arrive(voyageId)
   → WorldState.MoveToPort(portId)
→ Result/notifications → SaveEvent 정책에 따른 저장 요청 → Presentation refresh
```

- '항해 완료'는 여러 화면/서비스에서 각자 발행하지 않는다. 동일 `voyageId`의 재처리도 계약이 추가 차감되지 않아야 한다.
- 출발 항구로 복귀해도 기획서의 항해 1회 규칙을 따른다.

### 5.4 Event 연결 경계 — 현재 범위

Application에 Event 진입 요청·복귀 결과를 연결할 경계를 둔다. 기존 세션·공통 데이터·시간·입력·저장 조정자를 사용하며 별도의 세계 사본을 만들지 않는다. 구체 요청/결과 필드·사건 진행·전투·포로·체크포인트는 기본 프레임워크 완성 및 테스트 통과 후 설계한다. 지금 가짜 사건·성공 보상·임시 미니게임을 만들지 않는다.

## 6. 상태 전환과 시간

**권장 상위 진행 상태**: `ExploringShip`, `ExploringPort`, `Sailing`, `Dialog`, `Managing`, `Sleeping`, `Event`, `SpectatingBattle`, `EditingShip`, `GameOver`. 실제 상태는 필요할 때 구체화한다. 모든 상태를 하나의 상호 배타적인 enum으로 강제하지 않는다. 예: 항해 중 일지가 열리는 상태는 `NavigationContext + UI Modal + Pause`라는 **서로 독립적인 축**으로 표현할 수 있다.

- 상태 전이에는 **진입 조건 / 상태 변경 / 이탈 조건 / 정지 사유 / 저장 경계 / 결과 통지**를 각각 정의한다.
- 정지는 중첩 가능한 토큰 기반이다. UI A를 닫아도 UI B나 이벤트가 정지 요청을 가지고 있으면 세계 시간이 흐르지 않는다.
- `GameClock`의 시간과 물리 FixedUpdate는 구분한다. 물리 위치 캡처와 도메인 시뮬레이션 결과 반영 순서를 정의하여 저장 타이밍이 중간 상태를 잡지 않도록 한다.
- Input System은 행동 명령을 만들 뿐이며 도메인 규칙에 키 코드나 모바일 좌표가 스며들지 않는다.

### 6.1 P1-02 수용 — 시작·시간·정지·공간 전환

**상태:** 2026-11-01 사용자 수용. 상태 병존은 함선 진행·인물 위치·열린 화면·정지 여부라는 서로 다른 질문의 답을 함께 유지하는 뜻이며 추가 게임 기능이 아니다. 고정 게임 시드·판정별 파생 시드 설명도 수용했다. 근거는 GameDesign 2.4·4.1~4.4·5.1·13절 및 A01~A03·A27의 관련 부분이다. 확정 기획은 유지하며 아래 실행 순서·실패 정책·참조 표현은 기술 제안이다. 수면은 P1-04에서 고속 연산 후 08:00 정상 기상·결과 저장으로 확정했다. 사건 저장 상세는 기본 프레임워크 검증 이후다.

### 6.2 새 게임·이어하기·종료

- 새 게임: 플레이 ID·고정 게임 시드 준비 → 공통 콘텐츠 정의 검증 → 무작위 시작 항구 선택 → 고정 모델의 함선 생성·해당 항구 정박 연결 → 선원 0명·시작 자금 구성 → 플레이어 위치 연결 → 지역 표현·카메라·UI·입력 연결 → 시간 진행 허용. 시작 항구 추첨은 새 플레이 생성 시 한 번만 수행하며 화면을 열거나 로드할 때 재추첨하지 않는다. 초기 자금은 데이터로 둔다.
- 초기 플레이어가 항구 구역/선내 중 어디에서 시작하는지와 최초 시간은 기획에서 미지정이다. 첫 시작 위치를 첫 제품 Slice의 선장실과 자동으로 동일시하지 않는다. 구현할 시점에 명시하며 임의 초기 저장 이벤트를 추가하지 않는다.
- 이어하기: 파일 형식·버전·플레이 종료 상태 검증 → 공통 데이터·ID 관계·게임 시간·고정 게임 시드·파생 키 식별 정보 복원 → 지역 표현 연결 → 기상/조작 가능 상태 정리 → 입력·시간 활성화. 로드 중 새 게임 추첨·자원 소비·항해 차감·보상·승하선 SaveEvent를 실행하지 않는다. 저장된 공간 위치를 임의로 침대나 다른 항구로 이동시키지 않는다. 수면 저장은 기상 결과를 재연산 없이 복원한다. 일반 로드는 저장된 시각/위치를 유지한다. 사건별 중단 우선순위는 후속 범위다.
- 종료: 새 명령 차단 → 진행 중 전이의 안전한 경계 확보 → 정상 종료 SaveEvent → 파일 저장 성공 확인 → 세션·뷰·구독 해제 → 종료. 실패하면 이전 정상 파일을 보존하고 실패를 알리며 재시도 가능하게 하는 방식을 제안한다. 저장 실패를 정상 저장 종료로 표시하지 않는다. 로드 파일 검증 실패 시 기존 파일을 새 게임으로 덮어쓰지 않는다.

### 6.3 같은 세계에서 병존하는 상태와 시간

- 게임 날짜·시간 원본은 GameClock 한 곳이다. 정상 진행에서 현실 600초가 게임 하루이며, UI·각 선원·시장에 독립된 게임 시계를 만들지 않는다. 정지 중 현실 시간이 지나도 게임 시간이 누적되어 닫는 순간 몰아서 진행하지 않는다.
- 항구 정박/항해 상태, 플레이어의 선내/항구 위치, 열린 UI, 취침, 사건/전투는 서로 다른 상태 축이다. 항해 중 일지를 열었다고 항해 자체를 종료하지 않는다. 선내 승선과 출항, 하선과 자동 입항도 구별한다.
- 게임 시간이 진행할 때만 일과·식량·업무·항해·날짜 기반 시장 갱신·요청 기한 등이 각 규칙에 따라 진행한다. 동일 시간 원본을 읽는 것이 모든 시스템에 동일한 Update 빈도를 강제한다는 뜻은 아니다. 비용에 맞는 갱신 주기는 후속 설계에서 정한다.
- 게임 시간이 날짜 경계를 통과하면 그 경계까지 진행 → 해당 날짜 상태 갱신을 일관되게 반영 → 항해 중 하루 경과 SaveEvent 요청 → 다음 구간 진행 순서를 제안한다. 수면 중 날짜 경계는 경과 연산에 반영하고 동일 상태 경계의 저장 요청은 병합한다. 입항은 독립 Trigger 관계로 구간 내 진입을 검사한다. 사건 경계 상세는 후속 범위다.

### 6.4 중첩 정지와 입력 포커스

- 대화·거래·일지는 각자 정지 토큰을 얻는다. 정지 요청이 하나라도 남아 있으면 세계 시간과 시간에 종속된 진행을 멈춘다. 닫힌 화면은 자신이 얻은 토큰만 해제한다. UI의 이벤트 중복/예외 해제에서도 다른 화면의 토큰을 지우지 않는다.
- 화면을 열면 조작 포커스는 최상위 모달로 이동하고 월드 이동·상호작용 입력은 차단한다. 닫기 입력은 최상위 화면 하나를 닫는다. 모달이 모두 닫히고 다른 차단 사유가 없을 때 월드 입력을 복귀시킨다. 열린 화면을 뒤의 월드 클릭이 관통하지 않는다.
- UI 애니메이션·버튼 피드백은 세계 시간 정지와 별도로 동작할 수 있다. UI 표시를 정지 토큰 자체에 종속시켜 닫기조차 불가능하게 하지 않는다. 실제 이동·물리의 정지/재개 동기화는 P1-03에서 검토한다.
- 관전 전투는 실제 전투 시간이 진행되어야 하므로 사건이라는 이유로 영구 정지 토큰을 유지하지 않는다. 전투 준비·대화와 실제 전투 진행의 전환, 전투 중 모달 허용 범위는 P1-06에서 확정한다.
- 일지는 선장실의 지정된 상호작용 대상을 통해 연다. 입력 → 공통 상호작용 대상 확인·거리/차폐/상태 검사 → 일지 열기 요청 → 화면·포커스·정지 연결이다. HUD 항해 일자 표시는 일지 열기 버튼으로 사용하지 않는다. 검사 실패 시 상태·시간을 변경하지 않고 필요한 거부 피드백만 제공한다.

### 6.5 공간 전환·승하선·저장 요청

**P4 실행 계약 (2026-11-05):** 기존 선장실의 Transform/가구/카메라 기본 수치는 보존한다. 하나의 Game Scene 안에 구역별 직렬화된 WorldArea 뷰를 두고 현재 구역만 활성화한다. 각 구역 ID와 Portal 연결/도착점은 정의 데이터이며 플레이어 현재 위치의 원본은 CharacterState 하나다. WorldArea는 바닥·정적 충돌·카메라 경계·선택 가능한 대상만 제공하고 시간/인물 복사본을 소유하지 않는다. GameSession의 전환 명령이 유효한 현재 Portal·목적지·도착점을 검증하고 Transition 정지를 획득한다. Presentation 어댑터가 전환 화면을 표시하고 대상 자산/충돌을 검증한 후 도메인 위치를 한 번 확정하고 뷰·물리·카메라를 재연결한다. 실패하면 원래 위치/구역을 유지한다. 승하선 성공 후에만 SaveCoordinator가 저장하며 저장 실패는 완료된 이동을 되돌리거나 재실행하지 않고 메뉴에서 재시도한다. 층/항구 구역 간 일반 이동은 저장하지 않는다. 비표시 구역의 정의/시설은 파괴하지 않으며 미래 선원/업무 시뮬레이션 원본을 View 활성 여부에 결합하지 않는다. 현재 없는 선원/업무를 가짜 상태로 추가하지 않는다. 기존 버전1 저장의 AreaId/X/Y 표현을 유지하고 로드 시 해당 구역의 유효 위치와 연결한다. 도착/복귀·중복 입력·정지 중 거부·실패 rollback·승하선 저장 실패·반복 Play·기존 선장실 회귀 및 전환 프레임/GC를 검증한다. 2026-11-05 사용자가 이동·공간 전환 등 P4 목적 범위의 동작 조건을 모두 통과했다고 확인했다. 오브젝트 배치·Scene 디자인은 이번 평가에서 제외했으며 시각 승인으로 확대하지 않는다.

- 캐릭터의 공간 위치는 공통 위치 데이터로 지역 ID·필요한 함선 ID/층 ID·지역 내 좌표를 표현하는 방식을 제안한다. 월드는 연결 가능 여부와 접근점을 제공하고 인물 상태 소유자가 최종 위치를 반영한다. UI·카메라가 별도 실제 위치를 갖거나 함선과 항구에 인물 사본을 만들지 않는다.
- 전환 요청 → 유효 대상·접근 조건·도착점 검증 → 대상 지역 자산 준비 → 전환 동안 입력·시간을 임시 차단 → 위치와 현재 표시 지역을 함께 확정 → 뷰·카메라 연결 완료 → 승선/하선이면 SaveEvent 요청 → 임시 차단 해제 순서를 제안한다. 전환으로 시간이 경과하는 별도 게임 규칙은 추가하지 않는다.
- 도착 자산 준비·위치 검증 실패 시 원래 위치/뷰를 유지하고 승하선 완료·저장을 발행하지 않는다. 전환 성공 후 파일 저장만 실패한 경우에는 완료된 이동과 저장 실패를 구분하여 표시·재시도하고, 이동/보상을 무조건 재실행하지 않는다. 구체 저장 실패 UX는 구현 시 정한다.
- 한 화면에는 함선 한 층만 표시하고, 비표시 층의 공통 인물·업무·시설 데이터는 유지한다. 전환에 필요한 임시 정지 해제 후 다른 층도 게임 시간에 맞춰 진행한다. 층별 전환 일러스트 요구를 유지한다.
- 층 이동·일반 항구 포털 이동은 승선/하선과 구별하며 그 자체로 새 SaveEvent를 추가하지 않는다. 승선은 항구에서 함선으로, 하선은 함선에서 항구로의 인물 공간 전환이다. 자동 입항은 항해 완료 흐름에서 별도로 검토한다.

**검증 계약:** 새 게임의 시작 조건(A01), 중첩 UI 종료 시 조기 재개 없음(A02), 층 이동 후 한 층 표시·타층 상태 유지(A03), 정상 종료/복원(A27의 관련 부분)을 점검한다. 거부·중복 전환·대상 로드 실패·저장 실패·UI 예외 닫기·반복 세션 진입도 포함한다. 실제 조작·카메라 전환·입력 복귀·시간 누락/중복 진행은 제품 Scene에서 후속 검증하며 현재는 설계 검토다. 정지/전환의 역할과 비용을 분리하고 미구현 도메인의 임시 데이터를 선행 생성하지 않는다.

## 7. 저장과 일관성

- **사용자 확정 방향(2026-11-01): SaveEvent 기반 저장.** 각 시스템의 정해진 시점에서 저장 요청을 호출하고 하나의 SaveCoordinator가 기록한다. 매 프레임 캡처·프레임 이력·상시 스냅샷 저장·입력 전체 로그 재생을 요구하지 않는다. 기존 문서의 SaveSnapshot은 호출 주기를 뜻하지 않았으나 혼동 방지를 위해 이 문서에서는 저장 데이터로 표현한다.
- 확정 SaveEvent는 정상적인 종료, 승선, 하선, 항해 중 하루 경과, 수면이다. 승선·하선은 각각 포함하며 자동 입항이나 모든 포털 이동을 같은 이벤트로 자동 확대하지 않는다. 수면은 사용자가 지정한 “수면한 시점까지 저장, Load하면 기상하면서 시작”을 따른다. 앞서 제안했던 취침 시작 직전으로 되돌리는 방식은 확정안이 아니다. 수면 경과·중단 사건·입항의 상세 시간 경계는 P1-02/04에서 이 요구를 보존해 명시한다.
- 기존 사건 시작/종료 저장과 사건 중 시작 체크포인트 복원 규칙은 새 SaveEvent 열거 및 기상 시작과의 우선순위가 아직 명시되지 않았다. 사건 규칙을 임의로 폐기하거나 새 목록 외 추가 저장을 확정하지 않는다. P1-06에서 최종 확인 전까지 사건 관련 기존 조항은 검토 대상이다. 게임 오버 이어하기 제한은 유지한다.
- SaveEvent 처리 시 진행 중인 도메인 전이를 완료하거나 안전한 경계에서 상태·관계 ID·고정 게임 시드·파생 키 식별 정보를 함께 기록한다. 이는 저장 시점의 일관성을 위한 것이며 매 프레임 저장 방식이 아니다. GameObject/Transform/Scene 인스턴스/Unity 이벤트 구독은 저장하지 않는다.
- 결정론은 동일 저장 상태·동일 규칙 버전·동일한 의미의 행동과 조건에서 같은 게임 결과를 유도한다. 고정 게임 시드와 판정별 파생 시드를 사용하며 상세 계약은 7.1절을 따른다. 전역 난수 스트림 소비 위치를 필수 저장하는 방식은 채택하지 않는다.
- 저장 이후 행위가 로드 후 재반복되는 것은 허용한다. 복원된 상태에서 해당 행위를 다시 수행한 결과와, 이미 저장에 반영된 효과가 로드 처리 때문에 다시 가산되는 오류를 구분한다. 다른 선택·행동에도 같은 결말을 강제하거나 프레임·물리 전체를 동일 재현하는 요구로 확대하지 않는다.
- 저장 소유자는 하나의 `SaveCoordinator`다. 다른 도메인은 '저장 요청' 결과만 반환할 수 있으며 파일 IO를 직접 수행하지 않는다.
- 저장 버전, 안정 ID, 검증, 원자 교체, 오류 시 원본 보존, 게임 오버 계속하기 제한을 구현한다(`GameDesign.md` 13절).
- 거래·계약·항해·사건 보상 등 재실행에 민감한 전이는 **도메인 결과 식별자/적용 완료 상태**를 저장해 중복을 방지한다.
- 이벤트 진행 중 현재 UI 상태 저장이 아닌 **이벤트 시작 시점 체크포인트** 정책은 기획 확정 사항이다. 평상시 스냅샷과 동작이 달라지는 이유를 API 수준에서 명시한다.
- **새 프로젝트의 첫 저장 형식**부터 버전 관리를 시작한다. 기존 프로젝트의 임시 저장 슬롯·ID·직렬화 코드를 가져오지 않으며, 이전 파일 이관은 사용자 별도 요구가 있을 때만 설계한다.

### 7.1 고정 게임 시드·판정별 파생 시드 — 사용자 수용

- 새 플레이에 고정 게임 시드 하나를 부여하고 저장·복원한다. 같은 게임 안에서 시스템별로 별도의 무관한 원본 시드를 만들지 않는다.
- 시작 항구 선택, 사건 발생, 적 구성, 보상 등 게임 판정은 고정 게임 시드와 해당 판정을 구별하는 안정적인 키로 파생 시드를 얻는다. 용도·항해 ID·게임 날짜·사건 ID·판정 번호/시간 구간 등 실제 필요한 식별 정보를 조합한다. 모든 항목을 모든 판정에 무조건 넣지는 않는다.
- 같은 키는 호출 시점·서로 다른 시스템의 호출 순서와 관계없이 같은 결과를 얻는다. 키 결합·해시·난수 알고리즘은 실행 기기와 프로세스가 달라도 재현되도록 명시해야 한다. 구체 알고리즘과 버전 변경 호환은 구현 시 확정한다.
- 반복 판정을 서로 구별할 필요가 있으면 이미 존재하는 사건/항해 식별 정보나 안정적인 순번을 사용한다. 복원에 필요한 키의 원본 정보는 저장하되 별도 난수 상태 구조체나 전역 호출 횟수를 일괄 추가하지 않는다. 순번을 사용하는 경우에도 임의 시스템의 난수 호출 수가 아니라 해당 게임 판정의 정체성을 뜻한다.
- 판정 내부에서 여러 난수가 필요하면 용도별 하위 키 또는 판정에 국한된 난수 생성기를 사용할 수 있다. 다른 판정의 결과를 바꾸는 공용 가변 난수 흐름을 만들지 않는다. 중간 재개가 꼭 필요한 예외는 근거와 복원 경계를 별도로 검토한다.
- 저장 이후 같은 행동을 같은 조건에서 반복하면 같은 판정 결과를 얻는다. 다른 행동·선택에는 다른 결과가 허용된다. 물리 프레임 전체의 결정론은 요구하지 않는다. UI·효과 난수는 게임 판정의 키와 결과에 영향을 주지 않는다.
- 사건 시작/종료 SaveEvent 및 사건 중 로드·기상 상세는 기본 프레임워크 검증 이후 실제 Event 설계에서 확인한다. 현재의 추가 저장 경계로 확정하지 않는다.

## 8. 구조 변경 제안의 필수 산출물

도메인 추가, 새로운 Scene 경계, 관계 변경, 공용 계약 변경을 하기 전에 다음 여섯 항목을 `Architecture.md`에 반영하고 사용자에게 변경안을 제시한다.

1. 변경할 모델과 책임: 무엇을 **소유**하고 무엇을 소유하지 않는가.
2. 의존성 화살표: 대상이 아는 외부 계약과 금지할 역참조.
3. 데이터 수명: 생성·일시 숨김·복원·파괴와 안정 ID 관리.
4. 대표 시나리오: 입력에서 최종 도메인 상태/표현까지 호출 순서와 실패 처리.
5. 이전 기능 영향: 저장·장기 시뮬레이션·UI Frame·테스트의 영향.
6. **횡단 품질 영향**: 플레이어가 느끼는 반응성, 이동 연속성, 충돌 역할, 표현 피드백, 관련 규모에서의 CPU/GC/메모리 비용과 계측 방법.

### 구조 게이트 (`Architecture Gate`)

- 각 변경 도메인의 상태 쓰기 주체가 **하나로 명시**되어 있다.
- Domain에서 UI·Unity Scene·파일 IO로 역방향 접근하지 않는다.
- 다중 도메인 시나리오의 최종 결과 적용 지점이 **한 곳**이고 idempotency/실패 경계가 존재한다.
- 비표시 세계와 재진입/저장/복원이 같은 상태 원본을 사용한다.
- 새 기능 한 유형을 추가하는 경로가 설명되고, 무관한 중앙 매니저 수정이 불가피하지 않다.
- 순환 의존·고립된 개발 씬의 별도 게임 상태·무검증 구조 복제가 없다.
- 이동·충돌·공간 질의가 각 도메인/뷰에 중복 임의 구현되지 않으며, 실제 플레이 품질과 성능을 검증할 경로가 있다.

상기 항목 중 하나라도 설명되지 않으면 `미통과` 또는 `미확인`; 컴파일이 성공해도 다른 시스템 구현으로 확대하지 않는다.

## 9. 횡단 실행 품질 아키텍처 — 개별 기능보다 상위의 계약

이 장은 특정 이동·물리 알고리즘의 채택을 지시하지 않는다. **현재 게임에 맞는 알고리즘을 선택할 책임과 품질 평가의 의무**를 정의한다. 구현은 최소 기능만 켜되 동작의 충실도·표현의 연속성·시스템의 효율을 줄여서는 안 된다.

### 9.1 공간 엔티티 분류와 물리 사용 원칙

각 공간 객체 유형에는 다음을 **실제 씬 제작 전에** 결정한다: `역할(정적 지형/동적 유닛/상호작용 대상/감지 영역/시각 전용)` → `차단 여부` → `필요한 물리/공간 질의` → `레이어와 접촉 조합` → `활성/비활성 수명`.

| 유형 | 기본 기대 | 주의점 |
|---|---|---|
| 정적 벽·선체 경계·통행 장애 | 필요한 경계에만 정적 Collider 또는 동등한 공간 차단 데이터 | 장식 Sprite마다 Collider 복제 금지 |
| 플레이어·움직이는 선원 | 실제 충돌/회피 요구에 맞는 운동체와 충돌 정책 | 모든 유닛 쌍의 물리 접촉을 기본값으로 강제하지 않음 |
| 책상·시설·포털 등 상호작용 대상 | 점유 차단과 상호작용 가능 범위를 서로 독립적으로 정의 | 보이는 Sprite 전체를 감지 Collider로 간주하지 않음 |
| 거리·시야·선택·탐지 | 목적에 맞는 공간 질의·Trigger·인덱스 | 모든 엔티티에 상시 Trigger/Rigidbody를 추가하지 않음 |
| 바닥·조명·이펙트·표지 등 시각 전용 | 원칙적으로 불필요한 물리 연산 없음 | 입력/접근을 맡지 않는 객체의 무의미한 Collider 금지 |

이 표는 기본 정책이다. 예외는 게임 규칙·실제 접촉 요구·측정 근거를 기록하고 선택한다. 레이어 충돌 매트릭스와 질의 빈도는 `ProjectStructure.md`에 실제 엔진 값으로 기록한다. **Collider가 필요 없다는 가정도 무조건 옳지 않다**. 차폐·상호작용·통행·물리 반응이 필요한 요소는 누락하지 않는다.

### 9.2 움직임의 단일 책임과 시간 경계

- `Character` 또는 해당 인물 상태 소유자는 논리적 위치·이동 상태의 권위를 갖는다. `Movement` 역할은 목표/경로·조향·장애물 대응 및 최종 위치 반영을 계약으로 제공한다. 표현은 움직임 결과를 읽는다.
- `Input → Move Intent → Movement/Spatial Query → State Capture → View/Animation/Camera`의 흐름을 적용한다. 입력 클래스·AI·Transform 갱신·저장 코드가 각각 인물 위치를 독자적으로 수정하지 않는다.
- **움직임의 연속성**은 실제 경과 시간·스텝 정책·정지/재개/목표 변경에 대해 검토한다. 물리 시뮬레이션과 렌더 프레임의 차이가 눈에 띄는 끊김을 만들면 필요한 보간/동기화 등을 설계한다. 특정 보간 알고리즘을 필수로 고정하지 않는다.
- 벽 밀착·대각 이동·선원 간 근접·좁은 통로·층/지역 전환·화면 밖/안 전환·저장/재진입을 대표 사례로 삼는다. 좌표 순간 이동은 명시된 포털/씬 전환 등 규칙상 필요한 경우에만 허용하고 이유를 기록한다.
- 이동, 애니메이션, 카메라, 상태바 등 보이는 동작의 시간 기반 갱신 관계를 분리해 일관성을 유지한다. 화면 밖 선원의 판단·경로 갱신은 화면 가시성과 구분하되 **실제 필요한 빈도와 규모**를 기준으로 스케줄링한다.

### 9.3 성능과 변경 비용은 구조 설계의 속성

- `Update`/`FixedUpdate`에서 전체 계층 탐색·매번 경로 전면 계산·상태 불변인 UI 전체 재바인딩·불필요한 객체 생성/파괴·부모 재지정을 기본 패턴으로 사용하지 않는다. 이벤트/dirty 갱신, 캐시, 국소 공간 질의 등은 실제 요구와 계측에 따라 선택한다.
- 시스템별 **주요 비용과 확장축**을 밝힌다(유닛 수, 시설 수, 지역 크기, UI 행, 사건 수 등). 대표/혼잡 시나리오에서 비용을 관찰하고, 아직 측정하지 않았다면 성능은 `미확인`으로 둔다.
- 성능 최적화는 11단계에 처음 시작하는 작업이 아니다. 모든 Slice에서 명백한 비효율을 막고 관찰 가능한 성능 회귀를 검사한다. 11단계는 통합·장시간·기기별 튜닝을 담당한다.
- 무조건 풀링·ECS·커스텀 물리·복잡한 경로 탐색을 도입하지 않는다. **가장 작은 적합한 설계**를 측정과 실제 게임플레이 품질로 정당화한다.

### 9.4 구현 선택 및 품질 실패 처리

구현 착수 전 대상 행동의 예상 품질과 1~2개 실현 방법의 차이를 짧게 비교한다. 기술 선택을 과도하게 문서화하지 않되, 사용자 체감·물리 정책·성능·수정 비용에 큰 영향을 주는 결정은 이유를 남긴다. 구현 후 실제 Unity 플레이/시각 기록/Profiler로 예상과 실측의 차이를 확인한다. 기능 조건을 만족해도 눈에 띄는 끊김·부자연스러운 상호작용·불필요한 물리 비용·성능 저하가 있으면 **미완료**이며, 다음 기능으로 넘어가기 전에 같은 Slice에서 수정한다. 숫자 목표가 아직 합의되지 않은 항목은 관찰·측정 결과와 미정 사항을 분리해 보고한다.

### 9.5 P1-03 제안 — 함선·시설·인물·업무·이동·물리

**상태:** P1-03 사용자 수용·정정 반영 완료. 구체 기술 수치는 구현 시 검증한다. 기획 근거: GameDesign 4.2·7.1~7.5·9.1~9.4절, A03·A07~A08·A15~A17. 공통 데이터 컴포지션 원칙을 적용하며 아래 실행 계약·실패 정책은 제안으로 다룬다.

#### 9.5.1 함선·시설 데이터와 공간 원본

- **사용자 확정 정정:** 함선은 모델별 수용 규격을 가진 컨테이너이며 시설 목록은 추가·제거 가능한 개별 시설 인스턴스의 집합이다. 함선 기능·시설 목록을 고정 필드나 고정 슬롯 목록으로 가정하지 않는다. 시설 종류는 선원·품목과 마찬가지로 다양하게 확장한다.
- 함선 모델 정의에는 최대 수용 크기와 형상, 층 구성, 모델별 배치 가능 타일/영역, 기본 시설 구성, 연결점과 기획상 고정 배치 제약을 둔다. 각 모델은 서로 다른 타일 배치를 가질 수 있다. 수용 크기를 임의의 동일 격자나 단순 시설 개수 제한으로 치환하지 않는다. 수용 규격의 구체 데이터 표현·수치는 해당 모델 제작 때 정한다.
- Ship 인스턴스는 모델을 참조하고 실제 해금 상태·현재 설치 시설 인스턴스 목록·점유 상태를 유지한다. 모델의 기본 시설 구성은 새 함선 생성 시 실제 인스턴스로 만드는 초기 배치 규격이다. 로드/뷰 전환 때 기본 시설을 다시 생성하거나 현재 목록으로 덮어쓰지 않는다. 기본 포함 시설이라는 이유만으로 제거 불가/고정 시설로 취급하지 않는다. 고정 위치·이동/제거 제약은 기획에 근거한 별도 조건이다.
- 시설 종류의 공통 정의에는 점유 크기/형상·허용 층·필요한 기능 스탯·표현 참조를 연결한다. 실제 시설에는 안정적 시설 ID·종류 ID·소속 함선/층·배치 좌표·방향·현재 내구도/기능 상태를 둔다. 같은 종류라도 각 설치물의 위치·파손 상태는 독립이다. 수리·적재·침대·조타 등 필요한 기능 데이터를 조합하며 기능별 시설 사본을 만들지 않는다.
- 함선의 가변 기능은 실제 설치·해금·정상 기능 상태와 해당 시설 정의에서 도출한다. 예를 들어 유효한 화물 시설의 적재 스탯으로 함선 적재 가능량을 산출한다. 함선 모델의 고유 제약과 시설로 얻는 기능을 구분하고, 계산 캐시가 필요해도 재구성 가능한 결과로 취급한다. 같은 원본을 Ship의 별도 기능 플래그/수치와 시설 목록 양쪽에서 독립 변경하지 않는다.
- 추가·제거·재배치 요청은 함선 소유자의 한 변경 경계에서 시설 목록과 공간 점유를 함께 갱신한다. 목록만 변경되고 점유가 남거나 그 반대인 상태를 만들지 않는다. 모델 최대 범위·해금 타일·시설 전체 점유 영역·겹침·층/고정 제약을 검사한다. 기능이 사라지면 관련 작업/예약·수용 대상에 영향을 알리고 재검증한다. 초과 화물·수감자·현재 사용 중 시설의 제거 정책은 P1-05/06에서 검토하며 임의 삭제하지 않는다.
- ShipLayout이 논리 점유·통행 정보를 소유한다. Collider는 이를 기반으로 연결하는 표현/물리 수단이며 별도의 배치 규칙 원본이 아니다. 기능상 잠긴 타일은 통과 불가, 항해 중에는 해금된 타일만 활성·시각화한다. 항구 조선소와 허용된 항해 사건의 배치 권한을 구분하고 허용된 사건 중 배치는 시뮬레이션을 정지한다.
- Sprite 외곽·점유 타일·이동 차단 경계·작업 접근점은 구분한다. 선원은 정의된 유효 작업점에 접근한다. 필수 구성과 접근 가능성에 대한 영향도 검사하되, 필수 시설 부족 상태에서 편집 자체를 허용할지와 출항을 금지하는 판정은 구별한다. 기존 출항 제한을 모든 제거 요청의 즉시 금지로 확대하지 않는다. 구체 편집·제거·화물 이전 UX는 P1-05에서 검토한다.

**2026-11-04 로컬 배치 Grid 계약 — 현재 정의와 후속 구현 경계**

- World/Character의 연속 위치는 기존 원본을 유지한다. Placement Zone은 소유 객체/층의 로컬 원점·범위·셀 크기·셀 허용 정보를 제공하며 전역 이동/물리 격자가 아니다. 배의 이동/회전 시 Zone을 소유 객체의 좌표 변환으로 월드에 표시한다. 최신 사용자 정정의 표준 셀은 **1 unit**, Zone과 가구 논리 루트 배율은 1이다. 셀 경계에 맞는 가구 위치도 연속 실수 좌표로 표현한다.
- 같은 Grid 정의를 Domain의 범위/전체 Footprint 검사와 Editor Gizmo가 참조한다. P3에는 런타임 Overlay·스냅·드래그/Preview·확정 기능이 없다. 현재 정렬된 초기 배치는 Editor에서 작성한 배치이며 런타임 자동 보정으로 취급하지 않는다. 배치 금지 셀은 별도의 통행 금지 규칙이 없는 한 인물 이동을 막지 않는다.
- 표준 셀의 월드 크기는 공유 GridSettings.asset 하나가 소유한다(현재1 unit). 가구 Root의 CellSize가 점유 Cell 수·공유 설정·시설 종류·CellArea를 연결한다. FurnitureDefinition에는 종류 ID만 두며 점유 크기를 중복 저장하지 않는다. 현재 책상2×1, 침대1×2, 의자/상자는 미정(0,0)이다. 미정은 배치 가능한 크기가 아니다. Sprite는 원본 비율을 유지해 확정된 점유 안에 uniform fit한다. CellSize는 시설 위치·내구도·업무·재고를 소유하지 않는다.
- PlacementSpace는 함선/층의 공통 로컬 원점·설정·최종 제외 셀을 소유한다. 바닥에 연결한 하나 이상의 GridArea는 Inspector RectInt로 같은 원점 기준 셀 시작 좌표와 폭·높이를 정의한다. Area마다 별도 원점을 만들지 않는다. 허용 셀은 활성 Area의 합집합에서 제외 셀을 뺀 집합이며 겹침은 한 번만 계산한다. 전체 Footprint가 이 집합 안이면 여러 Area의 이음부를 걸쳐도 허용한다. 다른 PlacementSpace와는 합치지 않는다. 현재 선장실은 겹치는 두 Rect로63개 허용 셀을 구성한다. 파생 PlacementGrid는 변경 시 재구성하는 캐시이며 독립 원본이 아니다.
- 계층은 Root(CellSize) 아래 CellArea(FurnitureCellArea), Visuals(SpriteRenderer), Collision(Collider2D)의 형제 관계다. CellArea는 부모 CellSize와 같은 GridSettings를 읽는다. 적합성의 위치 기준은 CellArea 중심을 PlacementSpace 로컬로 변환한 연속 위치다. Sprite 크기를 바꿔도 Collision/CellArea가 함께 변형되지 않는다. 접근점도 형제 객체다.
- Editor Gizmos에서 가구 셀·점유·크기는 선택과 무관하게 표시하고 Prefab Mode에서도 공유 설정을 사용한다. 미정은 별도 표식이다. PlacementSpace 선택 시 합집합의 허용 셀과 최종 제외 셀을 표시한다. 이 표시는 런타임 Overlay가 아니며 Grid 설정 변경으로 가구 Transform을 자동 재배치하지 않는다.
- **후속 편집 흐름:** Interaction이 허용하는 편집 컨텍스트에서 Zone/시설 인스턴스 ID를 선택한다. 월드 포인터를 Zone 로컬 연속 좌표로 변환한 뒤 전체 Footprint를 놓을 수 있는 후보 중 가장 가까운 유효 기준점을 구한다. 동률은 고정된 셀 주소 순서로 정하며 후보 없음은 확정 불가다. 멀리 스냅된 후보는 포인터와의 차이를 분명히 표시한다. 별도 최대 스냅 거리는 아직 확정하지 않는다.
- **후속 판정 원본:** Zone 경계·셀 허용·현재 시설 점유·층/고정 제약·필수 접근 공간과 출입구·연속 좌표 인물의 실제 접촉을 조합한 결과를 Overlay/Preview/확정이 공유한다. 인물을 영구적인 점유 셀로 복제하지 않는다. Grid가 유효하더라도 편집 권한·결제/수용량 제한은 각각 재검증한다.
- **후속 트랜잭션:** 기존 시설을 드래그하는 동안 확정 상태와 기존 View를 보존하고 별도 Preview만 이동한다. 후보 계산에서 자기 점유만 제외한다. 취소는 원본 유지, 확정은 버전/조건 재검증 후 기존 점유 해제·새 점유·원본 연속 위치·필요한 비용/용량 변경을 하나의 명령 경계에서 반영한다. 실패 시 부분 반영하지 않는다. Collider·접근점·정렬은 확정 상태의 View로 갱신한다.
- **후속 저장/생명주기:** 시설의 확정 연속 위치·Zone ID·방향을 시설 원본에서 저장하고 셀 주소/점유는 같은 정의로 재구성한다. Preview와 편집 입력 포커스는 저장하지 않는다. 배치 확정을 새 SaveEvent로 추가하지 않으며 기존 정상 종료·승하선·하루 경과·수면 경계를 따른다. 편집 중 정상 종료는 미확정 Preview를 취소하고 확정 상태를 저장한다. 정의 변경으로 기존 배치가 무효가 되면 버전별 검증/명시적 이전을 적용하며 임의 재스냅/삭제하지 않는다.
- **Interaction Highlighting 현행 구현:** IInteractionTarget → InteractionResolver → GameSession.FocusedInteraction의 단일 선택 결과를 강조·행동 안내·입력 실행이 공유한다. 실행 가능/같은 공간/거리/가림을 먼저 검사하고 우선순위 내림차순·거리 오름차순·안정 ID 순으로 하나를 선택한다. 같은 우선순위에서는 기존 대상의 거리 여유0.12 unit으로 경계 흔들림을 억제한다. E 입력 시 선택했던 같은 ID/행동을 재검증하며 무효라면 다른 대상을 대신 실행하지 않는다. UI 정지·거리 이탈·가림·비활성·제거 시 해제한다. 일지 책상과 현재 활성 구역의 이동 Portal이 실제 대상이다. Portal도 같은 선택 결과·안내·E 실행·가림/정지 해제 규칙을 따른다. InteractionHighlight는 기존 SpriteRenderer에 공유 URP2D 재질과 MaterialPropertyBlock을 적용해 기본1.25 화면 픽셀의 따뜻한 색 내부 윤곽선을 표시한다. 기존 책상 Prefab의 승인된 직렬화 값은3px이며 유지한다. 원본 PNG·알파·Sort/차폐는 유지하고 해제 시 원래 재질/속성을 복원한다. 매 프레임 재질 인스턴스나 전역 Scene 탐색을 만들지 않는다. 저장 스키마/SaveEvent는 바꾸지 않으며 선택/강조는 일시 표현 상태다.

#### 9.5.2 인물·생활·업무의 공통 데이터

- 인물은 동일한 공통 인물 모델을 사용하고 플레이어/선원은 조작 주체와 가능한 행동을 구분한다. 능력·경력·특기·생활/위치와 실제 필요한 기능 데이터를 연결한다. AI·전투·고용마다 별도의 인물 원본을 만들지 않는다.
- 주 업무는 지속적인 담당 설정이다. 일회성 실행 명령과 구분하고, 자격/상황상 수행 불가하면 다른 가능한 업무를 탐색한다. 특별 업무는 해당 자격을 요구한다. 항해·정비는 특별, 경계·경비·낚시는 일반 업무 성능 관련 특기이며 직급과 특기를 동일 값으로 합치지 않는다.
- 일반 업무보다 식사·취침을 우선하고 기획의 야간 특별 근무 예외를 유지한다. 업무 성능에는 해당 능력·체력·경력·행복도를 적용하고 신뢰도를 직접 성능 배율로 쓰지 않는다. 경력 0이면 성능 0이 되는 산식을 피한다. 구체 능력 산식·욕구 주기·경력 자격 수치는 후속 구현에서 데이터로 정한다.
- 식량은 지정된 식량 품목에서 소비한다. 일반 식용 무역품을 자동 식량으로 전환하지 않는다. 부족 시 행복도·체력이 감소하되 굶주림만으로 사망하지 않는 규칙을 지킨다. 포로·야간 근무 등 실제 소비 주체의 예외는 해당 흐름에서 같은 재고 원본을 사용한다.

#### 9.5.3 업무 요청·선점·수행

- 제안 흐름: 수행 자격·생활/사건 상태 검사 → 주 업무 또는 남은 일반 업무 탐색 → 유효 대상·작업점으로 이동 → 도착 시 수행 조건 재검사와 선점 확정 → 업무 수행 → 완료/중단 시 정리. 처음 탐색할 때 얻은 대상 상태가 도착 때도 유효하다고 가정하지 않는다.
- 이동 목표와 실제 작업점 선점을 구분하는 방식을 제안한다. 도착해 자격·자원·작업점 조건을 만족하고 먼저 업무를 획득한 선원이 우선한다. 먼 거리에서 후보를 고른 것만으로 시설을 무기한 독점하지 않는다. 동시 획득은 단일 처리 순서로 한 선원만 확정하며 동률 정렬은 안정 ID 등 재현 가능한 기준으로 처리한다. 이는 ‘먼저 맡아 진행한 선원 우선’을 구현하는 제안으로 사용자 검토 대상이다.
- 다른 선원이 선점했거나 대상이 사라짐/완료/잠김·필요 물자 부족·경로 막힘이면 해당 조건을 실패로 반환하고 다른 후보를 탐색한다. 가능한 업무를 모두 검토해도 없으면 휴식하며 주변 안전한 지점으로 배회한다. 탐색 실패를 작업 성공으로 처리하거나 매 프레임 모든 대상을 재탐색하지 않는다.
- 선점은 시설/작업점 ID와 인물 ID의 관계로 하나만 관리한다. 완료·취침·식사로 이탈·사망·수감·전투·대상 제거·진행 불가능에는 점유가 영구히 남지 않도록 해제한다. 단순히 화면 밖이 되거나 다른 층이 표시되는 것은 해제 사유가 아니다.

#### 9.5.4 수리의 실행·중단·자원 반영

- 정비 자격과 유효한 작업점, 수리 가능한 내구도, 수리도구 재고를 확인한다. 완전 파손 전에는 선내 정비/조선소 수리가 가능하고 완전 파손은 조선소만 가능하다. 조선소 수리는 최대 내구도로 복구한다.
- 유효한 작업 구간에 대해서만 수리도구 소비와 시설 내구도 회복을 함께 확정한다. 소비 후 회복 실패 또는 회복 후 소비 실패 상태를 남기지 않는다. 구간·소비율·도구의 수량 단위는 구현 시 정하며 현재 임의 수치를 확정하지 않는다.
- 작업 중인 선원은 평상시보다 밀림에 강하되 고정 물체처럼 취급하지 않는다. 밀려 작업점 허용 범위를 벗어나면 진행과 해당 작업 자원 소비를 멈추고, 작업 시작 위치로 천천히 복귀한다. 복귀 후 거리/자격/대상/자원을 재검사해 재개한다.
- 일시 밀림·복귀 동안 기존 선점을 유지하는 방식을 제안한다. 단, 작업점 상실·복귀 불가·다른 우선 행동 진입에는 선점을 해제하고 재탐색한다. 복귀 불가 판정·재시도 간격은 막힘/교착 검증에 맞춰 정한다. 이동 경로와 무관하게 좌표만 바깥에 있는데 작업량을 올리지 않는다.

#### 9.5.5 이동·접촉·표현과 타층 유지

- 플레이어 입력과 선원 AI는 같은 이동 실행 계약에 이동 의도를 전달한다. AI의 목표/경로 선택과 실제 이동·접촉 해결을 구분한다. 실제 이동 결과를 한 경계에서 인물 위치 원본에 반영하고 Sprite·애니메이션·카메라는 결과를 읽는다. 입력·AI·Transform·저장이 각각 위치를 쓰지 않는다.
- 플레이어와 선원은 서로 물리적으로 밀 수 있어야 한다. 기존 9.1절의 ‘모든 유닛 쌍에 접촉을 강제하지 않음’은 불필요한 객체까지 물리를 적용하지 말라는 뜻이며 이 확정 접촉 요구를 생략하는 근거가 아니다. 벽·차단 시설·잠금 타일은 통행을 막고 바닥·장식은 불필요한 물리 계산에서 제외한다. 상호작용 감지와 물리 차단은 독립 역할이다.
- 일반 이동은 시간 기반의 연속 이동이며 좌표 점프로 대신하지 않는다. 포털·층 이동은 명시적 전환 예외다. 실제 물리 스텝·렌더 보간·카메라 갱신의 조합은 반복 접촉·방향 전환·정지 복귀·변동 프레임으로 검증해 선택한다.
- 비표시 층에도 인물·위치·목표·업무 진행·선점·시설 원본을 유지한다. 화면 가시성 때문에 이동·생활·작업 규칙이 달라지지 않도록 하며, 필요한 논리 접촉/통행을 표현 오브젝트의 Update나 활성 여부에 종속시키지 않는다. 화면 밖 물리/공간 질의의 구체 구현은 비용과 동일 규칙을 함께 검증해 결정한다.
- 저장은 확정 SaveEvent 때만 한다. 인물 현재 위치·행동·목적지·현재 중간 목적지·자원·작업 진행·복귀점을 보존하고 전체 경로는 재구성 가능하게 한다. 로드 시 선점 관계를 검증·재연결하며 이미 반영한 작업 자원을 재소비하지 않는다. 수면 저장의 기상 시작과 이후 업무 재평가는 P1-04에서 결합한다.

#### 9.5.6 시설 기능과 출항 검사

- 내구도 소진 시 기능 정지. 표시에는 검은색에서 붉은색으로 변하는 점선 윤곽·어두워지는 타일 요구를 반영한다. 잠김·파손·정상 기능 상태를 UI의 별도 원본으로 만들지 않는다.
- 침대 2×1, 대포 1×2, 화물 적재 1×1, 감옥 1×1의 기획 기준과 배치 층 제한을 유지한다. 화장실 등 미지정 크기와 대포의 구체 금지 층은 그림으로 확정하지 않는다.
- 시설 출항 검사: 침대 수가 선원 수 이상인지, 필수 시설이 최소 배치되어 기능하는지 확인한다. 선원 0명이라도 필수 침대 최소 조건을 없애지 않는다. 식량 부족·무선원을 새 출항 금지 사유로 추가하지 않는다. 후불 정산·명성/게임 오버는 별도 경계로 P1-05에서 연결한다.
- 돛 완전 파손은 감속 이동이며 침몰/이동 불가로 바꾸지 않는다. 실제 조타·항해 영향과 대포의 전투 전 적 체력 감소는 P1-04/06에서 연결한다.

**검증·미결정:** 자격 없는 특별 업무 거부, 같은 작업점 동시 획득, 밀림 중 작업 정지/완만한 복귀, 자원 소진·대상 제거·죽음/수감/전투 시 선점 해제, 타층 진행·재진입, 부분/완전 파손 수리, 출항 시설 조건을 점검한다. 실제 연속 입력·좁은 통로·벽/모서리·유닛 접촉·카메라·애니메이션 및 유닛/시설 수 증가 시 CPU·Physics·경로 갱신·GC 비용을 제품 Scene에서 검증한다. 경로 알고리즘·물리 방식·작업점 허용 거리·재탐색 주기·밀림 저항값·최대 규모·수치 성능 목표는 아직 확정하지 않는다. 저장·중단·자원 처리의 정합성을 확인하기 전 다른 기능으로 우회하지 않는다.

#### 9.5.7 공통 작업 실행 상태 — 사용자 수용

- 모든 작업 종류는 공통 상태 정의·전이 계약을 사용하되 상태 값은 각 선원의 작업 인스턴스마다 독립적으로 갖는다. 같은 상태 객체를 모든 선원이 공유하는 것이 아니다.
- 공통 상태: 작업하러 이동 중 / 작업 중 / 방해됨 / 복귀 중 / 완료 / 취소. 작업 인스턴스에는 담당 인물·작업 종류·대상·작업점·현재 상태를 연결하고 특정 작업에 필요한 진행/소비 데이터만 추가한다.
- 작업 중 상태이며 수행 조건이 유효할 때만 담당 기능을 실행한다. 수리와 조타는 같은 상태 흐름을 사용하되 실행 규칙·완료 조건이 다르다. 지속 업무를 임의로 유한 작업으로 바꾸지 않는다.
- 방해됨에는 이유를 둔다. 일시 밀림은 진행·소비 정지 후 복귀로, 대상 제거·자격 상실 등 재개 불가는 취소/선점 해제로 연결한다. 일시 복귀의 선점 유지·해제 조건은 9.5.4절을 따른다.
- UI의 세계 시간 정지는 작업 상태를 방해됨으로 바꾸지 않는다. 기존 상태를 유지하고 진행만 멈춘다. 로드 시 작업 상태와 선점/대상의 유효성을 재검사하며 부적합한 작업을 강제 재개하지 않는다.

## 10. P1-04 제안 — 항해·계획 경로·일지·기본 취침

### 10.1 항해와 조타

**2026-11-06 해수 표현 경계 보완:** 기존 SailingWater의 시각 결과는 사용자 미수용이다. NavigationState·조타·시간·저장의 원본은 유지하고, 해수는 자연 형상/색면→상대 흐름→수면선/SDF 국소 흐름·입자→별도 조명 순서로 분리한다. 아래 P5 첫 구현 계약의 기존 수면 수식이 새 Water 요구를 충족했다는 의미는 아니다. 요구 원문은 References/P5/WaterDesign_2026-11-06에 보존한다. Stage2-A 정적 수면은 사용자 승인되었다. Stage2-B는 독립 OceanAmbientReview의 OceanAmbientDriver가 표현용 경과 시간·4개 주기 위상·자연 파형/잔물결의 연속 이동량을 소유하며, 파도·보조 파도·잔물결·완만한 형상 변화에 공유 위상을 전달한다. 위상과 이동량이 모두0이면 승인된 정적 형상이다. 큰 파형의 생성 좌표 자체가 이동하고 잔물결은 별도 속도로 이동하며, 낮은 주파수의 변형을 더한다. 이 이동량은 항해 상대 흐름이 아니며 주기 위상처럼 래핑하지 않는다. 한 런타임 Material을4면에 공유하고 비활성화 시 원래 Material을 복구·런타임 사본을 해제한다. 정지는 시간을 누적하지 않으며 재개 시 보충하지 않는다. 이 표현 시계는 게임 시간·NavigationState·저장 원본을 변경하지 않는다. 사용자의 다음 단계 진행 지시 후 Stage3에서는 Game 복제 검토 Scene의 NavigationView에 선택적 OceanNavigationBinding을 연결했다. Binding은 GameClock 증가분과 Navigation 이동량을 읽고, OceanRelativeFlow가 표현용 속도 응답/누적 샘플 좌표를 계산한다. 이 값은 상태 원본이 아니라 재생성 가능한 시각 상태다. 공통 파형 계산 앞의 샘플 좌표에만 더해 파형 내부 수식과 결합하지 않는다. 자연 물결은 같은 게임 정지 경계를 따르며 비표시 층에서도 시각 시계는 유지한다. 원본 Game의 기존 수면 경로는 Stage6 통합 전까지 보존한다. Hull/SDF·입자·조명은 미구현이며 Stage3 사용자 수용 전 추가하지 않는다.

**P5 1단계 실행 계약(2026-11-05):** 사용자가 요청한 고정 선박 방식으로 논리 해상 공간과 선내 연속 좌표를 분리한다. GameSessionState.Navigation은 함선 ID·해상 X/Y·방향·항속·항해 ID/순번·누적 거리의 유일한 원본이다. 갑판/시설/물리 Transform을 해상 좌표로 이동·회전하지 않는다. NavigationView는 이 값을 지도 아이콘과 수면 샘플링/물살에 투영하며 상태를 되쓰지 않는다. 해상 좌표1단위는1해리, 내부 각도는 동쪽0°/반시계, 표시 방위는 북쪽0°/시계다. 항속·선회율은 NavigationSettings의 조정 가능한 초깃값이며 확정 밸런스가 아니다. GameClock의 동일 gameSeconds로 일정 조타 구간을 해석적으로 적분하여 표시 프레임 분할에 따른 경로 차이를 줄인다. 방향타 조작은 일시적 입력 소유 상태이고 조작 종료 후 현재 방향 전진을 유지한다. 자격 선원/자동 조타는 생성하지 않는다. 메뉴·일지·전환 정지는 항해에도 적용한다. 1단계의 최소 항해 시작은 실제 상태를 생성하며 항해 중 하선은 차단한다. 자동 입항/완료 및 전체 항구 출항 조건은2단계다. 정상 종료 저장은 버전2로 Navigation을 포함하고 버전1은 읽기 시 정박 상태를 보완하되 파일을 자동 갱신/초기화하지 않는다.

- 출항 요청은 시설·정산 등의 조건을 통과해야 한다. 통과 전 항해 ID를 완료/차감하지 않으며 실제 출항 확정 때 새 항해 ID·출발 항구를 연결한다. 동일 항구 복귀도 항해 1회다. 선원 0명 출항을 허용한다.
- Navigation은 현재 함선의 해상 위치·방향·속도 원본을 관리한다. 플레이어의 방향타 조작과 자격 있는 일등 항해사의 자동 조타는 같은 조타 명령 계약을 사용한다. 계획선은 Journal의 계획 데이터이며 그리기만으로 이동 명령을 발행하지 않는다.
- 자동 조타 여부는 자격 있는 선원이 해당 조타 작업을 실제 수행 중인지로 판별한다. 방해됨/복귀 중 등 작업 불가이면 자동 조타를 실행하지 않는다. 수동 조작 종료·외부 방향 변경을 근거로 별도 자동 복귀/해제 모드를 추가하지 않는다. 작업 중이면 현재 방향에서 계속 경로 보정하고 작업을 멈추면 보정을 멈춘다. 배 자체의 지속 이동은 별개다.
- 바람 추진 시스템은 제외한다. 폭풍의 조타 효과는 사건 명령으로 연결한다. 돛 파손은 감속 이동이며 침몰·완전 정지로 바꾸지 않는다. 속도/회전 수치는 구현 시 데이터로 정한다.
- 입항은 계획 경로와 독립된 항구 Trigger Area·함선 위치 관계로 판정한다. 경로의 존재·말단·자동 조타 여부가 입항을 발생/차단하지 않는다. 출항 직후 같은 항구 판정은 잠그고 지정 범위 밖에서 재활성화한다. 유효한 Trigger 관계에 따라 해당 항해 ID를 한 번만 완료하고 계약·일지에 결과를 반영한다. 하선은 별도이며 입항 자체의 추가 SaveEvent는 확정하지 않는다.

### 10.2 일지 원본·기록·이월

- 실제 현재 항로 추적 데이터, 플레이어가 기록한 확정 이력, 계획 경로를 같은 Journal 모델 안에서 의미별로 구분한다. 위치 원본은 Navigation이며 Journal은 기록에 필요한 경로를 누적한다. 경로 샘플은 게임 내 기록 데이터이고 매 프레임 디스크 저장이나 프레임 이력 저장을 뜻하지 않는다. 기록 정밀도·샘플링은 품질/비용을 검증해 결정한다.
- 일지 기록 시 해당 일자 미기록 구간과 기록 가능한 사건을 기존 기록에 누적한다. 하루 여러 차례 기록해도 덮어쓰기·중복 구간을 만들지 않는다. 사건 아이콘은 실제 발생 위치를 사용하고 임의 추가하지 않으며 제거·텍스트 메모를 지원한다. 항해 ID별 계획/실제 경로/사건/메모를 보존하고 과거 항해 레이어를 중첩 표시한다.
- 최신 일지 기록 후 추가 상호작용 없이 취침한 경우, 취침 진입 때 조건을 고정하고 마지막 기록~기상까지의 경로를 기상 처리에서 일지에 자동 확정한다. 이후 다시 기록 버튼을 누르지 않아도 갱신된 경로가 보인다. 수면 자체·수면 구간 내 날짜 변경은 조건을 무효화하지 않는다.
- 기록 후 미니게임·다른 이벤트 참여 또는 취침 전 날짜 변경이 있었고 재기록 없이 취침했다면 마지막 기록~기상 전체 구간을 일지에 추가하지 않는다. 수면 구간만 별도 반영하지 않는다. 재기록 시 최신 기록이 새 기준이다. 기존 확정 기록·계획 경로는 보존한다. 기타 상호작용 분류는 임의로 추가하지 않으며 미니게임/사건 구현은 후속 범위다. 기상 SaveEvent는 일지 반영 여부와 무관하게 현재 게임 결과를 저장한다.

### 10.3 수면 계산·시간 점프·기상 저장 — 사용자 정정 수용

- **사용자 확정(2026-11-01): 정상 기상 시각은 게임 시간 오전 8시(08:00)로 고정한다.** 취침 후 도래하는 08:00를 정상 수면 계산의 목표로 삼으며 임의 수면 길이나 조정 가능한 기상 시각으로 대체하지 않는다. 기존 자동 입항에 의한 수면 중단은 정상 기상 시각과 별도 규칙으로 유지한다. 사건 관련 중단은 후속 범위다.
- 수면은 플레이 화면에서 시간을 배속 재생하는 기능이 아니라 게임 시간을 기상 시점으로 Jump하는 기능이다. 화면을 일시적으로 멈추거나 컷씬/전환 화면을 표시하는 동안 경과 구간에 필요한 항해·생활·업무·식량·일지·날짜 갱신을 고속 연산한다. 단순히 시계 숫자만 바꾸지 않고 그 동안 일어난 상태 변화를 반영한다.
- 계산 완료 → 기상 상태 확정 → 10.2절 조건에 따른 일지 경로 자동 반영 또는 미기록 구간 정리 → 수면 SaveEvent로 저장 → 플레이 화면/입력 복귀 순서로 제안한다. 저장 데이터에는 기상 시점과 수면 과정의 결과가 포함된다. Load는 그 기상 상태에서 시작하며 수면 연산·자원 소비·입항 결과를 다시 실행하지 않는다.
- 정상 기상 08:00는 확정 규칙이다. 계산 스텝/구간 방식은 별도 구현 결정이며 프레임별 전체 물리 재현을 필수로 하지 않는다. 고정 게임 시드·판정별 파생 시드에 맞춰 같은 조건에서 같은 게임 결과를 유도한다. 화면 전환의 현실 시간·렌더 프레임 수가 결과를 바꾸지 않는다.
- 선원이 조타 작업 중이면 고속 연산에서도 같은 작업/조타 규칙을 적용한다. 야간 조타·식량 소비 및 다른 선원의 생활 상태를 반영한다. 계산 중 항구 Trigger Area를 지나칠 수 있으므로 구간 내 진입을 검사해 자동 입항 시각까지만 진행하고 기상 처리한다. 보이는 프레임이 생략되어도 공간 경계·날짜 변경·소비를 건너뛰지 않는다.
- 하루 경과와 기상 저장이 같은 상태 경계에 겹치면 필요한 갱신을 마친 동일 상태를 한 번 기록하는 제안을 수용된 방향으로 반영한다. 여러 날짜가 있는 경우의 중간 저장 요청 병합/작업 중 정상 종료 요청은 같은 일관성 계약을 지키도록 구현한다.
- 계산 실패 시 부분 갱신을 기상 완료로 표시하거나 기존 정상 저장을 덮어쓰지 않는다. 구체 복구·재시도 UX는 구현 시 결정한다.
- 실제 사건·불침번 등은 현재 계산 범위에 구현하지 않는다. 향후 Event가 구간을 중단할 진입 경계만 보존하며 사건 체크포인트·재개 정책은 기본 프레임워크 검증 이후 설계한다.

### 10.4 현재 검증 범위와 후속 경계

- 현재는 계획선만으로 자동 항해하지 않음, 조타 자격/작업 상태, 같은 항구 재입항 차단·항해 1회 확정, 일지 누적·이월, 기본 취침 중 시간/항해/생활 진행·입항 중단, 확정 SaveEvent·로드 시 기상·중복 결과 방지를 검증한다. 실제 사건 발생·불침번·전투·미니게임 실행을 통과 조건에 넣지 않는다.
- Event를 연결할 때 진행 중인 항해·작업·취침을 안전한 경계에서 제어하고 끝난 뒤 기존 세션으로 복귀할 확장점을 보존한다. 구체 중단/재개·저장 시점과 종류별 결과는 후속 설계에서 정한다. 기존 GameDesign의 사건·불침번 요구를 폐기하지 않는다.
- 규모 비용은 항로 기록 길이·동시 과거 레이어·시간 가속 시 생활 갱신량이다. 실제 지도·연속 항해·기상/전환·성능·사용자 수용은 각 제품 Slice에서 검증한다.

### 10.5 계획 경로 — 말단 연결·필기 표현·방향 보정

**상태:** 2026-11-01 사용자 수용 및 정정 반영. 적응 보존 좌표점 노드·오차 제한 필기 표현·구간 삭제/말단 처리·저장 병합 방향 수용. 입항 독립 판정·선원 작업 기반 조타·기상 시점 저장 정정 반영. 알고리즘 수치는 구현 시 검증한다. 일지 자동 반영 조건은 최신 GameDesign 6.3절 및 이 문서 10.2절에 정정 반영했다. 기존 임의 중간 편집·정확한 경유점 추종·수동 조타 후 자동 해제 제안을 이 절로 대체한다. 근거는 GameDesign 6.1~6.3절·A05~A06 및 현재 사용자 설명이다.

#### 10.5.1 사용자 지정 동작

- 경로는 Linked List와 같은 순서 연결 구조로 생성·관리한다. 새 경로는 반드시 현재 마지막 노드에서 이어지고 분기나 떨어진 독립 선을 만들지 않는다. 중간 노드를 삭제하면 그 노드 뒤의 노드들도 모두 제거하며 이후 남은 말단부터 다시 이어 그린다. 삭제 대상으로 지정한 노드 자체도 제거하는 해석을 기본 제안으로 명시한다. 이전의 임의 부분 수정/지우기 제안은 폐기한다.
- 지도에는 자연스러운 펜 곡선이 보여야 한다. 입력 점을 무조건 늘리거나 큰 오차의 베지어 보정으로 사용자 입력을 다른 경로로 바꾸지 않는다. 실제 항적도 같은 표현 품질 문제를 고려한다.
- 경로는 방향 지시다. 배는 계속 전진하고, 주기적인 조타 보정으로 경로에서 크게 벗어나지 않으며 경로 진행 방향을 따라간다. 외부 요인으로 방향이 바뀌더라도 유효한 자동 조타가 계속 수행 중이면 경로로 복귀할 수 있어야 한다. 정확한 노드 통과·좌표 고정·경로 위 순간 이동이 아니다.

#### 10.5.2 공통 경로 데이터와 저장 — 기술 제안

- 공통 경로는 ID·항해 ID·수정 버전·머리/말단·순서 연결 노드와 구간 형상을 사용한다. 노드는 연결/삭제 단위이고 구간 형상은 노드 사이 펜 선을 나타낸다. 형상에 필요한 점을 전부 힙 LinkedList 객체로 생성할 필요는 없다. 단순 점 노드 체인 또는 노드별 압축 점열 중 실제 편집 단위에 맞춰 선택하며 의미가 같은 별도 경로 원본을 만들지 않는다.
- 연결 구조의 채택과 메모리 구현은 구분한다. 실제 .NET LinkedList, 안정 ID/인덱스 연결, 연속 버퍼 중 비용과 저장 복원에 맞는 방식을 선택한다. 객체별 포인터·할당 비용을 무시하지 않되, 단순 좌표 데이터가 과도하다고 계측 없이 단정하지 않는다. 노드 삭제 단위가 실제 펜 입력 표본인지 사용자 제어점/획 구간인지는 아직 미결정이다.
- 해상 세계 좌표를 원본으로 두어 지도 줌/화면 크기와 분리한다. 계획과 실제 항적은 같은 좌표/곡선 표현을 재사용하지만 서로 독립된 경로 인스턴스이며 계획 수정으로 실제 항적을 바꾸지 않는다. 실제 항적에는 계획 편집 규칙을 자동 적용하지 않는다.
- 확정 SaveEvent에서 경로 연결/형상과 추종 진행 정보를 저장한다. 캐시·화면 메시·편집 임시 상태는 재구성하며 별도 원본으로 저장하지 않는다. 저장 복원·삭제 때 끊어진 연결·순환 연결·현재 추종 구간의 삭제를 검사한다. 게임 경로 데이터 누적은 매 프레임 디스크 저장이 아니다.

#### 10.5.3 펜 곡선과 데이터 양 — 권고 제안

- 입력 획을 일시 수집한 뒤 거리뿐 아니라 굽힘/방향 변화와 원래 선에서의 최대 이탈 오차를 기준으로 적응적으로 점을 남긴다. 직선에는 적은 점, 급한 굴곡에는 필요한 점을 둔다. 예리한 의도적 모서리를 무조건 둥글게 만들거나 작은 고리·왕복선을 무조건 삭제하지 않는다.
- 우선 권고는 오차 제한으로 정리한 공통 중심선 + 둥근 연결/끝단·적절한 안티앨리어싱의 스트로크 렌더링이다. 노드 개수와 화면 선분 분할 수를 동일하게 강제하지 않는다. 표시 메시의 세분화는 캐시이며 원본 노드를 늘리지 않는다. 단, 직선 형상을 세분화/둥근 조인만 해서는 실제 중심선 곡률이 새로 생기지 않으므로 충분한 굴곡 표본은 유지한다.
- 추가 곡률 보정이 필요하면 작은 구간의 제한된 곡선 맞춤을 검토한다. 전역 베지어로 전체 획을 덮어쓰지 않으며 원본 입력과의 최대 이탈·급한 방향 전환·지형 침범을 검사한다. 사용자가 그린 곡선과 차이가 크면 해당 구간 표본을 더 보존하는 편을 택한다. 정확한 곡선 알고리즘·오차·최대 줌·노드 단위는 실자산/입력 비교 전 미확정이다.
- 조타가 참조하는 공통 중심선과 지도 표시가 서로 다른 길을 가리키지 않도록 한다. 곡선 보정을 실제 경로로 채택하면 공간 투영·앞쪽 목표·길이 계산에도 같은 형상을 사용한다. 줌별 표시 LOD나 선 두께·펜 질감은 원본 경로를 변경하지 않는다.
- 실제 항적은 같은 형상/표현을 사용하되 항해 이동에서 표본을 얻는다. 압축 오차를 제한해 실제로 지나지 않은 지형·입항 경계를 지나간 것처럼 바꾸지 않는다. 원본/캐시/작업 입력의 보존 수명과 항해 이력 누적량은 계측하여 정한다.

#### 10.5.4 경로 주변 조타 — 권고 제안

- 자격 선원이 조타 업무를 수행할 때만 실행한다. 단순 계획 작성은 자동 조타 시작이 아니다. 배는 Navigation의 현재 방향·속도로 연속 이동하고 주기적 조타 명령으로 방향을 바꾼다.
- 현재 진행 구간 주변에서 배의 위치/짧은 예측 위치를 중심선에 투영한다. 투영점보다 경로 진행 방향으로 앞선 목표를 선택해 경로 횡방향 오차와 접선 방향을 함께 줄인다. 선 자체를 향해서만 조타해 직각 왕복하는 동작을 피한다. 허용 폭/방향 오차 안에서는 불필요한 보정을 줄이는 방식을 제안한다.
- 최근 진행 구간·경로상 거리로 연결의 순서를 유지한다. 자기 교차·가까운 평행 구간에서 전역 최근접점만 골라 후반 구간으로 점프하거나 지나온 경로를 역주행하지 않는다. 큰 이탈 시 탐색 범위를 넓히더라도 의도된 진행 순서와 재합류 구간을 검증한다. 복귀 회전·선회 반경·구간 초과·끝점 판정은 실제 항해 품질로 검증한다.
- 방향이 바뀐 원인과 관계없이 자격 선원이 조타 작업 중이면 주기적으로 경로 보정을 수행한다. 플레이어 수동 조작 종료 후 자동 복귀 여부라는 별도 상태는 두지 않는다. 작업 불가/중단 시 보정을 멈춘다. 같은 처리 경계의 방향 명령 충돌은 작업/상호작용 처리 순서에서 정합성을 지키며 별도 게임 모드를 추가하지 않는다.
- 말단 추가는 추종 중인 앞부분을 바꾸지 않는다. 뒤쪽 삭제로 현재/전방 참조가 사라지면 남은 경로에서 진행을 검증한다. 유효 추종 구간이 없어지거나 말단 추종이 완료되면 경로 보정만 끝내고 기존 방향의 전진은 유지한다. 입항은 언제나 독립된 항구 Trigger Area 판정이며 이 경로 상태에서 호출하지 않는다.
- 보정 간격·예측 거리·허용 폭·회전 속도는 선박 속도/선회 성질과 함께 조율한다. 매 프레임 전체 노드를 탐색하지 않으며 틱 간 위치 순간 이동으로 보정을 대신하지 않는다. 초기부터 특정 경로 추종 알고리즘·수치를 확정하지 않는다.

**검증:** 말단만 추가·중간 이후 일괄 삭제·저장/로드 연결 일치, 입력 대비 곡선 오차·확대 시 각짐·모서리/고리 보존·메모리/메시 비용, 계획/실제 항적의 공통 표현, 조타 자격·외부 방향 변화 후 재합류·교차/평행 경로의 순서 유지·연속 회전·끝점/입항 구분. 현재는 설계 검토이며 구현·실험 결과를 통과로 기록하지 않는다.

## 11. P1-05 제안 — 항구 거래·고용·정비·계약 정산

**상태:** 2026-11-02 사용자 수용·정정 반영 완료. 근거: GameDesign 8·9.3~9.4·12절, A09~A13·A15~A16·A25. 확정 수치·지급 시점·예외는 유지하며 아래 실행 순서·실패 정책은 제안이다. 전투/포로·사건/미니게임 상세를 현재 단계에서 설계하지 않는다.

**UI 결정 시점(사용자 지시):** 자세한 거래 UI·표기 구조는 구현 과정에서 사용자가 추가 설명한다. 현재는 필요한 정보·명령·확정/취소의 상태 계약만 다루며 버튼 배치·표기·선택 절차를 추가 확정하지 않는다. 기존 D 도안과 확정 기획은 유지한다.

**2026-11-02 사용자 확정:** 출항 시 보유금 우선 정산 방향 수용. 부족 시 강제 매각 후 선원 목록에서 지급 대상을 직접 선택하며 부족한 지급 버튼은 비활성화한다. 수용 부족 상태에서도 변경 선택/검토는 허용하고 결제/최종 확정은 금지한다. 제거 시설은 보관 자산으로 반환하고 보관 상태에서 매각·폐기 가능하다. 정확한 UI·가격·계수·콘텐츠 수량은 구현 단계에서 구체화한다.

### 11.1 공통 상태와 거래의 확정 경계

- 모든 상품은 공통 ItemDefinition과 소유자별 Inventory/ItemStack을 사용한다. 시장 화면·강제 매각·소비·화물에 별도 품목 사본을 만들지 않는다. 거래 가능·식량 용도·무역품 여부·적재 비용을 구분한다. 현재 가격은 항구/상인의 시장 조건과 품목 ID로 계산하며 품목 공통 정의에 항구별 현재 가격을 하나로 덮어쓰지 않는다.
- Wallet이 실제 골드 원본, Inventory가 실제 수량 원본이다. UI 선택 수량·합계·협상 미리보기는 확정 상태가 아니다. 선택 변경으로 실제 돈·재고·행복도·신뢰도를 누적 변경하지 않는다.
- 명령 → 대상/수량/가격 조건·골드·재고·적재 여유 재검사 → 관련 변경을 함께 확정 → 결과 통지 순서를 제안한다. 자금/재고/용량 부족·대상 변경은 실패 이유를 반환하고 일부 금액만 차감하거나 일부 물건만 옮기지 않는다. 복수 품목 구매는 전체 선택을 한 번에 확정하는 방식을 제안한다. 가격/능력 산식·반올림·정수 단위는 데이터와 명시된 수치 정책으로 구현 시 정한다.
- 중복 클릭/같은 요청 재전달에 대해 같은 거래 ID를 두 번 적용하지 않는다. 원자적 상태 확정과 디스크 저장은 별개다. 거래/고용/수리 때마다 새 SaveEvent를 자동 추가하지 않고 확정 SaveEvent에서 당시 게임 결과를 저장한다. 로드는 저장된 거래 결과를 다시 명령으로 재실행하지 않는다.

### 11.2 구매·판매·시장 갱신

- 구매는 품목별 상인, 판매는 거래 대행인이 담당한다. 한 상인이 모든 품목을 취급하거나 구매/판매 창구를 자동 통합하지 않는다. 품목/수량 선택 → 합계 미리보기 → 명시적 구매/판매 확정이며 상품·골드 이전은 같은 거래 경계다.
- 게임 날짜 변경 시 항구 가격·수요·재고를 갱신한다. 고정 게임 시드와 항구 ID·날짜·품목/판정 용도로 파생한 결과를 사용해 UI 재열기/로드로 재추첨하지 않는다. 필요한 실제 변경 상태는 저장한다. 날씨·국가 상황 등 후속 요인은 계산 연결점만 남기고 첫 대표 흐름에 모든 콘텐츠를 구현하지 않는다.
- 거래 UI 정지 중 세계 날짜·요청 기한도 멈춘다. 주민 요청은 같은 품목/재고·골드 계약에 요청 ID·조건·보상·게임 시간 만료를 연결한다. 최대 수량·주기·만료 수치는 임시 데이터다. 수락 확정 때 조건·기한·재고를 재검사하고 교환/요청 완료를 함께 반영한다. 미구현 요청 콘텐츠를 가짜 보상으로 표시하지 않는다.

### 11.3 고용·협상·계약

- 주점이 소개하는 후보도 같은 Character 원본과 안정 ID를 사용한다. 화면 재열기로 같은 후보의 능력·이력·협상 난수를 재추첨하지 않게 조회와 후보 생성 갱신을 구분하는 방식을 제안한다. 후보 갱신 주기·소개비·콘텐츠 수량은 별도 구현 데이터다.
- 인물 확인 → 평가·협상 조건 미리보기 → 횟수 N·선불/후불 선택 → 고용 확정 순서다. 평가의 -50~+50을 임의 퍼센트로 바꾸지 않는다. 행복도/신뢰도 변화는 미리보기에서 표시하고 실제 확정은 고용 때 한 번만 적용한다. 약속과 불이행에 따른 신뢰도 연결은 유지하되 구체 대사/계수는 현재 선행조건으로 만들지 않는다.
- CrewContract가 계약 ID·인물 ID·합의한 항해당 금액·횟수·총액·지급 방식·잔여 횟수·정산 상태를 소유한다. 인물 원본의 능력을 계약에 복제하지 않는다. 합의 후 금액은 향후 시세/능력 변화로 소급 변경하지 않는 방식을 제안한다.
- 선불은 고용 확정 때 N회분 전액을 한 번 차감한다. 후불은 고용 때 차감하지 않고 N회 완료 후 전액 지급 대상이다. 별도 월급·항해별 분할 지급을 추가하지 않는다. 계약 생성·필요한 차감·고용 관계를 함께 확정하며 실패하면 일부만 생성하지 않는다.
- 고용 시 침대 부족을 자동 고용 금지 규칙으로 확대하지 않는다. 부족한 상태와 출항 제한을 알리되 시설 출항 검사는 따로 한다.
- **사용자 확정(2026-11-02):** 지급 의무가 발생한 미지급 후불금이 해당 선원에게 남아 있으면 그 선원과의 재계약을 금지한다. 해당 후불금을 지급한 뒤 이 제한을 해제하고 다른 재계약 조건을 검사한다. 다른 선원의 미정산 후불금은 계약 대상 선원의 고용/재계약을 차단하지 않는다. 아직 지급 기한이 되지 않은 후불 계약 전체를 미정산 금지 조건으로 취급하지 않는다.
- UI는 대상 선원의 미정산 사유와 지급 경로를 표시하고, 재계약 확정 명령도 같은 characterId의 만기 미지급 후불금을 다시 검사한다. 버튼 비활성화만으로 규칙을 구현하지 않는다. 기존 채무를 새 계약으로 덮어쓰거나 재계약에 자동 합산해 제한을 우회하지 않는다.

### 11.4 입항·게시판·항해 차감

- 항구 Trigger가 실제 입항을 확정 → 항해 ID 완료 1회 → 해당 항해의 계약 적용 1회 → 일지/정박 상태 갱신 순서다. 잔여 횟수가 있으면 계약을 유지하고 0이면 만료 처리한다. 수면 계산·중복 Trigger·로드에서도 같은 voyageId를 두 번 차감하지 않는다. 누구를 해당 항해 참여자로 확정할지는 실제 승선/고용 관계와 출항 흐름에 연결하며 UI 목록 자체를 기준으로 삼지 않는다.
- 게시판은 계약 원본의 조회 화면이다. 현재 계약과 이번 항구에서 재고용 가능한 직전 동행 이력을 구분하고 다른 항구 만료자를 전역 목록에 쌓지 않는다. 만료됐지만 미지급인 후불금은 숨기지 않고 지급할 수 있어야 한다. 이름·직급·지급 방식·계약 금액·잔여 횟수·미정산 상태는 같은 원본에서 읽는다.
- 선원별 지급/재계약은 계약 ID로 처리한다. 생포·처형·사망·용서 등 미래 사건의 계약 유지/파기 규칙은 기존 요구를 보관하고 현재 프레임워크에 가짜 사건으로 구현하지 않는다.

### 11.5 미정산 출항·강제 매각·명성

- 출항 요청에서 만기 후불금과 다른 출항 조건을 확인하고 보유 골드를 우선 정산에 사용한다. 전액을 충족하면 자동 정산하는 수용 방향을 따른다. 총액이 부족할 때 임의 순서로 일부 선원을 자동 지급해 선택권을 없애지 않고 기존 보유금도 강제 매각 후의 지급 가능 금액에 포함하는 연결 방식을 적용한다. 자금 부족/미지급을 발견했다고 즉시 게임 오버로 처리하지 않는다.
- 기획 흐름은 만기 미정산 확인 → 강제 매각 UI → 사용자가 무역품 선택(필요액 초과 허용) → 항구 시장가의 60%를 초기 임시 매각률로 금액 산출 → 정산 → 잔여 미지급금에 비례한 전역 명성 감소 → 남은 채무 소멸 → 게임 오버 한계 판정이다. 전역 명성 기준 이하이면 게임 오버, 초과이면 다른 출항 조건 통과 여부에 따라 진행한다.
- 강제 매각은 사용자가 선택한 무역품만 대상으로 한다. 자동 전량 매각·시설/다른 함선 강제 처분·임의 채무 이월을 추가하지 않는다. 확보한 골드와 만기 미지급 선원 목록을 표시하고 사용자가 선원을 선택해 지급한다. 현재 골드가 그 선원의 지급액보다 적으면 지급 버튼을 비활성화한다. 부분 지급/자동 비례 배분을 추가하지 않는다. 지급 명령에서도 금액·계약 상태를 재검사하고 골드 차감과 지급 완료를 함께 확정한다. UI 비활성화만으로 규칙을 보호하지 않는다.
- 정산 후 다른 시설 조건으로 출항이 막혔더라도 이미 완료된 매각·지급·명성 처리를 같은 출항 재시도마다 반복하지 않게 확정 상태를 유지하는 방식을 제안한다. 최종 출항 불가가 예상되면 정산 UI를 열기 전에 먼저 알리는 UI는 가능하지만 서로 다른 원본을 만들지 않는다.

- 매각액에서 실제 지급액만 차감하며 남은 골드는 보존한다. 매각·지급·출항 처리 완료를 구분하고 지급 대상 목록/버튼을 결과에 맞춰 갱신한다. 잔여 미지급금의 명성 감소·채무 소멸은 출항 정산을 확정하는 경계에서 한 번만 처리하며 단순 목록 열기·지급 클릭만으로 미지급금 전체를 소멸시키지 않는다. 구체 취소·확정 UI는 구현 단계 설명에 따른다.

### 11.6 정비·시설 증감·함선 교체

- 조선소의 개별/일괄 수리는 대상·손상·비용을 제시하고 확정 때 골드 차감과 내구도 최대 회복을 함께 처리한다. 선내 수리는 정비 자격·도구 소비·완전 파손 전 조건을 사용하므로 조선소 처리와 역할을 구분한다.
- 시설 구매/추가/재배치/제거/해금은 공통 시설 정의와 함선 컨테이너 규격을 사용한다. 실제 시설 목록·타일 점유·비용·필요한 재고 이전을 일관되게 확정한다. 기본 배치 시설을 임의로 제거 불가로 만들지 않으며 명시된 고정/층 제약은 지킨다.
- 시설 변경·함선 교체로 수용량이 부족해져도 변경 대상을 선택하고 배치를 검토하는 것은 허용한다. 후보/편집 상태와 실제 확정 상태를 분리하며, 부족이 해소되기 전 금액 지불 및 최종 확정은 금지한다. 확정 명령에서 용량·점유·가격 등 조건을 다시 검사한다. 검토 중 실제 화물/인물/시설을 삭제·이전·차감하지 않으며 취소하면 기존 상태를 유지한다.
- 함선 교체는 해당 함선이 실제 정박한 항구에서만 한다. 대상 선택은 가능하나 수용·기존 제약·필요 이전을 모두 검증한 후 결제와 현재 승선 관계/실제 이전을 함께 확정한다. 실패하면 기존 함선·화물·위치를 유지한다. 포로의 구체 이전/인계는 후속 사건 범위이며 수용 검사 연결점만 보존한다. 가격·교체 UI는 구현 단계에서 구체화한다.

- 시설 제거 확정 시 보관 가능한 자산으로 반환한다. 보관 자산에서 매각·폐기를 선택할 수 있으며 제거 자체를 즉시 매각/환급/폐기로 처리하지 않는다. 같은 시설 정의와 실제 인스턴스 정체성·내구도/개별 상태를 유지하고 설치 소속·점유를 해제해 이중 보유를 막는다. 판매/폐기 확정 때 보관 관계와 필요한 골드 변경을 함께 반영하며, 실제 보관 위치·용량·재설치 비용·판매 가격/폐기 UI는 구현 과정에서 설명·확정한다. 화물 적재용량과 보관 자산 용량을 임의로 동일시하지 않는다.

### 11.7 다른 항구 서비스·검증·범위

- 전역 명성은 협상·미지급 정산·게임 오버, 현지 평판은 가격·수요·의뢰에 연결한다. 같은 값으로 합치지 않는다. 시청·정보 구매·의뢰는 공통 인물/품목/거래 계약에 연결하되 세부 콘텐츠·후속 사건 보상을 먼저 만들지 않는다. 프레임워크 완료 범위의 서비스는 실제 대표 흐름으로 활성/미구현 Frame을 구분한다.
- 검증: 구매/판매 전체 확정과 취소·골드/재고/적재 부족, UI 미리보기 비변경, 같은 품목/인물 원본, 날짜 갱신 재현, 선불/후불 N회·같은 항구 복귀·만료/잔여 유지, 게시판 지역 이력·만기 지급, 초과 강제 매각 잔액·채무 소멸·명성 기준, 시설 제거/교체 실패 보존·조선소 완전 수리, 중복 요청·SaveEvent 후 로드 결과 재적용 없음. 실제 화면·입력·정지·저장/복원·품목/선원 수 증가 비용은 제품 Slice에서 검증한다. 현재 설계 문서만으로 테스트 통과를 주장하지 않는다.

## 12. P1-06 수용 — Event 연결 경계·기본 저장/복원·종료·게임 오버

**상태:** 2026-11-02 사용자 수용 및 Event 적용 방식 정정 반영. GameDesign 13절·A27 및 최신 SaveEvent/기상·범위 결정을 근거로 한다. 사건·전투·불침번·미니게임·포로·사건 체크포인트 상세는 기본 프레임워크 검증 이후다. 이 절은 해당 기능을 지금 구현/설계하는 허가가 아니다.

### 12.1 Event 적용 범위·전략 교체·공통 생명주기 — 사용자 수용

- Event 진입은 단순 Scene 전환을 뜻하지 않는다. 동일 게임 프레임워크에서 Event 적용 범위의 일부 로직/전략을 일시 교체하고, 종료 시 기존 로직으로 복귀하는 구조다. Event마다 별도 프레임워크·게임 세션·인물/품목/함선 원본을 만들지 않는다. Scene/컷씬이 필요해도 표현·로딩 수단이며 Event의 정체성/규칙 원본은 아니다.
- 전략 패턴은 교체 가능한 행동/정책을 담당하고, 템플릿 메서드와 같은 공통 생명주기 방식은 적용·실행·종료·복원 순서 및 정리를 담당한다. 특정 기반 클래스 계층이나 모든 게임 기능의 전략화를 지금 강제하지 않는다. 실제 변경되는 경계에만 필요한 공통 계약을 둔다.
- 공통 흐름은 진입 요청 → 적용 가능 여부/현재 정책 충돌 확인 → 교체 대상과 기존 연결 확보 → 적용 → Event 실행 → 종료/중단 → 자신이 교체한 연결과 획득한 제어권 정리·복원 → 기존 게임 진행이다. 개별 Event가 공통 검증·복원 절차를 우회하거나 결과를 여러 번 확정하지 않도록 한다.
- 적용 범위는 필요한 대상·시스템·정책에 한정한다. 적용하지 않은 세계·인물·업무·UI 로직은 기존 프레임워크를 계속 사용한다. Event라는 이유로 전체 게임을 일괄 정지하거나 전 시스템 로직을 교체하지 않는다. 공통 입력·시간·저장 조정자를 사용하며 실제 교체 정책/정지 여부는 Event별 후속 설계에서 정한다.
- 종료 시 복원하는 것은 임시 로직/정책 연결과 제어권이다. Event 실행 중 정상 확정된 위치·재고·골드 등 게임 상태를 진입 시점으로 일괄 롤백하는 뜻이 아니다. 현재 상태를 같은 공통 모델에서 유지하며 원래 정책이 그 상태를 읽고 재개한다. 사건별 실패/보상·체크포인트는 후속 범위다.
- 준비 실패는 원래 동작을 유지하고, 부분 적용 실패·예외·취소·세션 종료에도 자신이 적용한 변경만 정리하는 경계를 둔다. 다른 모달의 정지 토큰이나 다른 소유자의 전략을 기본값으로 무조건 초기화하지 않는다. ‘기본 전략 재설정’보다 실제 이전 연결/소유 관계를 검증해 복원한다.
- 동시에 여러 Event가 같은 정책을 교체할 때의 중첩·우선권·충돌 처리는 미정이다. 전략을 무조건 스택으로 만들거나 모든 Event를 동시에 허용하는 규칙을 선행 확정하지 않는다. 현재는 적용 소유권·중복/충돌 검사·안전한 복원을 보장할 연결 경계만 정의한다. 구체 합성 방식은 실제 Event 설계 단계에서 정한다.
- 현재 실행할 Event가 없으면 가짜 사건·성공 결과·임시 전투를 만들지 않는다. 구체 Event 종류·발생 조건·교체할 전략·진행 필드·종료 결과·사건 중 저장/로드는 기본 프레임워크 완성 및 테스트 통과 이후에 설계한다. Event 진입/종료 자체를 현재 단계의 새 SaveEvent로 추가하지 않는다.

### 12.2 SaveEvent와 저장 일관성

- 저장 요청은 확정된 정상 종료·승선·하선·항해 중 하루 경과·기상 결과 확정에서 발생한다. 현재 단계에서 거래/고용/수리·계획 편집·자동 입항·Event 진입/종료를 추가 SaveEvent로 만들지 않는다. 필요한 상태는 다음 확정 SaveEvent의 기록에 포함된다.
- 요청한 시스템이 별도 파일을 쓰지 않고 하나의 저장 조정자가 순서를 관리한다. 이미 확정된 게임 상태가 중간에 바뀌어 위치·재고·계약의 시점이 섞이지 않도록 안전한 경계에서 공통 데이터를 읽는다. 파일 쓰기 동안의 읽기 일관성을 위한 임시 자료는 허용하되 새로운 게임 원본이나 프레임별 기록 시스템을 만들지 않는다.
- 같은 상태 경계의 중복 요청은 한 기록으로 합칠 수 있고, 서로 다른 경계는 최신 확정 순서를 보존한다. 오래 걸린 이전 쓰기가 최신 기록을 덮어쓰지 않도록 직렬화/세대 번호를 적용하는 방식을 제안한다. 쓰기 방식·스레드·포맷은 구현 시 적합한 방식을 정한다.
- 저장 대상은 플레이 ID/버전/종료 상태, 시간, 고정 시드·파생 키의 원본 정보, 세계·항구·함선/시설·인물·재고/골드·계약/정산·일지/계획/조타 진행 등 실제 구현된 공통 데이터와 안정 ID 관계다. 미래 기능의 빈 저장 필드/가짜 데이터를 일괄 추가하지 않는다. UI 객체·Sprite·Scene 인스턴스·매 프레임 물리 이력은 저장하지 않는다.

### 12.3 파일 기록·실패·복원

- 별도 임시 파일에 기록 → 형식/필수 관계 등 검증 → 성공한 파일로 원자 교체하는 방식을 제안한다. 실패 시 마지막 정상 파일을 보존하고 성공 표시를 하지 않는다. 내부 복구용 이전 정상본은 가능하나 사용자가 과거 슬롯을 선택하는 기능으로 확장하지 않는다.
- 저장 실패는 게임 규칙 실패와 구분한다. 이미 확정된 거래·지급·승하선을 저장 재시도 때문에 다시 수행하지 않는다. 실패를 표시하고 정상 종료는 저장 성공 전까지 완료하지 않는 기존 계약을 따른다. 사용자에게 저장 없이 종료하는 새 경로를 임의 제공하지 않는다.
- 로드는 플레이/형식 버전·종료 상태·정의 존재·ID 중복/연결·수량/금액 등 필수 조건을 검증한다. 잘못된 파일을 새 게임으로 조용히 덮어쓰거나 누락된 인물을 가짜로 생성하지 않는다. 지원 버전 변환이 필요하면 명시된 변환만 적용한다.
- 복원 중 입력·시간·AI·업무·Trigger의 게임 효과를 차단한다. 공통 데이터와 관계/선점/공간을 연결하고 뷰를 구성한 뒤 검증을 마쳐 진행을 허용한다. 항구 Trigger의 생성/복원 콜백으로 입항·계약 차감이 다시 발생하지 않아야 한다.
- 기상 저장은 수면 계산·일지 반영까지 완료한 상태다. 로드 때 수면 연산·소비·일지 자동 추가를 다시 하지 않는다. 일반 SaveEvent 로드의 기상 시작 표현은 저장된 시간/위치/배 방향을 보존하며 정상 기상 08:00로 시간을 다시 점프시키는 것이 아니다. 다른 선원의 저장된 업무·취침 상태까지 전부 플레이어와 함께 깨우지 않는다.
- 마지막 SaveEvent 이후의 미저장 진행을 로드로 되돌려 동일 행동을 재수행하는 것은 허용한다. 고정 시드·안정적 파생 키로 같은 판정 결과를 유도하며 이미 저장된 결과를 로드 부작용으로 재가산하는 것은 방지한다.

### 12.4 정상 종료·게임 오버의 차이

- 정상 종료는 입력 차단 → 상태 경계 확정 → 정상 종료 저장 요청 → 성공 확인 → 뷰·구독·세션 정리 → 종료다. 다음 로드에서 그 저장 상태를 이어간다.
- 게임 오버는 해당 플레이 종료다. 현재 기본 흐름의 원인은 미지급 정산 후 전역 명성이 설정된 기준 이하인 경우이며 전투 패배·선원 없음·식량 부족을 새 게임 오버 원인으로 만들지 않는다. 구체 기준/비율은 임시 데이터다.
- 종료 확정 후 신규 진행 명령을 차단하고 해당 playId의 이어하기 금지를 영속적으로 기록하는 방식을 제안한다. 이는 일반 SaveEvent를 계속 늘리는 것이 아니라 기존 ‘게임 오버 플레이는 과거 저장으로도 이어하기 불가’ 요구를 지키는 종료 기록이다. 게임 상태 파일과 종료 표식의 기록/복구 순서를 함께 설계해 정상본 복구로 금지를 우회하지 않게 한다.
- 종료 기록 실패 시 성공한 영속 종료로 표시하지 않고 실패/재시도 경로를 유지한다. 디스크 기록 자체가 불가능할 때 강제 종료 후에도 제한을 보장한다고 주장하지 않는다. 온라인 검증·외부 파일 변조 방지는 범위 밖이다.
- 새 게임은 새로운 playId·seed·상태로 시작한다. 기존 플레이/종료 기록을 새 플레이 생성 때문에 임의로 지우지 않는다. 저장 슬롯의 실제 개수·새 게임 교체 확인 UI·파일 보존 수명은 구현 단계에서 구체화한다.

### 12.5 검증과 미결정

- SaveEvent별 정확한 시점·중복 요청·쓰기 순서, 거래/계약/입항/일지 복원 중복 없음, 고정 시드/파생 키 재현, 잘못된 ID·파일 손상·지원하지 않는 버전·쓰기 실패·이전 정상본 복구, 정상 종료 후 이어하기, 게임 오버 후 과거 정상본 이어하기 차단·새 플레이 분리를 점검한다. Event는 진입/복귀 경계의 실패·중복·제어권 반환 계약만 확인하고 사건 콘텐츠 구현 통과를 요구하지 않는다.
- 실제 파일 포맷·경로·동기/비동기 기록·복구 파일 수·플랫폼 종료 콜백·성능 수치는 구현 시 검증한다. 게임 오버 플레이별 종료 기록과 일반 로드의 시간/위치 보존 방향은 사용자 수용됐다. 종료 표식의 실제 파일 구성·플랫폼 기록 방식은 구현 단계에서 검증한다. 현재는 설계이며 자동 테스트·실제 저장 복원 통과가 아니다.

## 13. P1-07 수용 — 표현·입력·제작·검증과 전체 요구 대조

**상태:** 2026-11-02 사용자 수용·정정 반영. 생성 예시의 시각 방향 수용, 일지 좌측 가죽 Day 텍스트 Toggle 탭 및 모바일 상세 후속 범위 확정. GameDesign 3~4·14·16~20절, VisualStandards 및 DevelopmentRules 근거. 게임 코드를 작성하거나 Unity 설정/Scene/Prefab을 변경하는 작업이 아니다. P1-01~06에서 수용한 기본 프레임워크 범위와 사용자 구현 단계 UI 결정권을 유지한다.

### 13.1 시각·공간과 화면 구성

- 배치는 D01~D12, 월드/유닛/지도 화풍은 G02/G03/G01을 기준으로 한다. E 이미지는 구성 분위기 참고이며 입체 RPG 시점·실존 지명·마법·골드 추가·자동 항해 버튼을 가져오지 않는다. 2026-11-02에 D01~D05·D07·G01~G03·E02를 다시 열어 대조했다. 나머지 제공 원본의 앞선 열람 결과도 유지한다.
- 월드는 위에서 내려다보는 2D 공간, 유닛은 머리/몸/분리된 손의 SD 표현을 사용한다. 작은 형태라도 방향·이동/정지·작업·방해/복귀가 구별되어야 한다. 배경 타일·벽·문·시설과 통행 의미를 읽을 수 있게 한다. 하늘에서 보는 함선의 선체 방향은 가로형이며 실제 표시 층은 하나다.
- 월드 캐릭터 Sprite와 고용/대화 일러스트는 표현 자산 역할을 구분하고 공통 인물 ID에 연결한다. 아이템/시설도 공통 정의·개별 상태에서 표시 자산을 참조한다. UI별로 새 인물/품목 게임 모델을 만들지 않는다.
- HUD는 D01의 금화/퀘스트/항해 일자/날짜·시간대 구획을 유지한다. 상단 항해 일자는 일지를 여는 버튼이 아니다. 실제 활성 도메인의 값만 표시하고 아직 없는 콘텐츠를 가짜 값으로 채우지 않는다. 모바일 조작 영역은 장래 Frame이며 PC 실제 조작은 키보드/마우스 우선이다.
- 일지는 D03의 좌측 이력·하단 펜, 중앙 지도, 우측 선택 정보·이미지, 우상단 닫기 구획을 유지한다. 최신 사용자 정정에 따라 좌측 과거 항해일은 지도 썸네일이 아니라 일체형 가죽 인덱스 탭으로 표현하고 `Day 1`, `Day 2`처럼 텍스트만 표기한다. 각 탭은 해당 기록 레이어의 Toggle이며 기존 과거 레이어 중첩을 보존한다. 표시 이름과 내부 항해/날짜 식별을 구분해 서로 다른 항해의 같은 Day 표기가 같은 데이터가 되지 않게 한다. 탭 배치·스크롤·선택 피드백 세부는 실제 UI 제작에서 검증한다. 지도는 가상 지형과 절제된 종이/수면 표현을 사용한다. 계획/실제 항적/과거 레이어는 같은 좌표 원본에 연결하고 선 색·두께·선택 표현은 구분 가능하도록 P2 실제 화면에서 검토한다. 그림을 누르는 것만으로 조타·출항하지 않는다.
- 거래/고용/조선소는 D04/D05/D07의 상대 구획을 기준으로 하되 상세 UI·표기·선택 순서는 구현 과정에서 사용자가 설명한다. 이번 제안은 확정된 명령·미리보기 비변경·골드 부족 지급 비활성·선원별 미정산 제한·수용 부족 결제 금지 같은 상태 계약만 고정한다. 게시판 등 별도 도안 없는 화면의 임의 레이아웃을 지금 확정하지 않는다.
- 한국어 폰트는 현재 Galmuri11 기본 설정을 사용한다. P0 사용자 확인과 별개로 실제 제품 화면에서 글리프·줄바꿈·말줄임·목록 폭·대비·표시 크기를 검증한다. 1280×720/1600×900/1920×1080은 최초 비교 세트 제안이며 최종 지원 범위/PPU/Canvas 배율·카메라 크기를 지금 임의 확정하지 않는다.

### 13.2 입력·상호작용·UI 상태

- 공통 Game Action 계약에 PC 입력을 연결한다. 이동·상호작용·UI 닫기와 지도 그리기/선택 입력을 문맥에 맞춰 분리한다. 구체 키 배치는 구현 단계에 정하고 게임 규칙에 키코드·터치 좌표를 넣지 않는다. 모바일 구체 동작·터치 제스처·조이스틱·기기 UX는 기본 프레임워크 완성 및 테스트 통과 이후 설계·구현한다. 현재는 PC와 모바일이 같은 행동 계약을 사용할 입력 인터페이스와 입력 소스 활성/제어권 경계만 둔다. 두 입력 어댑터가 같은 행동을 중복 발행하거나 서로 제어를 덮어쓰지 않도록 입력 소스 선택/문맥 라우팅을 한 경계에서 관리한다. 기기 전환·혼합 입력 우선순위·실제 모바일 구현을 지금 선행 설계하지 않는다.
- 같은 프레임의 입력이 UI 버튼/지도와 뒤의 월드에 동시에 적용되지 않아야 한다. 최상위 모달이 입력을 받고 월드 조작은 차단한다. UI 닫기는 해당 모달만 닫고 정지 토큰도 자기 것만 반환한다. 선택창/거래 확정 실패를 게임 규칙 성공으로 표시하지 않는다.
- 월드 상호작용은 대상 ID·유효 거리·차폐·현재 행동 가능 여부를 공통 경계에서 확인한다. 책상은 실제 일지 접근점, 시설은 유효 작업/접근점을 사용한다. 상호작용 요청 자체가 위치·재고·가격을 직접 수정하지 않는다.
- Screen은 선택/스크롤/편집 초안 등 표현 상태만 소유한다. 원본 공통 데이터 조회/변경 결과를 받아 표시하며 별도 저장·가격/계약 규칙을 만들지 않는다. 기본 화면은 Editor 제작 Prefab, 동적 행은 같은 사전 제작 Prefab을 바인딩/재사용한다. 매 프레임 전체 목록을 재생성하지 않는다.
- Active / FrameDisabled / HiddenUntilStage / DebugOnly를 구분한다. FrameDisabled는 표시만 하고 명령·가짜 성공·준비중 대화창을 발행하지 않는다. 첫 Slice에서 열기/닫기만 활성인 일지는 계획/기록 도구를 비활성 Frame으로 둘 수 있다. 실제 항해 단계에서 순차 활성화한다.

### 13.3 Scene·Prefab·공통 데이터와 생명주기

- 제안 기본은 하나의 정식 Game Scene/Composition Root와 지역·함선 층·캐릭터·시설·UI의 편집 가능한 Prefab이다. 제품 진입 Scene과 테스트 Fixture를 구분하고 테스트마다 별도 게임 로직/세션 원본을 만들지 않는다. 구체 씬 분할은 필요/로딩 규모가 확인될 때 승인된 경계 안에서 검토한다.
- Domain은 공통 게임 데이터·규칙, Application은 사용 사례·경계 조정, Infrastructure는 입력/파일/물리/로딩 어댑터, Presentation은 표시/피드백, Composition은 참조 연결을 담당한다. 폴더/asmdef를 나눠도 시스템마다 공통 구조체를 재정의하지 않는다. 불필요한 빈 인터페이스·assembly를 선행 생성하지 않는다.
- Definitions는 읽기 전용 종류/스탯, 실제 인스턴스는 상태 원본, Prefab은 표현이다. 시설 증감은 컨테이너의 인스턴스/점유/기능에 반영하고 표시만 새로 바꾼다. 화면/층/Prefab 제거가 계약·인물·시설 상태 삭제가 되지 않도록 한다.
- 뷰·입력·전략 교체·UI 구독은 획득한 연결을 해당 수명 종료 때 해제한다. Domain Reload 생략 환경의 Play 재진입에서도 전역 구독·정지·세션이 중복되지 않게 한다. Event는 전략 교체 범위만 준비하며 지금 사건별 Scene·클래스·저장 필드를 만들지 않는다.

### 13.5 A번호 밖의 요구와 최신 정정 정합성

- 공통 데이터는 인물뿐 아니라 품목·시설·함선 전반, 필요한 기능/스탯 컴포지션이며 Master 객체·시스템별 중복 모델을 금지한다. 정의와 소유자별 수량·개별 내구도는 실제로 다른 사실이다.
- 함선 모델별 수용 크기·타일·기본 시설과 실제 설치 목록을 구분한다. 제거 시설 보관→매각/폐기, 시설 편집/함선 교체의 수용 부족 시 선택 허용·결제/확정 금지는 11.6절에서 구현한다.
- 입항은 독립 Trigger, 조타 활성은 선원 실제 작업 상태, 계획은 말단 연결/뒤쪽 삭제, 배는 연속 전진·주기적 보정이다. 링크 노드·필기 곡선·추종 표현을 같은 공통 형상 계약으로 연결하며 경로 끝이 입항 명령이 되지 않는다.
- 수면은 화면 전환 중 고속 계산 후 기상 시점 Jump·08:00 정상 기상·결과 저장이다. 일지 자동 반영은 최신 6.3절 조건을 적용하고 ‘수면 경로 무조건 다음 기록 이월’로 되돌리지 않는다. 일지 기록과 파일 저장도 구분한다.
- 후불 제한은 채무가 있는 해당 선원만 재계약 금지다. 보유금 우선 정산과 부족 시 선원별 수동 지급을 구분하고 골드 부족 버튼 비활성/명령 검사를 함께 적용한다. 거래 UI 상세는 구현 시 사용자 결정으로 남긴다.
- Event는 전략 교체·공통 생명주기·한정 범위 복원이다. 기본 프레임워크 검증 이후 상세 설계하며 이전 사건 체크포인트 문구를 현재 승인된 구현 요구로 해석하지 않는다. 종료시 임시 전략 복원과 확정 게임 상태 롤백은 다르다.
- 기타 본문의 항구별 구매 상인/판매 대행인·시장 일일 갱신·주민 거래·정보 구매·일지 메모/이력·시설 증감/함선 교체·선원 능력/욕구/약속·포털/접근/모바일 Frame은 관련 기본 도메인/제작 계약에 연결한다. 상세 의뢰·정보·협상 콘텐츠 수량/대사/가격과 미니게임·치료·세계 생성은 현재 선행 구현하지 않는다. A번호가 없다는 이유로 확정 요구를 삭제하지 않는다.

### 13.6 완료·품질·비용 검증 계약

- 첫 Slice는 선장실 이동→책상 상호작용→일지 열기/닫기→시간·입력 복귀→기본 저장/복원이다. 목표 스타일 자산·Editor 제작·구조·실조작·저장까지 함께 수용한 뒤 늘린다. 이 단계의 계획/기록 컨트롤은 필요한 위치의 비활성 Frame이며 항해 기능이 아니다.
- 기본 반복 프레임워크는 대표 거래/고용/정비→출항→생활/업무/항해/경로/취침→입항/계약 정산→SaveEvent/Load/Exit까지 반복 검증한다. 잘못된 조건 거부·중복 요청·재입항·자원 부족·동시 선점·밀림 복귀·타층 진행·수면 계산·일지 조건·저장 실패/손상/게임 오버를 포함한다. 사건 콘텐츠가 없어도 이 경계를 실제 게임으로 검증할 수 있어야 한다.
- 구조 검토, EditMode 규칙/계약, PlayMode 실제 Scene/입력/포커스·역할별 접촉, 제품 Game View·연속 영상/직접 관찰, SaveEvent 후 재진입, Player의 CPU/Physics/GC/메모리/로딩을 구분한다. 합성 상태/Controller 직접 호출만으로 실제 조작·시각 통과를 주장하지 않는다.
- 비용 확장축은 선원 수·작업 후보/시설 수·경로 점/항해 기록 길이·화면 목록 행·활성 공간/접촉 수·수면 계산 구간/일일 갱신 수·저장 크기다. 정상/혼잡 조건과 기기·해상도·버전을 명시해 측정하고 동일 조건 회귀를 비교한다. 무조건 전체 매프레임 탐색·경로 재계산·UI 재생성·무근거 풀링/ECS 도입을 피한다. 수치 목표는 측정/대상 사양 합의 후 확정한다.
- P1 통과는 기본 구조 계약의 수용과 현재/후속/구현시 결정의 구분이며, P2 이후 아트/실행/저장/성능 통과를 뜻하지 않는다. P0 사용자 한글 확인도 제품 화면 전체의 검증으로 확대하지 않는다. 문서에는 수행 증거·미확인을 구분해 기록한다.

### 13.7 남겨 둘 결정과 다음 단계

- P1-07 사용자 수용: 공통 화면/입력 책임, 단일 게임 진입과 Prefab 제작, 현재/후속 범위 대응, 검증·비용 계약. 예시의 공간·유닛·일지 시각 방향은 사용자 상상과 일치함을 확인했다. 예시 좌측 지도 썸네일은 폐기하고 가죽 Day 텍스트 Toggle 탭으로 정정한다. 시각 방향 수용은 실제 Unity 화면·가구 수·색 수치·조작감 승인으로 확대하지 않는다.
- P2에서 실제 아트·PPU/피벗/레이어·카메라·Canvas·해상도별 한글/화면 규격과 사용자 시각 수용을 확보한다. 초상 스타일의 별도 참고 자료가 아직 없다는 사실을 유지한다. 생성 예시는 원본 D/G 레퍼런스를 대체하거나 실제 Game View 증거가 되지 않는다.
- 초기 플레이어 시작 구역·최초 시간·대표 항구/상품/시설 수·구체 입력 키·물리/추종/수면 계산 구현·가격/확률 수치는 해당 Slice 시작 전에 기존 규칙 안에서 결정하고 문서에 반영한다. 기획 변경이 필요한 항목은 사용자에게 제시한다. 별도 과거 기획·운영 로그를 자동 계승하지 않는다.
- P1-01~07 검토·수용 및 최신 정정 대조를 마쳤으므로 기본 프레임워크 범위 P1 설계 게이트를 통과로 판정한다. 공통 상태 소유자·명령/결과·수명·저장 경계·Event 한정 교체·제작/검증 책임은 본문과 A01~A28 대응표에 연결돼 있다. 구현 의존성·시각·실행·성능은 아직 검증 전이다. 다음은 P2 실제 아트/화면 규격 검토이며 현재 작업에서 자동 착수하지 않는다.
